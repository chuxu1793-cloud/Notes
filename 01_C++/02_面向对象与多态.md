# 面向对象与多态

C++ 的多态由"继承 + 虚函数 + 指针/引用"三者共同支撑，其底层机制是虚函数表与虚表指针。本篇从对象模型出发，依次整理继承中的成员布局、重载/隐藏/覆盖的区别、虚表的动态绑定过程与多重继承下的布局，最后落到几个与对象生命周期强相关的语言细节：`delete this`、`new` 失败、对象创建位置的限制，以及单例模式的几种语言层实现。

## 面向对象概括

- 数据结构 + 方法组成**对象**；
- 具有相同行为的对象归纳为**类**；
- 类的**封装**隐藏内部实现细节；
- **继承**实现类的特化/泛化；
- **多态**实现基于对象动态类型的**动态分派**。

这五句话对应 C++ 的 class、封装（访问控制）、继承、虚函数四套机制。多态是其中的关键：它让"用不变的代码处理可变的类型"成为可能，同类的泛型技术还有模板（编译期决议）和 RTTI（运行时决议）。

## 继承中的成员变量

同名成员变量**不会**形成覆盖（override），它们在派生类对象中各占一块独立空间。访问时遵循"就近原则"：自己有就用自己，没有就用父类的。

```cpp
class A {
public:
    int m;
    A() { m = 1; printf("A.m=%d\n", m); }
    virtual void print() { printf("%d\n", m); }
};

class B : public A {
public:
    int m;
    B() { m = 2; printf("B.m=%d\n", m); }
    void print() { printf("%d\n", m); }
};

class C : public B {
public:
    int m;
    C() { m = 3; printf("C.m=%d\n", m); }
    void print() { printf("%d\n", m); }
};

int main() {
    B b;                 // A.m=1  B.m=2
    b.print();           // 2
    printf("%d\n", b.m); // 2

    A *c = new C;        // A.m=1  B.m=2  C.m=3
    c->print();          // 3（虚函数，按动态类型分派）
}
```

要点：

1. 三层各有一个 `m`，对象里存在三份，不是同一份被改写；
2. 变量访问是**静态绑定**的，由表达式的静态类型决定访问哪一份：`A* c` 只能访问 `A::m`（值为 1），要访问 `C::m` 得先向下转型，写成 `static_cast<C*>(c)->m`；注意 `c->C::m`、`c->B::m` 都不合法——限定名只能指到静态类型 `A` 及其基类中存在的成员；
3. 成员函数是虚函数时走动态分派，因此 `c->print()` 输出 3；
4. 这也说明"派生类同名成员隐藏基类成员"只发生在**名字查找**层面，空间并未复用。

## 多重继承的构造与析构

以经典的 Panda 为例：`Panda : public Bear, public Endangered`，`Bear : public ZooAnimal`，`Endangered : public ZooAnimal`（虚拟继承）。

![](../../技术笔记/assets/D8EEA98927C44C7DBB685E2AF6DD4C30.png)

构造顺序：

1. `ZooAnimal`（最上面的虚基类先于一切）；
2. `Bear`（第一个直接基类）；
3. `Endangered`（第二个直接基类）；
4. `Panda` 自身成员，最后执行 `Panda` 构造函数体。

两条必须记住的规则：

- 构造次序**不受**初始化列表中基类出现顺序影响，只取决于**继承声明顺序**（虚基类优先）；
- 析构按构造的逆序进行：`Panda`、`Endangered`、`Bear`、`ZooAnimal`。

### 多重继承下的对象模型

![](../../技术笔记/assets/WEBRESOURCE0cccd2dd1c0187551d95f18c59841271.png)

![](../../技术笔记/assets/56325D5E8DCA4B249BE3276E75D2CBF2.png)

要点：

1. 每个带虚函数的基类子对象各有一套虚表（因此多重继承的对象里有多个虚表指针，分别位于各基类子对象的起始处）；
2. 派生类重写某基类的虚函数时，会替换**对应虚表**中该槽位的函数指针；
3. 派生类新增的虚函数，通常追加在**第一个**基类的虚表中；
4. 由于有多个虚表指针，把派生类指针转成不同基类指针时地址会发生变化，这直接导致下面的现象：

```cpp
class A { public: virtual ~A() {} };
class B { public: virtual ~B() {} };
class C : public A, public B { };

C *c = new C;
A *a = static_cast<A*>(c);
B *b = static_cast<B*>(c);

c == a;    // true，A 是主基类，子对象位于偏移 0
c != b;    // true，B 子对象在 C 之后，指针需要偏移
```

这也是为什么"多重继承下用 `void*` 保存对象地址再转回来"很容易出错。

### 虚继承与虚基类表

虚继承解决菱形继承中公共基类被重复继承的问题，代价是引入虚基类表指针（vbptr）。下面是一个 32 位下的常见布局：

```cpp
class A { public: int a; };                        // 4
class B : virtual public A { public: int b; };     // 12 = a(4) + b(4) + vbptr(4)
class C : virtual public A { public: int c; };     // 12
class D : public B, public C { public: int d; };   // 24 = a,b,c,d(16) + 2 个 vbptr(8)
```

具体大小与编译器、指针宽度相关（64 位下 vbptr 为 8 字节），这里只说明"每个虚继承分支各带一个虚基类表指针"的结构性事实。

## 重载、隐藏与覆盖

三个概念经常被混用，判据其实很清楚。

### 函数重载（overload）

1. 发生在**同一个类**（或同一作用域）中；
2. 函数名相同；
3. 参数类型、个数不同，或成员函数的 const 属性不同；**不能**只靠返回值类型区分；
4. virtual 可有可无，虚函数与普通函数在同一类中同样构成重载。

### 函数覆盖（override）

1. 发生在基类与派生类之间；
2. 基类中该函数声明为 `virtual`；
3. 函数名、参数类型、参数个数、返回值类型全部相同。

例外（C++ 允许的协变返回类型）：虚函数返回**本类对象的指针或引用**时，派生类可以返回派生类类型的指针/引用，仍构成覆盖。

### 函数隐藏（hide / name hiding）

1. 发生在基类与派生类之间；
2. 函数名相同；
3. 参数类型、个数、返回值中任意一项不同（或基类不是虚函数）。

基类与派生类之间的同名函数，只可能是**隐藏**或**覆盖**，不存在重载关系——因为重载要求同一作用域。

隐藏的表现：基类 `func()` 被派生类 `func()` 隐藏后，通过派生类对象**无法**直接调用基类的 `func()`；但基类的 `func()` 确实被继承下来了，可以用 `obj.Base::func()` 显式限定调用。

```cpp
class A {
public:
    void test() { fun1(); }
private:
    void fun1() { int a = 0; }
};

class B : public A {
private:
    void fun1() { int a = 0; }
};

B b;
b.test();     // 内部调用的是 A::fun1，不是 B::fun1
```

关键结论：**隐藏只影响外部名字查找，不影响类内部已经编译好的调用**。`A::test` 里的 `fun1()` 在编译 A 时就绑定到 `A::fun1`，与派生类是否隐藏无关。没有虚函数就没有多态，隐藏不产生多态效果。

### 虚函数实现多态的三个条件

1. 基类中把函数声明为 `virtual`；
2. 派生类中同名、同参数类型、同参数个数、同返回值类型；
3. 通过**基类指针或引用**调用（而非对象）。

缺任何一条，就只是隐藏，不会发生动态分派。

### 容易踩的边界情况

1. 基类和派生类都是虚函数、同名，但形参类型或个数不同：不构成覆盖，只是隐藏，没有多态效果；
2. 基类不是虚函数、派生类声明为 virtual：不构成多态，只是隐藏；
3. 两者都是虚函数、参数相同但返回值不同：编译报错（虚函数在隐藏时返回值冲突）；注意若两者都**不是**虚函数，则不会报错，隐藏成功；若基类不是虚函数而派生类是虚函数，也不报错；若基类是虚函数而派生类不是，会报错。结论：**涉及虚函数时，返回值类型必须一致**。

补充：派生类定义同名函数后，基类的所有同名重载版本都会被隐藏（不是只隐藏签名相同的那个）。若想保留基类版本，需要 `using Base::func;`。C++11 起应使用 `override` 关键字，让"本想覆盖却写成了隐藏"在编译期暴露出来。

## 虚函数表与动态绑定

### 虚表与虚表指针

C++ 标准并未规定虚函数的实现方式，主流编译器（Itanium ABI / MSVC）都采用虚函数表（vtable）。

- 每个**包含虚函数**的类有一张虚表，它是函数指针数组，元素是该类各虚函数的地址；
- 同一类的所有对象共享同一张虚表；虚表本身属于类而不属于对象；
- 对象内部含有一个指向本类虚表的指针（vptr），由编译器隐式添加；vptr 的初始化发生在**构造函数**中（因此构造期间调用虚函数不会分派到派生类）；
- 非虚函数不进入虚表，直接调用。

```cpp
class A {
public:
    virtual void vfunc1();
    virtual void vfunc2();
    void func1();
    void func2();
private:
    int m_data1, m_data2;
};
```

![](../../技术笔记/assets/0103AD627A884D5DA25B6CA28DBACDB9.png)

![](../../技术笔记/assets/5B6A95D856B540A8A1684F142A606F1E.png)

需要强调：虚表内的函数地址在编译/链接期就能确定（作为只读数据），**运行时变化的只是对象里的 vptr 指向哪张表**。

### 动态绑定的执行过程

```cpp
class A {
public:
    virtual void vfunc1();
    virtual void vfunc2();
    void func1();
    void func2();
private:
    int m_data1, m_data2;
};

class B : public A {
public:
    virtual void vfunc1();       // 覆盖 A::vfunc1
    void func1();                // 隐藏 A::func1
private:
    int m_data3;
};

class C : public B {
public:
    virtual void vfunc2();       // 覆盖 A::vfunc2
    void func2();
private:
    int m_data4;
};
```

![](../../技术笔记/assets/9E30E4ED25104647886E71750B42F1BA.png)

- A vtbl：`{ &A::vfunc1, &A::vfunc2 }`
- B vtbl：`{ &B::vfunc1, &A::vfunc2 }`
- C vtbl：`{ &B::vfunc1, &C::vfunc2 }`

规律一句话：**对象的 vptr 指向自己类的虚表；虚表中的槽位指向"继承链上最近一个重写该函数的类"的实现**。

```cpp
B bObject;
A *p = &bObject;
p->vfunc1();
```

执行 `p->vfunc1()` 的步骤：

1. 通过 `p` 取到对象里的 vptr（vptr 属于基类子对象，所以基类指针也能访问）；
2. 按 `vfunc1` 在虚表中的固定槽位索引取出函数地址；
3. 跳转调用。

可用表达式概括为：

```cpp
(*(p->__vptr)[n])(p)
```

即 `p->vfunc1()` 实际调用 `B::vfunc1()`。

发生动态绑定需要同时满足：

- 通过指针或引用调用（对象调用在编译期就确定了）；
- 指针发生向上转型（upcast，派生类 → 基类）；
- 调用的是虚函数。

这三条之外的调用都是静态绑定。

### 多重继承下的虚表布局

每个基类子对象各有一张虚表，派生类新增的虚函数放在第一个基类的虚表末尾：

```
Derive : public Base1, public Base2, public Base3
Derive 对象：
  [ vptr(Base1 子对象) ][ Base1 数据 ]
  [ vptr(Base2 子对象) ][ Base2 数据 ]
  [ vptr(Base3 子对象) ][ Base3 数据 ]
  [ Derive 自己的数据 ]
```

这样设计的目的是：无论用哪个基类指针指向同一个派生类对象，都能通过该子对象自带的 vptr 找到正确的函数实现，从而保证

```cpp
Derive d;
Base1 *b1 = &d;  Base2 *b2 = &d;  Base3 *b3 = &d;
b1->f();   // Derive::f()
b2->f();   // Derive::f()
b3->f();   // Derive::f()
b1->g();   // Base1::g()
```

### 通过内存直接访问虚表（以及旧文中的错误）

早期流传的一篇《C++ 虚函数表解析》用强制类型转换遍历虚表，方法本身可以用作实验手段，但其中若干结论是错的，这里按正确版本记录。

```cpp
typedef void(*Fun)(void);

Base b;
Fun pFun = (Fun)*((int*)*(int*)(&b) + 0);   // 仅 32 位可用
pFun();                                     // Base::f()
```

**错误 1：虚表末尾有一个 NULL（或 1）作为结束标记。** 虚表没有结束符。原图中"多画的那个结点"只是紧接着虚表之后的内存，读取它属于越界访问（未定义行为）。旧文在 32 位 Windows 下观察到 NULL、在 Linux 下观察到 1，都是相邻数据的巧合，不能作为"虚表结构"来理解。判断虚表长度只能靠已知的虚函数个数（或调试符号/ABI 规则）。

**错误 2：把对象地址直接转成 `int*` 取 vptr。** 这假设指针是 4 字节，64 位下必须用指针宽度的类型：

```cpp
void **vtable = *reinterpret_cast<void***>(&obj);       // 取 vptr 指向的虚表
auto fn = reinterpret_cast<void(*)()>(vtable[0]);
```

**错误 3："vptr 一定在对象最前面"要加限定条件。** 只有在**主基类**（第一个非虚基类）子对象中，vptr 才位于偏移 0；多重继承的第二个及以后的基类子对象，其 vptr 位于该子对象的起始处，相对整个派生类对象有偏移。所以 `(void*)derived_ptr` 与 `(void*)base2_ptr` 常常不相等。

**错误 4：槽位编号可以直接照抄。** 槽位顺序在 Itanium ABI / MSVC 下确实按声明顺序排列，但标准不作保证；此外 Itanium ABI 中虚析构函数占**两个**槽位（complete object destructor 与 deleting destructor），有虚析构时后面的槽位编号会整体后移。写这类实验代码时务必先打印出实际布局再对齐。

**关于"安全性"的正确表述**：用父类指针调用子类**自有**（未覆盖父类）的虚函数，编译期就会报错；用虚表指针在运行时绕过编译器可以做到，但这是未定义行为，不是语言保证。访问 private/protected 虚函数同理——它们确实存在于虚表中，绕过访问控制能调到，但依然属于 UB，只能当实验看。

多重继承的遍历示例（实验代码，行为依赖 ABI）：

```cpp
Derive d;

// 每个基类子对象的 vptr 都要从该子对象自身的地址取，
// 不能按指针宽度在对象内存里递推（pVtab[1] 落在数据成员或其它槽位上）
void **vt1 = *reinterpret_cast<void***>(static_cast<Base1*>(&d));
void **vt2 = *reinterpret_cast<void***>(static_cast<Base2*>(&d));
void **vt3 = *reinterpret_cast<void***>(static_cast<Base3*>(&d));

// Base1 的虚表
reinterpret_cast<void(*)()>(vt1[0])();      // Base1::f（已被 Derive::f 覆盖）
reinterpret_cast<void(*)()>(vt1[1])();      // Base1::g
reinterpret_cast<void(*)()>(vt1[2])();      // Base1::h
reinterpret_cast<void(*)()>(vt1[3])();      // Derive::g1（新增虚函数追加在末尾）

// Base2、Base3 的虚表各自从对应子对象取
reinterpret_cast<void(*)()>(vt2[0])();      // Derive::f
reinterpret_cast<void(*)()>(vt3[0])();      // Base3 虚表的第一项
```

> 示例中的 Base1/Base2/Base3 只含虚函数、不含数据成员；有数据成员时 vptr 仍位于各子对象起始处，但子对象偏移与槽位顺序需按实际 ABI 先打印再对齐。

### 虚函数的开销

**空间开销**

1. 每个类一张虚表，增大二进制体积；
2. 每个对象多一个 vptr（32 位 4 字节，64 位 8 字节），小对象上占比可观，且会破坏缓存局部性。

**时间开销（表面）**

多一次内存寻址：先读 vptr，再读表项，然后跳转。相比普通调用确实慢，但幅度通常不大。

**真实开销**

普通函数是直接调用，地址在编译期确定；虚函数是间接调用，目标地址在运行时才从内存取出。现代 CPU 的间接跳转若预测失败会造成流水线冲刷，**分支预测失败才是主要成本**。因此在热点循环里，把"循环内不变"的虚调用提到循环外、或用 `final`/去虚化帮助编译器，往往比微调其它代码更有效。

## 引用与多态

引用同样能触发动态绑定，因为引用在实现上就是" dereference 后的指针"，动态类型信息没有丢失。

```cpp
class A {
public:
    virtual void fun() { std::cout << "A" << std::endl; }
};

class B : public A {
public:
    virtual void fun() { std::cout << "B" << std::endl; }
};

int main() {
    B b;
    A &a = b;    // A 类型的引用绑定到 B 对象
    a.fun();     // 输出 B
}
```

几点提示：

- 包含虚函数的类，编译器都会为它创建虚表；基类与派生类各有一张；
- 引用是别名，定义时必须初始化，标准未规定它是否占用存储（实现上通常等价于一个指针）；
- 用基类引用作为函数参数是最常见的多态用法：形参写基类类型，调用时传派生类对象，函数内部即可通过虚函数分派到派生类实现。这比"传指针"更安全（不会为空），代价是无法表达"可选"语义。

## delete this

结论先说：**在成员函数中调用 `delete this` 是合法的**，前提是对象由 `new` 分配，且此后不再访问该对象的任何成员（包括虚函数）。很多引用计数实现都用这个技巧（`release()`）。

原因在于对象的内存模型：对象内存里只有数据成员和 vptr，成员函数的代码放在代码段，与对象无关。调用成员函数时通过隐含的 `this` 参数定位对象。`delete this` 释放对象内存后，只要不触碰 `this` 指向的内容，函数继续执行不会出错；一旦读写数据成员或调用虚函数，就是访问已释放内存，属于未定义行为。

```cpp
class A {
public:
    A() { member = 1; }
    ~A() { member = 0; }
    void test() {
        std::cout << member << std::endl;   // 1
        std::cout << this << std::endl;
        delete this;
        std::cout << this << std::endl;     // 地址不变，delete 不会把指针置空
        std::cout << member << std::endl;   // 未定义行为
    }
private:
    int member;
};
```

关于这个实验要澄清两点：

1. **`delete` 不会把指针置为 null**，`this` 仍指向原地址，这块内存可能被分配器缓存而暂时仍可读，所以"打印出来还是原地址、member 变成 0"看起来很正常。member 变成 0 是因为析构函数把它清零了，而不是"对象还在"。读已释放内存是 UB，编译器优化后结果可能完全不同。
2. **对栈对象调用 `delete this` 是 UB。** 若 `A a; a.test();`，`delete` 一个并非由 `new` 得到的地址会导致堆管理器报错（macOS 上是 `pointer being freed was not allocated`，VS 下是 Debug Assertion Failed）。原文观察到"没问题"，是因为栈内存尚未被复用，属于侥幸，不能当作规则。

必须遵守的约束：

- 对象必须由 `new` 分配（不能是栈对象、`new[]` 的元素、placement new 的对象或静态对象）；
- `delete this` 之后不能再访问任何成员、不能调用虚函数、不能再次 `delete this`；
- **绝不能在析构函数里调用 `delete this`**：`delete` 会先调用析构函数，析构函数又 `delete this`，形成无限递归直至栈溢出；
- 调用方在 `release()` 之后不能再使用该指针（这是接口约定，编译器不检查）；
- 更安全的现代做法是用 `std::shared_ptr` / `std::enable_shared_from_this`，避免手工生命周期管理。

顺带复习 `this` 的类型：

- 非 const 成员函数中：`T* const`，可以改指向的值，不能改 this 本身；
- const 成员函数中：`const T* const`，两者都不能改；
- 不能自定义 this 形参，但可以显式使用；需要"把整个对象作为整体引用"时必须显式写 `*this`（如 `return *this;`）；
- const 成员函数只能把 `*this` 作为 const 引用返回。

## new 失败与 std::bad_alloc

`new` 申请失败（如内存耗尽、单次申请过大）时，默认行为是抛出 `std::bad_alloc` 异常：

```cpp
int main() {
    std::cout << "Attempting to allocate 1 MiB...";
    try {
        char *p = new char[1048576];
        std::cout << "Succeeded!\n";
        delete[] p;
    } catch (std::bad_alloc &e) {
        std::cout << "Failed: " << e.what() << "\n";
    }
    return 0;
}
```

若不想承担异常开销，可用 `nothrow` 版本，失败时返回 `nullptr`：

```cpp
char *p = new (std::nothrow) char[1048576];
if (p == nullptr) {
    std::cout << "Failed!\n";
} else {
    delete[] p;
}
```

要点：

- 捕获时应使用 `const std::bad_alloc&`（按引用捕获），按值捕获会切片（`bad_alloc` 本身无额外状态，但按引用是通用规范）；
- 异常抛出与栈展开有一定开销，原文给出的"额外 20~30ms"只是特定环境下的粗略估算，具体取决于实现与异常表配置（**待核实**）；
- 普通 `new` 抛异常而不是返回空，这是它与 `malloc` 的重要区别之一：`malloc` 失败返回 `NULL`；
- 可以通过 `std::set_new_handler()` 注册处理函数，在 `operator new` 失败时先尝试释放内存再重试，全部失败才抛异常；
- 若构造函数在 `new` 过程中抛出异常，编译器会自动调用对应的 `operator delete` 释放已分配的原始内存，不会泄漏；
- `new[]` 失败同样抛 `bad_alloc`（或返回 `nothrow` 版的空指针），必须用 `delete[]` 配对释放。

## 类对象的分配空间限制

### 只能建立在堆上

编译器在为对象分配栈空间前会检查构造函数与析构函数的可访问性。把析构函数设为 private，栈上就无法创建对象：

```cpp
class A {
public:
    A() {}
    void destroy() { delete this; }
private:
    ~A() {}
};

// A a;        // 编译错误：析构函数不可访问
A *p = new A;  // OK，构造函数是公有的
p->destroy();  // 必须通过成员函数释放
```

缺点：

- **继承问题**：作为基类时析构函数通常要设为 virtual 以便多态删除，而 private 的析构无法被派生类调用，因此应改为 protected（类外不可访问、子类可访问）；
- **用法别扭**：`new` 创建却要用 `destroy()` 释放，不能用 `delete`（`delete` 会调用不可访问的析构函数）。为了统一，常把构造函数也设为 protected，提供静态工厂：

```cpp
class A {
protected:
    A() {}
    ~A() {}
public:
    static A* create() { return new A(); }
    void destroy() { delete this; }
};
```

这里已经能看到单例模式的雏形：把构造/析构藏起来，只暴露受控的创建入口。

### 只能建立在栈上

只有 `new` 才会在堆上创建对象，而 `new` 表达式总是先调用 `operator new`。把 `operator new` 设为 private 即可禁止堆分配：

```cpp
class A {
private:
    void* operator new(size_t) { return nullptr; }   // 注意参数类型与返回值是固定的
    void operator delete(void*) {}                   // 重载了 new 就应重载 delete 配对
public:
    A() {}
    ~A() {}
};

// A *p = new A;    // 编译错误：operator new 不可访问
A a;                // OK
```

现代写法用 `= delete` 更清晰：

```cpp
void* operator new(size_t) = delete;
void operator delete(void*) = delete;
```

注意这只禁止了"类的 `operator new`"，用 `::new A`（全局 operator new + placement 构造）仍可绕过，属于刻意为之的边界情况。

## 单例模式（语言层实现）

单例要满足两点：构造函数私有（防止外部实例化），并提供唯一实例的访问点。难点全在**线程安全**与**析构时机**上。

### 版本 1：懒汉 + 裸指针（有问题）

```cpp
class Singleton {
private:
    static Singleton *local_instance;
    Singleton() {}
public:
    static Singleton *getInstance() {
        if (local_instance == nullptr) {
            local_instance = new Singleton();
        }
        return local_instance;
    }
};
Singleton *Singleton::local_instance = nullptr;
```

两个缺陷：多线程下可能 `new` 两次；程序结束时不会调用析构函数（内存泄漏，虽在进程退出时影响有限，但资源（文件、锁、日志缓冲）不会被正确释放。

### 版本 2：局部静态对象（C++11 起推荐）

```cpp
class Singleton {
private:
    Singleton() { std::cout << "构造" << std::endl; }
    ~Singleton() { std::cout << "析构" << std::endl; }
    Singleton(const Singleton&) = delete;
    Singleton& operator=(const Singleton&) = delete;
public:
    static Singleton& getInstance() {
        static Singleton local_s;
        return local_s;
    }
};
```

优点：C++11 起标准保证局部静态变量的初始化是线程安全的（编译器的"magic static"实现通常用一次性 guard 变量 + 原子操作，开销极小），无需加锁；对象在程序退出时按构造逆序自动析构；代码最短，也天然禁止外部直接实例化。

注意：私有构造/私有析构**并不会**删除隐式生成的拷贝构造与拷贝赋值，`new Singleton(Singleton::getInstance())` 仍能造出第二份实例；私有析构只挡住类外的 `delete` 与栈对象，对 `new` 不起作用。所以要靠显式 `= delete` 拷贝构造与赋值（如上），否则"唯一实例"并不成立。

另外：C++11 之前的标准不保证局部静态初始化的线程安全，多线程下可能重复构造，这是原文"该代码只能在较新编译器上使用"的含义。

### 版本 3：mutex + 静态成员辅助析构（C++11 之前可用）

```cpp
class Singleton {
private:
    static Singleton *local_instance;
    static pthread_mutex_t mutex;

    Singleton() { std::cout << "构造" << std::endl; }
    ~Singleton() { std::cout << "析构" << std::endl; }

    class rememberFree {                 // 利用静态成员的析构时机释放单例
    public:
        ~rememberFree() {
            if (Singleton::local_instance != nullptr) {
                delete Singleton::local_instance;
            }
        }
    };
    static rememberFree remember;

public:
    static Singleton *getInstance() {
        pthread_mutex_lock(&mutex);
        if (local_instance == nullptr) {
            local_instance = new Singleton();
        }
        pthread_mutex_unlock(&mutex);
        return local_instance;
    }
};

Singleton *Singleton::local_instance = nullptr;
pthread_mutex_t Singleton::mutex = PTHREAD_MUTEX_INITIALIZER;
Singleton::rememberFree Singleton::remember;
```

每次取实例都加锁，正确但慢。

### 版本 4：双检查锁（DCLP）为什么错

```cpp
static Singleton *getInstance() {
    if (local_instance == nullptr) {              // 第一次检查，无锁
        pthread_mutex_lock(&mutex);
        if (local_instance == nullptr) {          // 第二次检查，持锁
            local_instance = new Singleton();
        }
        pthread_mutex_unlock(&mutex);
    }
    return local_instance;
}
```

问题在于 `local_instance = new Singleton()` 不是原子操作，它包含"分配内存 → 构造对象 → 写指针"三步，编译器和 CPU 都可能重排，使指针先被写入。此时另一线程在第一次检查处看到非空指针，返回一个**尚未构造完成**的对象，造成未定义行为。Java 中的 DCLP 有同样问题（后来通过 `volatile` 语义修正），C++ 的结论也一样（参见 Scott Meyers / Alexandrescu 关于 DCLP 的分析）。

几种"修复"尝试及其问题：

1. **用临时变量强制顺序**——编译器会把临时变量优化掉，无效：

```cpp
auto tmp = new Singleton();
local_instance = tmp;      // 仍可能被重排
```

2. **给指针加 volatile**——`volatile` 只保证不把访问优化掉，不提供跨线程的内存序保证；而且 `volatile Singleton*` 的 `*ptr` 和成员都不是 volatile，仍可能被重排，最后只能把整条链都写成 volatile，代码极难维护且语义依然不完整；
3. **正确做法**：用原子变量 + 内存栅栏（acquire/release），或直接用 C++11 的 `std::call_once` / 局部静态。

### 版本 5：原子变量 + 内存栅栏

```cpp
class Singleton {
private:
    static std::atomic<Singleton*> instance;

    Singleton() { std::cout << "构造" << std::endl; }
    ~Singleton() { std::cout << "析构" << std::endl; }

    class rememberFree {
    public:
        ~rememberFree() {
            Singleton *p = instance.load(std::memory_order_relaxed);
            if (p != nullptr) delete p;
        }
    };
    static rememberFree remember;

public:
    static Singleton* getInstance() {
        Singleton *tmp = instance.load(std::memory_order_relaxed);
        std::atomic_thread_fence(std::memory_order_acquire);   // 保证读到指针时对象已构造完
        if (tmp == nullptr) {
            static std::mutex mtx;
            std::lock_guard<std::mutex> lock(mtx);
            tmp = instance.load(std::memory_order_relaxed);
            if (tmp == nullptr) {
                tmp = new Singleton();
                std::atomic_thread_fence(std::memory_order_release);
                instance.store(tmp, std::memory_order_relaxed);
            }
        }
        return tmp;
    }
};

std::atomic<Singleton*> Singleton::instance{nullptr};
Singleton::rememberFree Singleton::remember;
```

acquire 栅栏保证"看到指针"之后的读写不会被重排到读取之前；release 栅栏保证"对象构造完成"之前的写不会被重排到写指针之后。这是 muduo 书里称为"大杀器"的写法，逻辑正确但可读性差。

### 内存序的六个选项

`memory_order_relaxed`、`memory_order_consume`、`memory_order_acquire`、`memory_order_release`、`memory_order_acq_rel`、`memory_order_seq_cst`。它们归为三种模型：

- 顺序一致（sequentially consistent，`seq_cst`，也是所有原子操作的**默认值**）；
- 获取-释放（acquire/release/consume/acq_rel）；
- 自由序（relaxed）。

DCLP 这类场景用 acquire/release 足够，性能优于默认的 seq_cst。

### 其他方案

- `std::call_once` + `std::once_flag`：标准库封装的一次性初始化，异常安全（初始化抛异常会重置标志，允许重试）；
- `pthread_once`：POSIX 版本，语义类似；
- 局部静态（版本 2）本质上就是编译器生成的"一次性初始化"，在 C++11 之后应当作为首选，其余方案主要用于理解或兼容旧标准。

补充：若单例需要在多线程下安全销毁，且析构顺序敏感（例如析构时还要用日志系统），局部静态对象可能在日志系统销毁之后才析构，需要显式管理生命周期——这也是很多项目宁愿"故意泄漏"单例的原因。
