# 内存管理与智能指针

> 导读：C++ 的资源管理围绕一条主线展开——谁申请、谁释放、何时释放。`new` 把"分配内存"和"构造对象"绑在一起，手动配对 `delete` 极易出错；RAII 用栈对象的析构来托管堆资源，智能指针正是它的标准实现；右值引用与移动语义则让"转移资源所有权"变得廉价而明确。本篇最后合并了两篇性能优化笔记，去重后按主题重新组织。

## 一、`new` 的分配与构造行为

### 1.1 `new` 做了两件事

对一个 `new` 表达式，编译器会：

1. 调用 `operator new` 分配足够大的原始内存（可能失败并抛异常）；
2. 在这块内存上构造对象（对类类型调用构造函数）。

`delete` 的顺序相反：先调用析构函数，再调用 `operator delete` 释放内存。

### 1.2 内置类型与自定义类型的差异

这是一个高频考点：

```cpp
int* p1 = new int[10];     // 只分配，不初始化：元素值不确定
int* p2 = new int[10]();   // 分配 + 值初始化：全部为 0

int* p3 = new int;         // 值不确定
int* p4 = new int();       // 0
int* p5 = new int(42);     // 42
```

- 对**内置类型**，`new` 只负责分配内存，除非显式加上 `()`，否则不会初始化；加上 `()` 相当于做值初始化（内置类型置 0）。
- 对**自定义类型**，只要调用 `new`，编译器就会分配内存并调用默认构造函数，无论后面有没有写 `()`：

```cpp
struct Widget
{
    int a;
    Widget() : a(0) { std::cout << "ctor\n"; }
};

Widget* w1 = new Widget;     // 调用默认构造
Widget* w2 = new Widget();   // 同样调用默认构造（不是“多此一举”的语法差异）
```

注意：如果类**没有用户提供的构造函数**（是聚合/POD），则 `new T` 与 `new T()` 的差异会重新出现——后者会把成员零初始化。

### 1.3 数组与配对释放

```cpp
int* arr = new int[10];
delete[] arr;        // 必须用 delete[]，不能 delete
```

`new[]` 与 `delete[]` 必须配对；`new` 与 `delete` 必须配对。混用是未定义行为（对含析构函数的类类型尤其危险，可能只析构第一个元素）。

### 1.4 分配失败：异常与 `nothrow`

默认情况下，`new` 失败会抛出 `std::bad_alloc`：

```cpp
#include <iostream>
#include <new>

int main()
{
    try
    {
        char* p = new char[1048576];
        std::cout << "Succeeded!\n";
        delete[] p;
    }
    catch (const std::bad_alloc& e)
    {
        std::cout << "Failed: " << e.what() << "\n";
        return -1;
    }
    return 0;
}
```

> 原始笔记中的示例把 `p` 声明在 `try` 块内部，却在块外 `delete[] p`，无法通过编译；上面已修正作用域。

如果不想用异常，可以使用 `nothrow` 版本，失败时返回 `nullptr`：

```cpp
char* p = new (std::nothrow) char[1048576];
if (p == nullptr)
{
    std::cout << "Failed!\n";
}
else
{
    std::cout << "Succeeded!\n";
    delete[] p;
}
```

> 原笔记称"异常处理会额外多出 20~30 ms"，这个具体数值缺乏依据（异常在**不抛出**时几乎零成本，抛出时的开销取决于实现和栈展开深度），此处标记为**（待核实）**。选 `nothrow` 的理由应是"接口语义需要返回空指针"，而不是"异常一定慢"。

### 1.5 顺带：全局变量的零初始化

```cpp
enum string { x1, x2, x3 = 10, x4, x5 } x;
```

`x` 是全局变量，位于静态存储区，程序加载时被零初始化，因此 `x == 0`（即 `x1`）。若把它定义在函数内部作为局部变量，则不会被自动初始化，其值不确定。这也说明：**"未初始化"只发生在自动存储期和动态分配的对象上**，静态存储期对象总是先零初始化。

## 二、智能指针

### 2.1 核心思想：用栈对象管理堆对象

C++ 程序的内存大致分为：

| 区域 | 内容 | 生命周期 |
|:---|:---|:---|
| 静态存储区 | 全局变量、静态变量 | 程序运行期 |
| 栈 | 局部变量、函数参数 | 作用域结束自动回收 |
| 堆 | `new`/`malloc` 分配 | 需手动释放 |

智能指针的本质是：**在栈上放一个对象，让它持有堆对象的裸指针，并在析构函数中释放堆对象**。栈对象的析构由编译器保证，于是堆资源也随之确定性地释放——这就是 RAII。

### 2.2 `auto_ptr` → `unique_ptr`

`auto_ptr` 是 C++98 的方案，C++11 已废弃（C++17 移除）：

```cpp
std::auto_ptr<std::string> p1(new std::string("I reigned lonely as a cloud."));
std::auto_ptr<std::string> p2;
p2 = p1;      // 编译不报错，但 p1 的所有权被剥夺
// 此后 p1 为空：get() 等调用仍是良定义，对它解引用才是未定义行为
```

它的致命问题是**拷贝即转移所有权**，与普通拷贝语义冲突，容易在容器、函数传参时意外悬空。

`unique_ptr` 取而代之，语义是**独占所有权**：

```cpp
std::unique_ptr<std::string> p3(new std::string("auto"));
std::unique_ptr<std::string> p4;
// p4 = p3;                  // 编译错误：拷贝被删除
p4 = std::move(p3);          // 正确：显式转移，p3 变为空
```

特点：

- 同一时刻只有一个 `unique_ptr` 拥有对象；
- 不使用引用计数，析构时直接 `delete`，开销与裸指针几乎相同；
- 不可拷贝，只能移动；
- 支持数组：`std::unique_ptr<int[]> arr(new int[10]);`，会正确调用 `delete[]`；
- 优先用 `std::make_unique<T>(...)`（C++14）创建，避免 `new` 与构造之间的异常安全问题。

`unique_ptr` 如何实现"不可拷贝"？把拷贝构造和拷贝赋值声明为 `private` 或 `= delete`：

```cpp
template <class T>
class SmartPtr
{
public:
    explicit SmartPtr(T* ptr = nullptr) : _ptr(ptr) {}

    T& operator*()  const { return *_ptr; }
    T* operator->() const { return _ptr; }

    ~SmartPtr()
    {
        delete _ptr;
    }

    SmartPtr(const SmartPtr&)            = delete;
    SmartPtr& operator=(const SmartPtr&) = delete;

private:
    T* _ptr;
};
```

### 2.3 `shared_ptr`

`shared_ptr` 实现**共享所有权**：多个指针指向同一对象，通过引用计数决定何时释放。

每个 `shared_ptr` 内部持有两个指针：

1. 指向对象的裸指针；
2. 指向**控制块**的指针（控制块中含强引用计数、弱引用计数、删除器等）。

因此拷贝一个 `shared_ptr` 时，两个对象共享同一个控制块，计数原子地加 1；最后一个 `shared_ptr` 析构时计数归零，对象被销毁。

```cpp
auto sp1 = std::make_shared<std::string>("hello");
std::shared_ptr<std::string> sp2 = sp1;   // 强引用计数 = 2
std::cout << sp1.use_count() << std::endl; // 2
```

#### `get()` 的使用边界

`get()` 返回裸指针，但**不转移所有权、也不增加计数**：

- 只有在确定拿到指针的一方不会 `delete`、也不会用来初始化另一个智能指针时，才可以使用；
- 不要用 `get()` 的结果去构造另一个 `shared_ptr`，否则会出现两个独立的控制块，导致重复释放：

```cpp
std::shared_ptr<int> a(new int(1));
// std::shared_ptr<int> b(a.get());   // 错误：两个控制块，double free
std::shared_ptr<int> b = a;           // 正确
```

#### `shared_ptr` 与多态

```cpp
class A
{
public:
    ~A() { std::cout << "dealloc A" << std::endl; }
};

class B : public A
{
public:
    ~B() { std::cout << "dealloc B" << std::endl; }
};

int main()
{
    A* a = new B();
    delete a;                              // 只打印 dealloc A（A 的析构非虚）

    std::shared_ptr<A> spa = std::make_shared<B>();
    // 析构时先打印 dealloc B，再打印 dealloc A
    return 0;
}
```

原因：`make_shared<B>()` 在构造时记录了**真实类型 `B`** 的删除器，销毁时按 `B` 的完整类型析构，因此不依赖虚析构函数。

但这条结论有前提：**构造 `shared_ptr` 的那一刻，类型信息必须是完整的 `B`**。如果指针已经被转换成 `A*` 再交给 `shared_ptr`，例如：

```cpp
A* raw = new B();
std::shared_ptr<A> sp(raw);   // 删除器按 A* 生成
```

此时仍然需要 `A` 的析构函数是 `virtual`，否则行为未定义。稳妥做法是：基类一律写虚析构，或始终用 `make_shared<Derived>()` 直接构造。

### 2.4 `weak_ptr` 与循环引用

两个 `shared_ptr` 互相引用，或多个 `shared_ptr` 首尾相连，会形成环：环上每个对象的强引用计数都不为 0，程序结束时也无法释放，造成内存泄漏。

```cpp
class B;
class A { public: std::shared_ptr<B> b; };
class B { public: std::shared_ptr<A> a; };

int main()
{
    auto spa = std::make_shared<A>();
    auto spb = std::make_shared<B>();
    spa->b = spb;      // B 的强引用计数 = 2
    spb->a = spa;      // A 的强引用计数 = 2
    return 0;
}   // 两者计数都不为 0，A、B 均泄漏
```

把其中一条边改为 `weak_ptr` 即可破环：

```cpp
class B;
class A { public: std::shared_ptr<B> b; };
class B { public: std::weak_ptr<A> a; };

int main()
{
    auto spa = std::make_shared<A>();
    auto spb = std::make_shared<B>();
    spa->b = spb;      // B 的强引用计数 = 2
    spb->a = spa;      // 弱引用，不影响 A 的强引用计数
    return 0;
}   // spb、spa 依次析构：spa 释放 A，A 的成员 b 释放 B，环被解开
```

`weak_ptr` 的规则：

- 只能从 `shared_ptr` 或另一个 `weak_ptr` 构造，不能直接用裸指针构造；
- 不增加强引用计数，**不影响对象生命周期**；
- 不重载 `operator->` / `operator*`，不能直接访问对象；
- 提供 `expired()`（是否已销毁）与 `lock()`（提升为 `shared_ptr`，成功则计数 +1，失败返回空）；
- 使用前应先判断，典型的"权限提升"写法：

```cpp
std::shared_ptr<int> spa = std::make_shared<int>(1);
std::weak_ptr<int> wp = spa;

if (!wp.expired())          // 或用 auto sp = wp.lock(); if (sp)
{
    auto sp = wp.lock();
    *sp += 10;
}
```

`lock()` 的原子性很重要：`if (!expired()) { auto sp = lock(); ... }` 在多线程下仍可能出现"判断后、提升前被释放"的竞态，因此更推荐直接 `if (auto sp = wp.lock())`。

### 2.5 多线程安全

分两种情况：

1. **多个线程操作不同的 `shared_ptr` 对象，但共享同一个控制块**：引用计数的增减是原子的，因此是安全的；
2. **多个线程同时操作同一个 `shared_ptr` 对象**：不安全。例如一个线程 `reset()`，另一个线程同时读取裸指针，可能读到已释放的地址。对同一个 `shared_ptr` 实例的读写需要用锁或 `std::atomic<std::shared_ptr<T>>`（C++20）。

`shared_ptr` 保证的是**控制块的计数线程安全**，而不是**指针变量本身的线程安全**。

归纳成一句：并发**拷贝**或**只读**同一个 `shared_ptr`（即各线程持有各自的副本）是安全的；并发**修改或析构同一个实例**则不安全，必须改用 `std::atomic<std::shared_ptr<T>>`（C++20）或在外部加锁同步。

### 2.6 一个简化实现

下面这个版本保留了原始笔记的结构，但修掉了空指针解引用和计数非原子的问题：

```cpp
#include <atomic>

template <typename T>
class shared_ptr
{
public:
    shared_ptr() noexcept = default;

    explicit shared_ptr(T* obj)
        : _ptr(obj)
        , _count(obj ? new std::atomic<long>(1) : nullptr)
    {
    }

    shared_ptr(const shared_ptr& other)
        : _ptr(other._ptr)
        , _count(other._count)
    {
        if (_count)
            ++(*_count);
    }

    shared_ptr& operator=(const shared_ptr& other)
    {
        if (this == &other)
            return *this;

        release();

        _ptr   = other._ptr;
        _count = other._count;
        if (_count)
            ++(*_count);
        return *this;
    }

    ~shared_ptr() { release(); }

    T* get() const noexcept { return _ptr; }
    T& operator*()  const { return *_ptr; }
    T* operator->() const { return _ptr; }
    long use_count() const { return _count ? _count->load() : 0; }

private:
    void release()
    {
        if (_count && --(*_count) == 0)
        {
            delete _ptr;
            delete _count;
        }
        _ptr   = nullptr;
        _count = nullptr;
    }

    T* _ptr = nullptr;
    std::atomic<long>* _count = nullptr;
};
```

> 原始版本的三个问题：默认构造后 `_count == nullptr`，析构时执行 `--*_count` 是未定义行为；`operator=` 未做自赋值之外的异常/空指针保护；计数用 `int*`，多线程下不安全。上面的版本已修正。它仍然缺少自定义删除器、`weak_ptr`、`make_shared`、别名构造等能力，仅用于理解原理。

## 三、右值引用与移动语义

### 3.1 左值与右值

左值和右值都是针对**表达式**而言：

- **左值（lvalue）**：表达式结束后依然存在的持久对象；
- **右值（rvalue）**：表达式结束后就不再存在的临时对象。

最实用的判别方法：**能否对表达式取地址 `&`**。能取地址的是左值，否则是右值。

```cpp
int a = 10, b = 20;
int* pFlag = &a;
std::vector<int> vctTemp;
vctTemp.push_back(1);
std::string str1 = "hello ", str2 = "world";
const int& m = 1;
```

逐个判断：

| 表达式 | 类别 | 理由 |
|:---|:---|:---|
| `a`、`b` | 左值 | 持久对象，可取地址 |
| `a + b` | 右值 | 临时结果，不可取地址 |
| `a++` | 右值 | 返回的是自增前的**副本**（临时对象） |
| `++a` | 左值 | 返回 `a` 本身 |
| `pFlag`、`*pFlag` | 左值 | 持久对象 |
| `vctTemp[0]` | 左值 | `operator[]` 返回 `int&` |
| `100`、`std::string("hello")` | 右值 | 字面量/临时对象 |
| `str1` | 左值 | 具名对象 |
| `str1 + str2` | 右值 | `operator+` 返回临时 `string` |
| `m` | 左值 | `m` 是引用变量，本身是持久对象（尽管绑定到右值） |

`++i` 与 `i++` 的差异可以直接从实现看出来（下面是示意写法：内置类型不能自定义成员运算符，实际语义由编译器直接生成）：

```cpp
// 前置：返回引用，可作为左值
int& int::operator++()
{
    *this += 1;
    return *this;
}

// 后置：返回临时值，是右值
const int int::operator++(int)
{
    int oldValue = *this;
    ++(*this);
    return oldValue;
}
```

因此：

```cpp
int i = 0;
int* p1 = &(++i);   // 正确
int* p2 = &(i++);   // 错误：i++ 是右值
++i = 1;            // 正确
i++ = 5;            // 错误
```

### 3.2 右值引用

右值引用用 `T&&` 声明，可以绑定到临时对象，从而"延长"其生命并允许修改它：

```cpp
class A {};

A&  r1 = A();    // 错误：无名临时对象是右值，不能绑定到左值引用
A&& r2 = A();    // 正确：右值引用
const A& r3 = A(); // 也正确：const 左值引用可以绑定右值
```

右值引用的两大用途：**移动语义**与**完美转发**。这里只讨论移动语义。

### 3.3 移动构造与移动赋值

如果类持有堆资源，拷贝构造需要深拷贝。移动构造则直接"偷走"源对象的指针，把源对象置于可析构的空状态，成本从 O(N) 降到 O(1)。

```cpp
#include <cstring>
#include <iostream>
#include <utility>

class String
{
public:
    char* str;

    String() : str(new char[1]{0}) {}

    String(const char* s)
    {
        str = new char[std::strlen(s) + 1];
        std::strcpy(str, s);
    }

    // 拷贝构造：深拷贝
    String(const String& s)
    {
        std::cout << "copy constructor called\n";
        str = new char[std::strlen(s.str) + 1];
        std::strcpy(str, s.str);
    }

    // 拷贝赋值
    String& operator=(const String& s)
    {
        std::cout << "copy operator= called\n";
        if (this != &s)
        {
            char* tmp = new char[std::strlen(s.str) + 1];
            std::strcpy(tmp, s.str);
            delete[] str;
            str = tmp;
        }
        return *this;
    }

    // 移动构造：接管资源，并把源对象置为空串
    String(String&& s) noexcept : str(s.str)
    {
        std::cout << "move constructor called\n";
        s.str = new char[1]{0};
    }

    // 移动赋值：先释放自身资源，再接管
    String& operator=(String&& s) noexcept
    {
        std::cout << "move operator= called\n";
        if (this != &s)
        {
            delete[] str;          // 原笔记漏了这一步，会泄漏自身原有缓冲区
            str = s.str;
            s.str = new char[1]{0};
        }
        return *this;
    }

    ~String() { delete[] str; }
};
```

使用：

```cpp
template <class T>
void MoveSwap(T& a, T& b)
{
    T tmp(std::move(a));   // 移动构造
    a = std::move(b);      // 移动赋值
    b = std::move(tmp);    // 移动赋值
}

int main()
{
    String s;
    s = String("this");    // 临时对象 -> 移动赋值
    std::cout << s.str << std::endl;

    String s1 = "hello", s2 = "world";
    MoveSwap(s1, s2);
    std::cout << s2.str << std::endl;
}
```

要点：

- 移动构造/赋值应尽量标记 `noexcept`。否则 `std::vector` 在扩容时出于强异常安全保证，会退化为拷贝而不是移动；
- 但要注意上面把源对象重置为空串时又做了一次 `new char[1]`：这只是一次**常数级**的额外分配，不改变移动"接管而非拷贝"带来的 O(1) 复杂度；然而该函数已标记 `noexcept`，一旦这次分配抛出 `std::bad_alloc`，程序会直接 `std::terminate`。若在意这个风险，可把源对象的 `str` 置为 `nullptr`（并让析构函数容忍空指针），而不是重新分配；
- 被移动后的对象必须处于**有效但未指定**的状态，至少能安全析构、能重新赋值；
- 移动赋值必须先释放自身原有资源，否则泄漏（这是原始笔记中的实际 bug）；
- 若没有自定义拷贝/移动操作，编译器会按规则生成；一旦自定义了析构函数，隐式移动操作就不会自动生成，需要显式 `= default`。

### 3.4 `std::move` 的本质

`std::move` **不移动任何东西**，它只是一个类型转换：把表达式无条件转换为右值引用，告诉编译器"这个对象可以被移动"。

```cpp
struct X {};

int main()
{
    X a;
    X&& b = std::move(a);    // 输入左值
    X&& c = std::move(X());  // 输入右值
}
```

标准库中的大致实现：

```cpp
template <typename T>
typename std::remove_reference<T>::type&& move(T&& t)
{
    return static_cast<typename std::remove_reference<T>::type&&>(t);
}
```

原理拆解：

1. 参数 `T&&` 是**转发引用**，既能接左值也能接右值；
2. 通过**引用折叠**保持类型：`X& &&`、`X& &` 折叠为 `X&`；`X&& &&` 折叠为 `X&&`；
3. `remove_reference<T>::type` 去掉引用，得到裸类型；
4. `static_cast` 把它转为 `T&&`。

左值实参的推导：

```cpp
std::string s("hello");
std::move(s)
// T 被推导为 std::string&
// remove_reference<T>::type 为 std::string
// 实例化为：std::string&& move(std::string& t)
// 返回 static_cast<std::string&&>(t)
```

右值实参的推导：

```cpp
std::move(std::string("hello"))
// T 被推导为 std::string
// 实例化为：std::string&& move(std::string&& t)
```

`remove_reference` 通过类模板的**偏特化**实现：

```cpp
template <typename T>
struct remove_reference { typedef T type; };

template <class T>
struct remove_reference<T&> { typedef T type; };

template <class T>
struct remove_reference<T&&> { typedef T type; };
```

`static_cast` 的使用边界：任何具有明确定义的类型转换，只要不涉及底层 `const`，都可以用 `static_cast`；它不能去掉 `const`（那需要 `const_cast`）。

```cpp
double d = 1;
void* p = &d;
double* dp = static_cast<double*>(p);   // 正确

const char* cp = "hello";
// char* q = static_cast<char*>(cp);    // 错误：不能去掉 const
std::string s2 = static_cast<std::string>(cp);  // 正确
```

### 3.5 移动语义与智能指针

- `unique_ptr` 不可拷贝、只能移动，正是因为其拷贝构造被删除、移动构造被保留。`std::move(up)` 是转移独占所有权的标准方式；转移后源指针为空，解引用它是未定义行为。
- `shared_ptr` 的移动构造只是"偷走"控制块指针并把源置空，不改变引用计数；拷贝构造才会增加计数。
- 函数返回 `unique_ptr`、把 `unique_ptr` 放入容器，都依赖移动语义，因此不需要 `std::move`（返回值优化/隐式移动会自动处理）。

```cpp
std::unique_ptr<int> up(new int(5));
// auto up2 = up;            // 编译错误
auto up2 = std::move(up);    // 正确
// std::cout << *up;         // 危险：up 已为空
```

## 四、C++11 中与资源管理相关的新特性

### 4.1 统一初始化与 `initializer_list`

所有标准容器都支持列表初始化：

```cpp
std::vector<int> v = {1, 2, 3};
std::list<int>   l = {1, 2, 3};
std::set<int>    s = {1, 2, 3};
std::map<int, std::string> m = {{1, "a"}, {2, "b"}};
```

对资源管理而言，这意味着容器可以一次性构造完成，减少"先构造空容器再逐个插入"带来的多次扩容与异常风险。自定义类也可以提供 `initializer_list` 构造函数。

### 4.2 成员默认初始值（NSDMI）

```cpp
class A
{
public:
    int m = 1;      // 声明处给默认值
};
```

初始化动作发生在构造函数体之前，效果类似自动把这些初值放进初始化列表；如果构造函数的初始化列表也初始化了 `m`，则以初始化列表为准：

```cpp
class A
{
public:
    A() : m(2) {}
    int m = 1;      // 被忽略，最终 m == 2
};
```

这能有效避免"忘记初始化成员"导致的未定义值，对指针成员尤其有用（可默认置 `nullptr`）。

### 4.3 `nullptr`

`NULL` 通常是宏 `0`，在重载决议中会被当成 `int`，导致选错重载：

```cpp
void f(int);
void f(char*);

f(NULL);       // 可能调用 f(int)，与直觉不符
f(nullptr);    // 明确调用 f(char*)
```

`nullptr` 的类型是 `std::nullptr_t`，可隐式转换为任意指针类型，但不会转换为整数。资源管理代码中应统一使用 `nullptr` 表示空指针。

### 4.4 `auto` 与 range-for

```cpp
// 过去
std::map<int, std::string>::const_iterator itr = m.find(1);

// 现在
auto itr = m.find(1);
```

`auto` 的类型推导规则与模板一致，会**丢弃顶层 const 和引用**；需要保留时写 `const auto&` 或 `auto&&`。

range-for：

```cpp
for (const auto& kv : m)
    std::cout << kv.first << ": " << kv.second << std::endl;
```

遍历时用 `const auto&` 可避免容器元素（如 `std::string`、`std::pair`）的拷贝。

### 4.5 `= delete` / `= default`

这两个特性与所有权语义直接相关：

```cpp
class NonCopyable
{
public:
    NonCopyable() = default;
    NonCopyable(const NonCopyable&) = delete;
    NonCopyable& operator=(const NonCopyable&) = delete;
};
```

`= delete` 让"禁止拷贝"从运行期错误变成编译期错误；`= default` 则显式要求编译器生成默认实现（例如在自定义了析构函数后仍希望保留移动构造）。`unique_ptr` 的独占语义正是靠删除拷贝操作实现的。

### 4.6 其他同期特性（与资源管理关系较弱）

- **强类型枚举 `enum class`**：枚举值不再泄漏到外层作用域，且不同枚举类型之间不能比较，避免误用；
- **`final`**：禁止虚函数被进一步重写，或禁止类被继承；
- **`override`**：显式声明重写，签名不匹配时编译报错（例如漏写 `const`），避免"以为重写了，其实定义了一个新函数"。

```cpp
class A
{
public:
    virtual void f1() const {}
};

class B : public A
{
    // virtual void f1() {}          // 不会报错，但是新函数，不是重写
    virtual void f1() override {}    // 报错：找不到可重写的函数
};
```

## 五、内存泄露检查工具

### 5.1 Visual Leak Detector（VLD，Windows）

使用方式：在包含 `main` 的 `.cpp` 中 `#include <vld.h>`，以 Debug 方式编译运行，程序退出后会输出泄漏报告。

注意事项：

1. 若存在 `#include "stdafx.h"`（预编译头），`<vld.h>` 要放在它**之后**；否则放在所有 include 的最前面；
2. VLD 只在 Debug 版本生效；
3. 若要把日志写入文件，把安装目录下的 `vld.ini` 复制到可执行文件目录，并修改：

   ```ini
   ReportFile = .\memory_leak_report.txt
   ReportTo   = both
   ```

4. 直接双击运行生成的 exe，而不是在 VS 调试器里运行，报告更完整。

📎 [vld-2.5.1-setup.exe](../../技术笔记/assets/vld-2.5.1-setup.exe)

### 5.2 CRT 内存诊断（Windows / MSVC）

MSVC 的 CRT 在 Debug 下支持内存诊断。进程退出时若看到：

```
Detected memory leaks!
Dumping objects ->
```

说明有内存未正确释放。默认报告只有块号，看不到代码行号；定义 `_CRTDBG_MAP_ALLOC` 后可以打印分配处的文件名和行号。

```cpp
#define _CRTDBG_MAP_ALLOC
#include <cstdlib>
#include <crtdbg.h>

int main()
{
    int* p = new int[10];
    // ...

    _CrtDumpMemoryLeaks();   // 在程序退出前调用
    return 0;
}
```

要点：

- 宏名是 `_CRTDBG_MAP_ALLOC`（**带前导下划线**）。原始笔记的代码写成了 `CRTDBG_MAP_ALLOC`，少了下划线，不会生效；
- 该宏必须在包含 `<crtdbg.h>` 之前定义，且建议放在文件最顶部；
- `_CrtDumpMemoryLeaks()` 打印的是"执行到当前位置时仍未释放的所有块"，不一定都是泄漏（可能是稍后才释放的对象），因此应放在程序退出前；
- 只对 Debug CRT 有效。

### 5.3 其他平台

Linux/macOS 下常用 Valgrind（`valgrind --leak-check=full ./app`）或编译器的 AddressSanitizer（`-fsanitize=address`）。ASan 开销较小，适合日常测试；Valgrind 不需要重新编译，但运行较慢。

## 六、性能优化（两篇笔记合并）

### 6.1 总原则

1. **先测量，再优化**。用 profiler 找出真正被频繁调用的热点函数，关注其耗时、调用次数与调用关系；对占据大量 CPU 时间的函数调优，而不是凭直觉。
2. **算法与数据结构的选择决定性能上限**，微观优化只能锦上添花。避免不必要的计算、避免在循环里反复全表查找。
3. **不要过早优化**。把函数压到极紧凑后再想改动或复用会非常困难。
4. **优化往往损害可读性与可维护性**，要权衡并写注释。效率要求直接、强耦合；可读性要求模块化、解耦合。
5. **宏观优化（算法、架构、数据结构）由人负责，微观优化（寄存器分配、指令选择）交给编译器**。

### 6.2 尽量用引用/指针传参，少用值传递

值传递会构造副本：调用拷贝构造 → 复制内容 → 函数结束时析构。若对象内部还持有其他对象，开销会层层放大。

```cpp
void byValue(BigObject o);              // 差
void byConstRef(const BigObject& o);    // 好：只读
void byRef(BigObject& o);               // 好：需要修改
```

对内置类型（`int`、`float`、指针）而言，传值往往比引用传递更快或相当，不必教条。

### 6.3 前置 `++` 优于后置 `++`

对自定义类型（尤其是迭代器），后置 `++` 需要先拷贝一份当前状态，再自增，最后返回副本：

```cpp
// 前置：直接改自身，返回引用
Iterator& Iterator::operator++()
{
    pNote = pNote->pNext;
    return *this;
}

// 后置：构造临时对象，返回副本
Iterator Iterator::operator++(int)
{
    Iterator tmp(*this);
    pNote = pNote->pNext;
    return tmp;
}
```

后置版本会多一次拷贝构造 + 一次析构。遍历 100 个元素时，`it++` 比 `++it` 多 200 次函数调用：

```cpp
for (Iterator it = list.begin(); it != list.end(); ++it) { }  // 推荐
for (Iterator it = list.begin(); it != list.end(); it++) { }  // 多一次拷贝
```

对 `int` 这类内置类型，编译器通常会把差异优化掉；但泛型代码中应统一写 `++it`。

### 6.4 循环内定义还是循环外定义对象

```cpp
// A：循环外构造
ClassTest ct;
for (int i = 0; i < 100; ++i)
{
    ct = a;
    // do something
}

// B：循环内构造
for (int i = 0; i < 100; ++i)
{
    ClassTest ct = a;
    // do something
}
```

- A：1 次构造 + 100 次赋值；
- B：100 次拷贝构造 + 100 次析构。

若 `operator=` 的开销小于"构造 + 析构"，A 更快；反之 B 更快。没有普适答案，取决于类。现代实践倾向于 B（作用域最小化），确有必要时再改为 A。

### 6.5 避免过大的循环体

```cpp
// A：合并循环
for (int i = 0; i < n; ++i) { fun1(); fun2(); }

// B：拆分为两个循环（fun1、fun2 无依赖）
for (int i = 0; i < n; ++i) fun1();
for (int i = 0; i < n; ++i) fun2();
```

直觉上 A 少做 n 次自增与判断，应该更快。但当 `fun1`、`fun2` 的代码量都很大、超过指令 cache 容量时，A 每次循环都要把另一段代码挤出 cache，反复从内存加载；B 则让每个循环的指令与数据保持局部性，理论上只需在切换时清空一次。**结论取决于函数规模与硬件 cache，必须实测**。

这也是 cache 的时间局部性/空间局部性原理的直接体现。

### 6.6 局部变量与静态变量

常见误区：认为静态变量在程序启动时就分配好，所以访问更快。

实际上，局部变量在栈上，分配只是调整一次栈指针（即使一组局部变量也通常只调整一次）；函数返回后栈空间被回收，下一次调用可复用同一批地址，数据容易留在 L1 cache 中。

静态变量位于静态存储区，不在栈上，且具有全局生命周期；它的初始化（C++11 起局部静态变量的初始化是线程安全的）还可能引入守卫变量检查。因此**不要为了"性能"把局部变量改成静态变量**，静态变量还会带来可重入性和线程安全问题。

> "静态变量是低效的"这一说法过于绝对，应理解为：在需要频繁访问的短生命周期数据上，栈变量通常具有更好的局部性。**（经验性结论，具体以测量为准）**

### 6.7 多重继承

多重继承会让对象布局复杂化：成员访问需要通过 `this` 加偏移计算，涉及多个基类时还要做指针调整；虚基类（解决菱形二义性）的偏移计算更复杂。

不过，对现代编译器而言，这些偏移大多是编译期常量，**运行时开销通常很小**。避免多重继承的主要理由仍是设计与可维护性（二义性、耦合），而不是性能。**（性能影响的具体量级待核实）**

### 6.8 少用 `dynamic_cast`

`dynamic_cast` 需要在运行时沿继承层次查询类型信息（通常借助 RTTI），继承层次越深、关系越复杂，开销越大。它不应出现在热路径中。

替代方案：用虚函数实现多态分派；用 `static_cast`（确定类型时）；或在设计上用标签/`std::variant`（C++17）替代运行时类型判断。

### 6.9 减少除法

无论整数还是浮点，除法都是较慢的指令。可做的优化：

1. 用数学等价变换把除法变乘法（注意前提）：

   ```cpp
   // a、b、c 均为正数时等价
   if (a > b / c)  ->  if (a * c > b)
   ```

2. 除数为编译期常量时，编译器可把除法 strength-reduce 为移位/乘法。写成 `n / 8` 且 `n` 为无符号时，编译器可直接用右移：

   ```cpp
   unsigned q = n / 8;   // 可优化为 n >> 3
   ```

   注意：对有符号负数，右移与除法的舍入方向不同，因此不要为了"优化"把可能为负的 `int` 强转 `unsigned`，那会改变语义。

3. 循环中可以把除法提到循环外，或改用乘以倒数（浮点时注意精度）。

### 6.10 内联（`inline`）

函数调用有现场保护、参数压栈、返回地址等开销。内联把函数体直接展开到调用处，消除这些开销，但会增加代码体积。

适用于**短小且被频繁调用**的函数，例如：

```cpp
inline int Max(int a, int b) { return a > b ? a : b; }
```

注意：

- `inline` 只是建议，编译器可以拒绝（函数太复杂、含循环/递归/`switch` 等）；
- 类定义内部直接实现的成员函数**隐式内联**；
- 由于 ODR 规则，`inline` 函数的定义必须在**每个使用它的翻译单元**中可见，因此通常放在头文件；若函数只在单个 `.cpp` 内使用，定义在该 `.cpp` 中也可以，此时加不加 `inline` 都不影响链接。

> 原始笔记"内联函数只能出现在 .h 文件中"的说法不准确，准确表述是"定义必须对使用它的每个 TU 可见"。

### 6.11 虚函数的开销

虚函数调用需要：取对象的 vptr → 查虚表 → 间接跳转，且通常会阻止内联。在极热的循环中，这可能成为瓶颈。

优化手段：

- 确定不会变化的类型，改用非虚函数/模板静态分派（CRTP）；
- 用 `final` 帮助编译器去虚化（devirtualization）；
- 把多态调用提到循环外，循环内只做数据操作。

但不要为了性能盲目去掉虚函数——运行时多态的价值远大于这点开销。

### 6.12 拷贝构造 vs 赋值：减少临时对象

```cpp
Complex c2(c1);   // 拷贝构造（直接初始化）
Complex c2 = c1;  // 仍然是拷贝构造（拷贝初始化），不是赋值
c1 = c2;          // 赋值运算符（c1 已存在）
```

区分规则：**创建新对象 → 拷贝构造；对已存在对象赋值 → `operator=`**。

减少临时对象的常见做法：

- 用 `const T&` 接收只读参数；
- 返回大对象时依赖 RVO/NRVO 或移动语义；
- 用 `emplace_back` 直接在容器内构造，避免"先构造临时对象再拷贝"；
- 在 `operator=` 中做好自赋值检查与异常安全。

### 6.13 优化清单

| 层次 | 做法 |
|:---|:---|
| 算法/数据结构 | 选对容器与算法；避免 O(N²)；避免循环内重复查找 |
| 接口设计 | 引用/指针传参；`const&` 只读；避免返回大对象副本 |
| 循环 | `++it`；循环不变量外提；控制循环体规模；注意 cache 局部性 |
| 函数 | 短小热函数内联；减少虚调用；少用 `dynamic_cast` |
| 运算 | 减少除法；用常量除数；避免不必要的类型转换 |
| 内存 | 减少分配次数；用对象池/`reserve`；移动而非拷贝 |
| 工程 | 先 profile；改动写注释；用基准测试验证收益 |
