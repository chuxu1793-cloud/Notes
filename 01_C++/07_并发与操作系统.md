# 并发与操作系统

本篇从操作系统的基本抽象讲起：内核态/用户态、进程与线程，然后是 POSIX 线程的实践、锁的选择与定时器设计；后半部分转入支撑这些概念的硬件基础——CPU/GPU/FPGA 的体系结构差异、存储带宽、指令流水线，以及定点数、浮点数与堆栈的内存模型。并发问题的根源往往不在 API，而在这些底层事实上。

## 一、内核、进程与线程

### 1.1 内核的职责

内核管理硬件资源并向应用提供稳定的运行环境：

- **CPU 调度**：决定哪个执行流在哪个核上运行多久；
- **内存管理**：虚拟地址空间、页表、缺页处理；
- **设备与文件**：驱动、文件系统、I/O 调度；
- **进程间通信与同步**：管道、共享内存、信号、futex 等。

应用通过**系统调用**进入内核，这是唯一合法的入口。

### 1.2 用户态与内核态

CPU 提供不同的特权级（x86 的 ring 0–3，ARM 的 EL0–EL3）。用户态代码不能直接访问页表、不能关中断、不能操作设备寄存器；需要这些能力时必须陷入内核。

一次系统调用的成本不只是"跳转"：

- 保存/恢复寄存器上下文；
- 切换内核栈；
- 可能触发 TLB / cache 行为变化；
- 安全缓解措施（KPTI 等）会进一步放大开销。

这就是为什么"尽量减少系统调用"是高性能 I/O 的基本功，也是 `futex` 这类用户态优先的同步机制存在的理由。

> **过时表述提醒**：原笔记写"每个进程都有 4GB 虚拟地址空间，1GB 内核空间，3GB 用户空间"。这是 **32 位 Linux 的经典 3G/1G 划分**。64 位系统下用户空间与内核空间各有数十 TB 的虚拟地址范围（Linux x86-64 典型为用户态低半区、内核态高半区），该说法已不适用。

### 1.3 进程与线程

| 维度 | 进程 | 线程 |
|---|---|---|
| 定位 | 资源分配的基本单位 | CPU 调度的基本单位 |
| 地址空间 | 独立 | 同进程内共享 |
| 拥有 | 页表、文件描述符表、信号处理、环境变量 | 栈、寄存器上下文、调度属性、线程私有数据（TSD）、待决/阻塞信号集 |
| 创建开销 | 大（复制/建立大量内核结构） | 小（共享大部分资源） |
| 切换开销 | 需换页表，TLB 可能失效 | 同一地址空间，主要是寄存器与栈切换 |
| 通信 | 管道、消息队列、共享内存、socket、信号 | 全局变量、静态变量（需自行同步） |
| 隔离性 | 一个进程崩溃通常不影响其它进程 | 一个线程崩溃会带走整个进程 |

线程共享进程资源带来两个直接后果：

1. 一个线程关闭文件、修改堆内存，对同进程所有线程立即可见；
2. 两个指针可以指向同一块数据，**读写共享内存必须显式同步**。

### 1.4 Linux 的线程实现

> **修正**：原笔记"Linux 下没有真正意义的线程，线程是用进程模拟的"是早期 LinuxThreads 时代的说法，容易误导。
>
> 现代 Linux 的内核调度实体统一是 `task_struct`，线程通过 `clone()` 带上 `CLONE_VM | CLONE_FS | CLONE_FILES | CLONE_SIGHAND | CLONE_THREAD` 等标志创建，从而共享地址空间与文件表。也就是说，Linux 内核**不区分进程和线程的结构体**，但线程是一等公民：有独立的 `tid`、独立的栈、可被独立调度。用户态由 NPTL（glibc）实现 1:1 模型，每个 `pthread_t` 对应一个内核调度实体。`getpid()` 返回线程组 ID，`gettid()` 返回线程 ID。

"轻量级进程（LWP）"这个说法仍然成立，但它的含义是"共享资源的调度实体"，而不是"用进程假装线程"。

### 1.5 进程 vs 线程的选型

- 需要**强隔离**、崩溃不扩散、可独立重启 → 多进程；
- 需要**大量共享状态**、低切换开销、高并发连接 → 多线程（配合锁或无共享设计）；
- 需要**海量并发且 I/O 密集** → 事件循环 / 协程往往比"一线程一连接"更合适。

## 二、线程模型与并行程序设计

### 2.1 什么是线程

从开发者视角，线程就是"一个可以被操作系统独立调度的函数执行流"。多线程程序 = 多个这样的流同时或交替推进。

在 SMP（对称多处理）架构上，线程是获得**真正并行**的手段；在单核上，线程提供的是**并发**（交错执行）与阻塞隔离，不会提升 CPU 密集型任务的吞吐。

### 2.2 常见线程模型

- **Manager/Worker**：一个管理线程负责接收任务并分发，工作线程只处理。又分静态工作池（线程数固定）与动态工作池（按负载增减）。
- **Pipeline（流水线）**：任务拆成若干阶段，每个阶段由独立线程处理，阶段间用队列连接。适合阶段耗时差异大、可流式处理的场景。
- **Peer（对等）**：主线程创建完其它线程后自己也参与工作，没有专门的管理者。

### 2.3 共享内存模型与线程安全

共享内存模型的三条约定：

1. 所有线程可访问全局/堆内存；
2. 每个线程另有私有栈与 TSD；
3. **程序员负责保护共享数据的访问**。

**线程安全**指：多个线程同时调用同一段代码，不会破坏共享数据、不会产生竞争条件。判断一个函数是否线程安全，要看它是否访问了可变的全局状态（全局变量、静态变量、共享堆对象、`errno` 之类的线程局部量除外）。

实践建议：

- 不确定第三方库是否线程安全时，**默认它不安全**，直到被证实；
- 优先设计**无共享**（消息传递、线程私有数据、不可变数据），其次才是加锁；
- 加锁要覆盖**所有**访问路径——四个线程改同一变量、只有一个加锁，等于没加。

### 2.4 线程的收益与代价

收益：

- **I/O 与计算重叠**：一个线程阻塞在 I/O 上时，CPU 可以跑其它线程；
- **优先级/实时调度**：重要任务可以抢占次要任务；
- **异步事件处理**：web 服务器可以同时处理多个请求。

代价：

- 同步复杂度、死锁、竞态；
- 上下文切换与缓存局部性下降；
- 调试与复现难度陡增（Heisenbug）。

历史上（2000 年代中期的 SMP 集群）有过一组 `fork()` 与 `pthread_create()` 的创建开销对比：`fork()` 的 real 时间在几十毫秒量级，`pthread_create()` 在 1–2 毫秒量级；线程间通信因为是同一地址空间、无中间拷贝，带宽接近 memory-to-CPU 带宽，明显高于 MPI 共享内存通信。**这些绝对数值已严重过时，仅保留其相对结论：线程创建远快于进程创建，共享内存通信远快于跨进程拷贝。**

## 三、POSIX Threads 实践

### 3.1 API 分类与命名

Pthreads 由 IEEE POSIX 1003.1c 定义，头文件 `<pthread.h>`，标识符统一以 `pthread` 开头。

| 前缀 | 作用域 |
|---|---|
| `pthread_` | 线程本身及通用函数 |
| `pthread_attr_` | 线程属性对象 |
| `pthread_mutex_` | 互斥量 |
| `pthread_mutexattr_` | 互斥量属性 |
| `pthread_cond_` | 条件变量 |
| `pthread_condattr_` | 条件变量属性 |
| `pthread_key_` | 线程私有数据键（TSD） |

三大类功能：**线程管理**（创建、分离、连接、属性）、**互斥量**（互斥与保护共享数据）、**条件变量**（基于数据值做同步）。

编译时链接线程库：

```bash
gcc -pthread main.c -o main      # 推荐，-pthread 同时设置宏和链接
g++ -pthread main.cpp -o main
```

### 3.2 创建与终止

```c
#include <pthread.h>
#include <stdio.h>
#include <stdlib.h>

#define NUM_THREADS 5

void* PrintHello(void* arg) {
    int tid = (int)(intptr_t)arg;
    printf("Hello World! It's me, thread #%d!\n", tid);
    pthread_exit(NULL);
}

int main(void) {
    pthread_t threads[NUM_THREADS];
    for (int t = 0; t < NUM_THREADS; ++t) {
        int rc = pthread_create(&threads[t], NULL, PrintHello, (void*)(intptr_t)t);
        if (rc) {
            printf("ERROR: pthread_create() returned %d\n", rc);
            exit(-1);
        }
    }
    pthread_exit(NULL);
}
```

`pthread_create` 的四个参数：线程句柄、属性对象（`NULL` 为默认）、入口函数（`void* (*)(void*)`）、单个 `void*` 参数。

终止线程的方式：

1. 从入口函数 `return`；
2. 调用 `pthread_exit()`；
3. 被其它线程 `pthread_cancel()`；
4. 进程整体结束（`exit()` / `exec()` / main 返回）。

`pthread_exit()` **不会**关闭线程中打开的文件，也不会执行 C++ 栈对象的析构（除非用异常展开），资源需要自己清理。

`main()` 若在其它线程结束前 `return`，整个进程会退出；在 `main` 末尾调用 `pthread_exit(NULL)` 可以让已创建的线程继续运行——但这是"能跑"而不是"好设计"，正常做法是显式 join。

### 3.3 参数传递：三个必须记住的例子

**正确：每个线程一份独立数据**

```c
int* taskids[NUM_THREADS];
for (int t = 0; t < NUM_THREADS; ++t) {
    taskids[t] = (int*)malloc(sizeof(int));
    *taskids[t] = t;
    pthread_create(&threads[t], NULL, PrintHello, taskids[t]);
}
```

**正确：结构体打包多个参数**

```c
struct thread_data {
    int   thread_id;
    int   sum;
    char* message;
};

struct thread_data thread_data_array[NUM_THREADS];

void* PrintHello(void* arg) {
    struct thread_data* my = (struct thread_data*)arg;
    printf("thread %d, sum %d, msg %s\n", my->thread_id, my->sum, my->message);
    pthread_exit(NULL);
}

/* 创建时传入 &thread_data_array[t] */
```

**错误：传局部变量地址**

```c
for (int t = 0; t < NUM_THREADS; ++t) {
    pthread_create(&threads[t], NULL, PrintHello, (void*)&t);
}
```

循环变量在所有线程真正运行前就变了（甚至已销毁），线程读到的是同一个地址的最终值或悬空值。这是最经典的线程参数 bug。

### 3.4 Join 与 Detach

- **joinable**：线程结束后保留退出状态，必须由其它线程 `pthread_join()` 回收，否则资源（栈等）泄漏；
- **detached**：线程结束后自动回收，不能被 join。

```c
pthread_attr_t attr;
pthread_attr_init(&attr);
pthread_attr_setdetachstate(&attr, PTHREAD_CREATE_JOINABLE);
pthread_create(&thread, &attr, worker, NULL);
pthread_attr_destroy(&attr);

void* status;
pthread_join(thread, &status);   // 阻塞直到 thread 结束
```

`pthread_join()` 只能调用一次，第二次是逻辑错误。`pthread_detach()` 可把已创建的 joinable 线程转为 detached，没有反向操作。

建议：**需要拿返回值或确认结束就用 joinable + join；否则创建时直接设 detached**，避免资源泄漏。

### 3.5 栈大小

POSIX 不规定默认栈大小，各平台差异极大（历史上从 96 KB 到 32 MB 都有）。线程里放大数组、深递归很容易超限，表现为崩溃或静默数据损坏。

```c
size_t stacksize;
pthread_attr_getstacksize(&attr, &stacksize);
stacksize = sizeof(double) * N * N + 1000000;   // 预留足够空间
pthread_attr_setstacksize(&attr, stacksize);
```

原则：**不依赖默认值**，按最坏情况估算并显式设置。另外可用 `pthread_attr_setstackaddr` 指定栈所在内存区域（非可移植，慎用）。

### 3.6 其它常用函数

```c
pthread_t pthread_self(void);
int pthread_equal(pthread_t t1, pthread_t t2);   // 相等返回非 0
int pthread_once(pthread_once_t* once_ctl, void (*init)(void));
```

`pthread_t` 是不透明类型，**不能用 `==` 比较**，必须用 `pthread_equal`。

`pthread_once` 保证初始化函数**对同一个 `once_control` 只执行一次**；也就是说，"进程内只执行一次"并不是它自带的性质，而是靠所有调用方共享同一个控制变量实现的。用静态全局（或函数内静态）的控制变量时，效果才等于进程内一次；若每个对象各自持有一个 `once_control`，初始化函数就会按控制变量的个数各执行一次。它是实现线程安全懒初始化（包括单例）的最简工具：

```c
pthread_once_t once_control = PTHREAD_ONCE_INIT;
pthread_once(&once_control, init_routine);
```

### 3.7 互斥量

互斥量保护**临界区**，保证同一时刻只有一个线程进入。

初始化两种方式：

```c
pthread_mutex_t m = PTHREAD_MUTEX_INITIALIZER;      // 静态
pthread_mutex_init(&m, NULL);                       // 动态，可设属性
```

属性对象 `pthread_mutexattr_t` 支持协议（priority inheritance / protection）、优先级上限、进程间共享等，但并非所有实现都完整支持。

```c
pthread_mutex_lock(&m);      // 已被占用则阻塞
/* critical section */
pthread_mutex_unlock(&m);

if (pthread_mutex_trylock(&m) == 0) {   // 不阻塞，占用时立即返回 EBUSY
    /* ... */
    pthread_mutex_unlock(&m);
}
```

典型竞争示例（银行转账）：

| Thread 1 | Thread 2 | Balance |
|---|---|---|
| 读余额 1000 | | 1000 |
| | 读余额 1000 | 1000 |
| | 存入 200 | 1000 |
| 存入 200 | | 1000 |
| 写回 1200 | | 1200 |
| | 写回 1200 | 1200 |

两次存款丢了一次。正确做法是把"读—改—写"整体放进同一把锁。

注意：互斥量不是魔法，它只是线程之间的"君子协定"。忘记解锁、锁错对象、只在部分路径加锁，都会破坏它。谁先拿到刚释放的锁也是不确定的（除非使用优先级调度），不能依赖顺序。

**dot-product 示例（多线程分段计算 + 加锁汇总）**

```c
typedef struct {
    double* a;
    double* b;
    double  sum;
    int     veclen;
} DOTDATA;

#define NUMTHRDS 4
#define VECLEN   100

DOTDATA dotstr;
pthread_t callThd[NUMTHRDS];
pthread_mutex_t mutexsum;

void* dotprod(void* arg) {
    long offset = (long)arg;
    int start = offset * dotstr.veclen;
    int end   = start + dotstr.veclen;
    double mysum = 0.0;

    for (int i = start; i < end; ++i)
        mysum += dotstr.a[i] * dotstr.b[i];

    pthread_mutex_lock(&mutexsum);
    dotstr.sum += mysum;
    pthread_mutex_unlock(&mutexsum);

    pthread_exit((void*)0);
}
```

这里每个线程只写自己的局部 `mysum`，共享的 `dotstr.sum` 用锁保护——**缩小临界区**是并发性能的关键。

### 3.8 条件变量

互斥量解决"谁能访问"，条件变量解决"什么时候可以访问"。没有条件变量，等待方只能轮询，白白消耗 CPU。

典型协作流程：

- 等待方：加锁 → `while (!condition) pthread_cond_wait(&cv, &m);` → 处理 → 解锁；
- 通知方：加锁 → 修改共享状态 → `pthread_cond_signal(&cv);` → 解锁。

`pthread_cond_wait()` 的三个关键行为：

1. **必须在持有 mutex 时调用**；
2. 调用时**原子地**释放 mutex 并进入等待；
3. 被唤醒后**自动重新获取 mutex** 再返回。

```c
pthread_mutex_lock(&count_mutex);
while (count < COUNT_LIMIT) {                 // 必须用 while，不能 if
    pthread_cond_wait(&count_threshold_cv, &count_mutex);
}
pthread_mutex_unlock(&count_mutex);
```

> **修正**：原笔记的示例用的是 `if (count < COUNT_LIMIT)`。条件变量存在**虚假唤醒（spurious wakeup）**，也可能被 `broadcast` 唤醒后条件又被别的线程改掉，因此**必须用 `while` 重新检查条件**。这是条件变量最容易写错的地方。

```c
pthread_mutex_lock(&count_mutex);
count++;
if (count == COUNT_LIMIT)
    pthread_cond_signal(&count_threshold_cv);   // 唤醒一个等待者
pthread_mutex_unlock(&count_mutex);
```

- `pthread_cond_signal` 至少唤醒一个等待线程（不保证是哪个）；
- `pthread_cond_broadcast` 唤醒全部；
- 在 `wait` 之前 `signal` 会丢失（逻辑错误），所以共享状态的修改与判断都必须在锁内完成；
- `signal` 之后忘记解锁，等待方永远无法真正返回。

条件变量常与互斥量配合实现**生产者—消费者队列**、线程池的任务分发、事件等待等。

### 3.9 未覆盖但重要的主题

线程调度策略与优先级、线程私有数据（TSD / `pthread_key_*`）、跨进程条件变量、线程取消（`pthread_cancel` 与 cancellation point）、多线程与信号（信号处理函数应尽量只做 `write` 之类的异步信号安全操作）。这些在真实工程里都会遇到，需要单独查手册。

## 四、互斥锁与自旋锁

### 4.1 行为差异

| | 互斥锁（mutex） | 自旋锁（spinlock） |
|---|---|---|
| 拿不到锁时 | 阻塞，让出 CPU，进入睡眠 | 忙等，循环检查 |
| 上下文切换 | 有 | 无 |
| 适用持锁时间 | 长 | 极短 |
| CPU 浪费 | 无（睡眠不占 CPU） | 有（等待期间持续占核） |
| 典型场景 | 含 I/O、复杂逻辑、单核 | 内核临界区、极短保护、多核 |

> **修正**：原笔记说互斥锁"工作在内核模式"，自旋锁"始终工作在用户模式"。这不准确。
>
> - 现代互斥锁基于 **futex**：无竞争时完全是用户态的一条原子指令（CAS），只有发生竞争才通过系统调用进入内核睡眠。所以"加锁一定进内核"是错的。
> - "自旋锁工作在用户模式"也不是普遍事实。用户态自旋锁只是一个 `atomic_flag` 忙等；**内核自旋锁**在持锁期间通常还要关闭抢占（`preempt_disable`）甚至关中断，运行在内核态。

### 4.2 futex：用户态优先的同步原语

futex（fast userspace mutex）是 Linux 构建锁、信号量、条件变量的基础组件，应用一般不直接使用。

设计动机：绝大多数加锁操作**没有竞争**，为此进一次内核完全不划算。系统调用的开销包括保存寄存器、切换栈、上下文切换，代价是几十到几百条指令。

futex 的做法：

- 在用户态维护一个共享整型变量；
- 无竞争时，`lock` 只是一次原子 CAS，成功即返回，**不进内核**；
- 竞争时，通过 `futex(FUTEX_WAIT)` 让当前线程睡眠；
- 解锁时，若检测到有等待者，用 `futex(FUTEX_WAKE)` 唤醒。

"用户态快路径 + 内核慢路径"这个模式，是理解现代同步性能的关键。

### 4.3 选择建议

- 临界区里有 I/O、系统调用、复杂计算、可能缺页 → **mutex**；
- 临界区只有几条指令、且确定运行在多核 → **spinlock**，但要评估持锁时间上限；
- 单核上自旋毫无意义（等待者占着唯一的核，持锁者无法运行）；
- 内核里禁用睡眠的场景（中断上下文）只能用自旋锁；
- 高竞争场景下，自旋 + 退避（backoff）或分级锁往往比纯自旋更好。

## 五、跨平台定时器设计

### 5.1 接口抽象

一个最小可用的定时器系统需要三个行为：

```cpp
TimerId StartTimer(Interval interval, ExpiryAction action);
void    StopTimer(TimerId id);
void    PerTickBookkeeping();   // 每个 tick 检查是否有到期定时器
```

### 5.2 核心数据结构

`StartTimer` 时把 `now + interval` 作为 key 放入容器；每次 tick 取出最小 key 与当前时间比较，小于当前时间则到期，执行回调。

容器需要频繁地**取最小值 + 插入 + 删除**：

- **最小堆**：`find-min` 为 O(1)，插入/删除 O(log n)，实现简单，是最常见选择；STL 提供 `make_heap/push_heap/pop_heap`，或直接用 `std::priority_queue`；
- **红黑树**：有序，支持删除任意节点与范围查询，libuv 在 Windows 上用红黑树；
- **时间轮（timing wheel）**：O(1) 插入与删除，适合大量定时器且精度要求不高的场景；Linux 内核、skynet、folly 的 `HHWheelTimer` 都是这个思路；
- **多级时间轮 / 分层堆**：兼顾大范围与高精度。

### 5.3 时间源

这是唯一真正需要处理平台差异的地方。要考虑：

- **精度**：`gettimeofday()` 精度受限于时钟源，通常是微秒级但不保证单调；
- **单调性**：壁钟会被 NTP 调整甚至回拨，定时器必须用**单调时钟**，否则会出现"定时器永远不到期"或"一次性全部到期"；
- **CPU 时间 vs 壁钟时间**：定时器语义通常是壁钟。

| 平台 | API | 说明 |
|---|---|---|
| Windows | `QueryPerformanceFrequency()` / `QueryPerformanceCounter()` | 高精度计数器 |
| Linux | `clock_gettime(CLOCK_MONOTONIC, ...)` | 推荐；`CLOCK_REALTIME` 会被调整 |
| macOS | `mach_absolute_time()` / `clock_gettime` | `gettimeofday` 非单调，不推荐 |
| 跨平台 C++ | `std::chrono::steady_clock` | **不要用 `high_resolution_clock`**，它可能是 `system_clock` 的别名 |

> **修正**：原笔记推荐 `std::chrono::high_resolution_clock`。它只保证"高精度"，**不保证单调**（libstdc++ 中它就是 `system_clock`）。定时器应使用 `steady_clock`。

### 5.4 单线程还是独立线程

- **放在主循环**：基于回调的单线程实现，无锁、无跨线程通信，但定时器回调会阻塞主循环；
- **独立 timer 线程**：适合回调可能耗时的情况，需要设计线程间通信（任务队列 / 事件通知），asio、skynet 都有独立的 timer 线程。

无论哪种，回调执行时间都应尽量短；耗时操作丢到工作线程。

### 5.5 常见实现参考

- **boost.asio** `timer_queue`：最小堆；
- **libuv**：Windows 用红黑树，Unix 用最小堆；
- **Linux kernel** `kernel/time/timer.c`：多级时间轮；
- **skynet** `skynet_timer.c`：时间轮；
- **folly** `HHWheelTimer`：分层时间轮。

选型时先问三个问题：定时器数量级、精度要求、是否需要频繁取消。数量大 + 精度低 → 时间轮；数量中等 + 需要精确取消 → 最小堆或红黑树。

## 六、CPU、GPU 与 FPGA

### 6.1 CPU：为串行代码优化

CPU 是标量体系结构，目标是**尽快执行一条依赖链**。现代 CPU 是超标量、乱序执行、多线程的复杂核心：

- 一次取多条指令，构建依赖图；
- 乱序执行互不依赖的指令；
- 复杂的分支预测；
- SIMD 指令（SSE/AVX/NEON）处理数据并行部分。

结果是单核 IPC 可以远超 1（相对经典标量流水线的 1 IPC，现代桌面核心可达数倍）。

![标量流水线 CPU 与超标量 CPU](../../技术笔记/assets/WEBRESOURCEcd4d645cb116c4f2bedba292c860a54a.jpg)

CPU 的优势：

- 乱序超标量执行，能挖掘大量指令级并行（ILP）；
- 分支预测准确，适合分支散度高、控制流复杂的代码；
- 延迟低（无需卸载数据）；
- 顺序代码开发简单；
- 指令集丰富，适合各种工作负载。

### 6.2 GPU：为吞吐量优化

GPU 由大量小而专用的核心组成，优化目标是**所有核心的总吞吐量**，而不是单线程延迟。

- 硅面积更多给 ALU，更少给 cache 和控制器；
- 有序执行，不做复杂分支预测；
- 深流水线，靠**大量独立线程**掩盖访存延迟；
- SIMT（Single Instruction, Multiple Threads）执行模型：多个线程以锁步方式执行同一条 SIMD 指令流；
- 多个 SIMD 流映射到一个执行单元（EU），一个流停顿时切换到另一个流。

![CPU 与 GPU 的结构差异](../../技术笔记/assets/WEBRESOURCE9e08fdb824e9a75f617ca1ece70845b4.jpg)

GPU 的优势：数千个轻量 SIMD 核心、极高的数据并行吞吐、很高的 DRAM 带宽。

GPU 的劣势：分支发散（warp 内分支不同路径要串行化）、需要大量并行度才能填满流水线、数据传输与 kernel 启动有开销。

### 6.3 FPGA：空间体系结构

FPGA 是可重新配置的硬件：编译后的"指令"变成空间上排布的硬件电路，所有电路可以同时工作。

- 由大量 1 位可编程逻辑块（LUT）、可配置存储块、DSP 块组成；
- 用可编程互连网络连接；
- 数据流经为算法定制的深流水线，**没有取指、译码、寄存器回写、分支预测等控制开销**；
- 流水线并行是主要并行形式，可与数据并行、任务并行、超标量并行组合。

![FPGA 的可重配置阵列](../../技术笔记/assets/WEBRESOURCE6cce00a2cde203b920ac728867d2d469.jpg)

优势：极高的能效比、可定制指令与非标准数据类型、确定性延迟、丰富的 I/O 与片上存储拓扑。

劣势：开发门槛高（HDL/高层次综合）、编译时间长、不适合频繁变更的算法、峰值频率低于 CPU/GPU。

### 6.4 三者怎么选

| 场景 | 首选 |
|---|---|
| 复杂控制流、分支多、串行依赖强 | CPU |
| 大规模规整数据并行（图像、矩阵、神经网络推理） | GPU |
| 超低延迟、确定性、极致能效、流式处理 | FPGA |
| 数据量小但计算密集 | CPU（传输开销占比太高，卸载不划算） |

经验法则：**先看算术强度（compute / bytes）**。算术强度低 → 受带宽限制，卸载到 GPU 收益有限；算术强度高且并行度足够 → GPU/FPGA 才有优势。

## 七、存储带宽

### 7.1 显存带宽

基本公式：

```
带宽 (B/s) = 等效数据率 (MT/s) × 位宽 (bit) / 8
```

按此式算出的**数值**单位是 MB/s（例如 `500 × 128 / 8 = 8000`），再按 `1 GB/s = 1000 MB/s` 折成 GB/s；要严格的 B/s 再乘 `10⁶`。

乘以通道数则是总带宽。这里的"频率"对 DDR/GDDR 指**等效数据率**（DDR 双沿传输，所以 500 MHz 时钟对应 1000 MT/s），不要直接拿时钟频率代入。

原笔记的例子（500 MHz、128/256 位）属于 DDR 时代：

- 128 位：500 MT/s × 128 / 8 = 8000 MB/s = 8 GB/s
- 256 位：500 MT/s × 256 / 8 = 16000 MB/s = 16 GB/s

这个换算关系仍然正确，但**参数已过时**。现代显卡早已不是 64/128/256 位三档：

- GDDR6/GDDR6X 常见 128–384 位，等效数据率 14–21 Gbps 以上；
- HBM2e/HBM3 用 1024 位以上的超宽接口 + 2.5D 封装，靠位宽而不是频率取胜。

> **待核实**：具体型号的带宽请以厂商规格为准。示例量级：384 位 @ 21 Gbps ≈ 1008 GB/s（RTX 4090 级别）；HBM3 旗舰可达 3 TB/s 以上。原笔记中的 8/16 GB/s 是 2000 年代中期的水平。

### 7.2 CPU 内存带宽

```
带宽 = 等效数据率 (MT/s) × 位宽 (bit) / 8 × 通道数
```

DDR5-5600 双通道、64 位/通道：5600 × 64 / 8 × 2 ≈ 89.6 GB/s。服务器多通道平台可达数百 GB/s。

### 7.3 为什么带宽重要

- GPU 的算力/带宽比（arithmetic intensity）决定了它是"计算受限"还是"带宽受限"；
- 多线程共享内存时，真正的瓶颈常常是 cache line 争用与内存带宽，而不是锁；
- 数据布局（AoS vs SoA）、访问顺序、对齐方式，对实际带宽的利用率影响巨大。

## 八、指令流水线与分支预测

### 8.1 流水线

指令流水线把一条指令的处理拆成若干连续且独立的阶段，让不同指令的不同阶段重叠执行，从而提高**吞吐量**。

典型四阶段：

1. **Fetch**：取指令
2. **Decode**：译码
3. **Execute**：执行
4. **Write back**：写回结果

关键点：**流水线不降低单条指令的延迟**，反而可能因为拆分阶段、增加寄存器而略微增加延迟；它提升的是单位时间完成的指令数。理想情况下 k 级流水线的吞吐量提升接近 k 倍。

![指令流水线](../../技术笔记/assets/307B52E25C8546CFB5838CDCE2829F5D.png)

### 8.2 分支预测

流水线只有在"知道下一条指令在哪"时才能持续填充。遇到条件分支时，处理器在计算出条件之前并不知道该走哪条路（条件由输入数据决定），于是：

- **分支预测器**根据历史记录猜测最可能的方向，并**推测执行**后续指令；
- 预测正确 → 流水线不中断，收益巨大；
- 预测失败 → 必须清空（flush）流水线，从正确地址重新取指，付出严重的**性能惩罚**（典型十几个到几十个周期，深流水线更贵）。

这解释了很多性能现象：

- **有序数组遍历远快于随机顺序**：分支预测器能学到规律；
- **分支少、可预测的代码更快**：把热点循环里的 `if` 改成无分支写法（查表、算术掩码）有时能显著提速；
- **间接跳转（虚函数、switch）难预测**：BTB 命中率下降，惩罚上升；
- 编译器会用条件传送（`cmov`）替代短分支，避免预测失败。

## 九、定点数与浮点数

### 9.1 定点数

定点数约定小数点的位置固定：

- **纯整数**：小数点固定在最低位之后；
- **纯小数**：小数点固定在最高位之前；
- **整数 + 小数**：约定中间某个位置，如前 5 位整数、后 3 位小数。

以 8 bit、前 5 后 3 为例：

```
1.5(D)   = 00001 100(B)
25.125(D)= 11001 001(B)
```

局限：

- 表示范围由整数位宽决定（5 位整数最大 31）；
- 精度由小数位宽决定（3 位小数最小步长 2^-3 = 0.125）；
- 想扩大范围就得右移小数点，精度随之下降，二者不可兼得。

因此定点数适合**范围已知、精度固定**的场合（音频采样、嵌入式控制、金融以"分"为单位存储），现代通用计算中的整数本质就是定点数（小数点在最右）。

小技巧：二进制小数每右移一位就是除以 2。`00000 110(B)` = 2^-1 + 2^-2 = 0.75。

### 9.2 十进制转二进制

**整数：除 2 取余，逆序排列**

```
6 / 2 = 3 ... 0
3 / 2 = 1 ... 1
1 / 2 = 0 ... 1
=> 110(B)
```

**小数：乘 2 取整，顺序排列**

```
0.8125 × 2 = 1.625 -> 1
0.625  × 2 = 1.25  -> 1
0.25   × 2 = 0.5   -> 0
0.5    × 2 = 1.0   -> 1
=> 0.1101(B)
```

**0.1 是无限循环小数**：

```
0.1 × 2 = 0.2 -> 0
0.2 × 2 = 0.4 -> 0
0.4 × 2 = 0.8 -> 0
0.8 × 2 = 1.6 -> 1
0.6 × 2 = 1.2 -> 1
0.2 × 2 = 0.4 -> 0   (开始循环 0011)
...
=> 0.0001 1001 1001 1001...(B)
```

这直接解释了为什么 `0.1 + 0.2 != 0.3`（**双精度**；单精度的 `0.1f + 0.2f == 0.3f` 是误差恰好抵消的巧合）：它们都无法用有限位二进制精确表示，只能存最近的可表示值。

### 9.3 IEEE 754 单精度格式

32 位单精度：`1 位符号 + 8 位指数 + 23 位尾数`。

![IEEE 754 单精度格式](../../技术笔记/assets/WEBRESOURCEbad6ebd4f845b0d84627d4b9946f4809.png)

图中示例（位模式以 s、e、m 三段标注，含 31…0 的位编号）可独立写出为：

```
位模式   = 0 01111100 01000000000000000000000
sign     = 0                              → (+1)
exponent = 124 − 127 = −3
fraction = 1 + 2^-2 = 1.25
value    = (+1) × 1.25 × 2^-3 = +0.15625
```

- **符号位 s**：0 正 1 负；
- **指数字段 e**：8 位无符号数，实际指数 = e − 127（偏移量 127）；
- **尾数字段 m**：存储时省略了规格数最高位的那个 `1`，所以有效精度是 **24 位**。

取值公式（规格数）：

```
value = (-1)^s × 1.m × 2^(e-127)
```

三种状态：

| 指数 e | 尾数 m | 含义 |
|---|---|---|
| 1 – 254 | 任意 | 规格数，实际指数 −126 … +127 |
| 0 | 0 | ±0 |
| 0 | ≠0 | 非规格数（次正规数），值 = 0.m × 2^-126，用于表示极接近 0 的数 |
| 255 | 0 | ±∞ |
| 255 | ≠0 | NaN |

> **修正**：原笔记一处写"指数位用于表示 [−127, 128] 范围"，与另一处"实际范围 −126 到 +127"矛盾。正确结论是：8 位指数字面值 1–254 对应实际指数 **−126 到 +127**（去掉全 0 与全 1 两个保留值）；偏移量是 127。

**例：20.5**

```
20.5(D) = 10100.1(B) = 1.01001 × 2^4
符号位 s = 0
指数 e  = 4 + 127 = 131 = 1000 0011(B)
尾数    = 0100 1000 0000 0000 0000 000(B)   // 去掉前导 1.，右侧补零
结果    = 0 1000 0011 0100 1000 0000 0000 000
```

特殊值约定：

- IEEE 754 规定 `-0.0 == 0.0`；
- `e = 255, m = 0` → `inf`；`e = 255, m ≠ 0` → `nan`；
- 最大规格数 ≈ `1.111...1 × 2^127` ≈ **3.4028235 × 10^38**；
- 最小正规格数 ≈ `1.0 × 2^-126` ≈ **1.1754944 × 10^-38**。

### 9.4 浮点数的"间隔"与精度

浮点数的分布**不是均匀的**。可以把 32 位浮点数的位模式想象成一个表盘：尾数每加 1，就走到下一个可表示值。由于尾数只有 23 位，相邻两个值的间隔（ULP）随指数增大而增大。

![浮点数表盘：间隔随指数增大](../../技术笔记/assets/WEBRESOURCEfed2521fcf685d37176b127221ec2da6.png)

推导：从 `0 00000001 000...0` 走 2^23 步到 `0 00000010 000...0`，指数增加 1，值翻倍。该区间内被均分为 2^23 份，所以：

```
间隔 = (2^(e+1) - 2^e) / 2^23 = 2^e / 2^23
```

在 [1, 2) 区间（e = 0）：

```
间隔 = 1 / 2^23 = 1.1920928955078125e-7
```

这正是 `FLT_EPSILON`：

```c
#define FLT_EPSILON 1.192092896e-07F   // 满足 1.0f + FLT_EPSILON != 1.0f 的最小值
```

C99 的定义是："1 与大于 1 的最小可表示 float 之间的差"。注意它**只对 [1,2) 区间成立**；换个区间，"最小可分辨增量"就变成该区间的间隔：

| 真实指数（unbiased） | 偏移后的指数（biased） | 最小值 Minimum | 最大值 Maximum | 间隔 Gap |
|---|---|---|---|---|
| −1 | 126 | 0.5 | ≈ 0.999999940395 | ≈ 5.96046e−8 |
| 0 | 127 | 1 | ≈ 1.999999880791 | ≈ 1.19209e−7 |
| 1 | 128 | 2 | ≈ 3.999999761581 | ≈ 2.38419e−7 |
| 2 | 129 | 4 | ≈ 7.999999523163 | ≈ 4.76837e−7 |
| 10 | 137 | 1024 | ≈ 2047.999877930 | ≈ 1.22070e−4 |
| 11 | 138 | 2048 | ≈ 4095.999755859 | ≈ 2.44141e−4 |
| 23 | 150 | 8388608 | 16777215 | 1 |
| 24 | 151 | 16777216 | 33554430 | 2 |
| 127 | 254 | ≈ 1.70141e38 | ≈ 3.40282e38 | ≈ 2.02824e31 |

所以在 16777216（2^24）之后，`float` 无法表示所有整数（奇数会被舍入）；在 [2^23, 2^24) 区间内间隔已经是 1，恰好能表示该区间的全部整数。

**实践含义**：

- 浮点相等比较必须用容差，且容差应**随数量级缩放**（相对误差），不能固定用 `1e-6`：

  ```cpp
  bool nearly_equal(float a, float b, float eps = 1e-5f) {
      float diff = std::fabs(a - b);
      return diff <= eps * std::max(1.0f, std::max(std::fabs(a), std::fabs(b)));
  }
  ```

- 大数吃小数：把 1e-8 累加到 1e8 上毫无效果；
- 累加大量浮点数时用 Kahan 求和或先排序；
- 需要精确十进制（金额）时用定点整数，不要用 `float/double`。

## 十、堆与栈

### 10.1 两种语境

"堆"和"栈"在不同语境下含义不同：

- **内存布局**：两种内存管理方式；
- **数据结构**：两种抽象数据类型（FILO 栈、优先队列堆）。

### 10.2 程序内存分区

一个进程的典型地址空间：

```
高地址
+------------------+
|     栈 Stack      |  向下增长，函数参数、局部变量、返回地址
+------------------+
|       ↓           |
|                  |
|       ↑           |
+------------------+
|     堆 Heap       |  向上增长，malloc/new
+------------------+
|  BSS（未初始化全局）|
+------------------+
|  Data（已初始化全局/静态）|
+------------------+
|  Text（代码/只读常量）|
+------------------+
低地址
```

**栈**：由编译器/操作系统自动管理，存放函数参数、局部变量、返回地址、保存的寄存器。函数返回即释放。

```c
int main(void) {
    int b;             // 栈
    char s[] = "abc";  // 栈（数组本身在栈上，内容可写）
    char* p2;          // 栈（指针变量本身）
}
```

栈帧布局（x86 典型）：

```
[高地址]  调用者的栈帧
          实参（常见从右向左压栈）
          返回地址（EIP/RIP）
          保存的 EBP/RBP
          局部变量
[低地址]  当前栈顶（ESP/RSP）
```

**堆**：由程序员申请和释放，`malloc/free` 或 `new/delete`。未释放时生命周期等同进程。

```c
char* p1 = (char*)malloc(10);   // 堆
free(p1);

char* p2 = new char[10];        // 堆
delete[] p2;
```

堆分配器内部维护空闲块结构（空闲链表 / 分离空闲链表 / buddy 等）：找到足够大的块、切分、把剩余部分放回。块头通常记录大小，`free` 才能知道释放多少。频繁申请释放会产生**内存碎片**。

### 10.3 堆与栈的区别

| 维度 | 栈 | 堆 |
|---|---|---|
| 管理方式 | 编译器/OS 自动 | 程序员手动（或 GC） |
| 大小 | 小，编译期/线程创建时确定（Windows 默认 1 MB，Linux 默认 8 MB，`ulimit -s` 可调） | 大，理论上受虚拟内存与物理内存限制 |
| 生长方向 | 通常向低地址（x86/ARM 常见） | 通常向高地址 |
| 分配方式 | 静态（局部变量）+ 动态（`alloca`，函数返回自动回收） | 动态 |
| 效率 | 高：仅移动栈指针，有专门寄存器与指令，cache 友好 | 低：分配器查找、可能系统调用、碎片、cache 不友好 |
| 存放内容 | 返回地址、参数、局部变量、保存的寄存器 | 任意，由程序员决定 |
| 失败方式 | 栈溢出（崩溃） | 返回 `NULL` / 抛 `bad_alloc` |

> **修正/待核实**：
> - 原笔记"64 位 Windows 默认 1 MB，64 位 Linux 默认 10 MB"中，Linux 默认值通常是 **8 MB**（`ulimit -s` 常见 8192 KB），不是 10 MB。
> - 原笔记"后定义的局部变量地址一定低于先定义的变量"**不成立**。C/C++ 标准不规定局部变量的相对地址，编译器会重排、复用栈槽、做对齐优化。只能观察，不能依赖。
> - "栈向低地址增长"是主流 ABI 的实现，不是语言标准保证。

### 10.4 数据结构中的栈与堆

**栈**：只能在一端（栈顶）插入和删除的线性表，FILO。可用数组（顺序栈）或链表（链式栈）实现。基本操作：`init / isEmpty / push / pop / top`。

```cpp
struct SeqStack {
    int data[MAXSIZE];
    int top;          // -1 表示空
};

bool push(SeqStack* s, int x) {
    if (s->top == MAXSIZE - 1) return false;
    s->data[++s->top] = x;
    return true;
}

bool pop(SeqStack* s, int* x) {
    if (s->top == -1) return false;
    *x = s->data[s->top--];
    return true;
}
```

**堆**：满足堆序性的完全二叉树。大顶堆每个节点 ≥ 子节点，小顶堆反之；左右孩子无顺序要求。用数组存储，下标 `i` 的左右孩子是 `2i+1`、`2i+2`，父节点是 `(i-1)/2`。插入/删除 O(log n)，取极值 O(1)。用于优先队列、堆排序、Top-K、定时器（见第五节）。

注意：数据结构里的"堆"与内存管理里的"堆"**没有任何关系**，只是中文译名相同。

### 10.5 使用建议

- 优先栈：生命周期与作用域一致、大小可控的数据；
- 需要动态大小或跨函数生命周期时才用堆，并用 RAII / 智能指针管理；
- 大对象（几 MB 的数组）不要放栈上，会栈溢出；
- 递归深度不可控时改迭代，或显式设置线程栈大小；
- 无论堆栈都要防越界：越界写会破坏相邻数据，表现为"随机崩溃"或"结果不对"，极难排查。
