# 编译、链接与工程组织

本篇把「一段代码如何变成可执行文件」作为主线：先看预处理、编译、汇编、链接四个阶段各自做了什么，再讨论头文件、静态库/动态库与符号导出，最后落到最常见的链接错误和 C/C++ 混合编程。理解了符号（symbol）在哪个阶段产生、由谁解析，绝大多数 LNK2019/LNK2001 都能自己定位。

## 一、从源代码到可执行文件

![编译链接流程](../../技术笔记/assets/47D1EAF7ED5A47368FF156EF834C9F2A.png)

四个阶段的分工：

| 阶段 | 输入 | 主要工作 | 输出 |
|---|---|---|---|
| 预处理 | `.c` / `.cpp` + 头文件 | 展开 `#include`、宏替换、处理条件编译、删除注释、插入行号标记 | `.i` |
| 编译 | `.i`（一个编译单元） | 词法/语法/语义分析、符号汇总、生成汇编 | `.s` |
| 汇编 | `.s` | 翻译成机器指令、生成符号表、记录重定位信息 | `.o` / `.obj` |
| 链接 | 多个 `.o` + 库 | 符号解析、重定位、合并节 | 可执行文件 / 共享库 |

### 1.1 预处理

预处理是**逐编译单元独立**进行的：每个 `.cpp` 各自展开自己 include 的头文件，互不影响。因此同一个头文件被 N 个源文件包含，就会展开 N 份；预处理器不做去重，去重靠头文件里的 include guard。

预处理完成后头文件就"消失"了——后续阶段看到的只有展开后的 `.i`。这解释了后面很多现象：头文件里写函数定义，等价于在每个包含它的源文件里各写一份定义。

### 1.2 编译

编译以编译单元为单位，只做**声明检查**：函数有没有声明、类型是否匹配、语法是否合法。它**不关心函数体在哪里**，只要见过声明就允许生成一条"待解析的外部符号"引用。

所以"编译通过"只说明语法和声明没问题，符号能否找到是链接阶段的事。

### 1.3 汇编

汇编把 `.s` 变成二进制目标文件，同时产出符号表：

- 本单元**定义**的符号（函数、全局变量）记为已定义；
- 本单元**引用**但未定义的符号记为 undefined，等待链接器补上。

这里常被误解的一点是"重定位 = 建立物理内存与虚拟地址的映射"。**不对**。汇编/链接阶段的重定位，是把指令中的符号引用改写为节内偏移或最终地址；虚拟地址到物理地址的映射是程序**加载运行时**由 MMU + 页表完成的，和链接器无关。

### 1.4 链接

链接器做两件事：

1. **符号解析**：每个 undefined 符号都要在其它目标文件或库里找到唯一一处定义；
2. **重定位**：把引用处的占位地址改写为符号的最终地址。

两个直接推论：

- 链接之前，各目标文件是彼此隔离的；
- 同一个强符号（非 `static`、非 `inline` 的函数或全局变量）出现两次，就是重定义错误（MSVC 是 LNK2005，GCC 是 multiple definition）。

### 1.5 编译单元、声明与定义

| | 处理阶段 | 作用域 | 可否重复 |
|---|---|---|---|
| 声明 | 编译 | 当前编译单元 | 可以，且必须一致 |
| 定义 | 链接（分配实体） | 全程序唯一（强符号） | 不可重复 |

由此可以完整解释"函数实现放在头文件里会怎样"：头文件被多个源文件包含 → 每个 `.o` 里都有一份该函数的定义 → 链接时出现多个同名强符号 → 重定义。只有一个源文件包含该头文件时不会报错，因为不存在第二个定义。

## 二、头文件的正确组织

### 2.1 Include Guard

```cpp
#ifndef MYPROJECT_MATH_UTILS_H_
#define MYPROJECT_MATH_UTILS_H_

// 声明

#endif  // MYPROJECT_MATH_UTILS_H_
```

作用是防止**同一个编译单元**内重复展开同一个头文件（A 包含 B，B 又包含 A 的典型菱形包含）。它**不能**防止多个源文件各展开一份——那是 ODR 的问题，不是 include guard 能解决的。

`#pragma once` 是事实标准，语义更简单（按文件路径去重），但非 ISO C++；可移植代码仍建议用 guard。宏名要带项目/路径前缀，避免和第三方库撞名。

### 2.2 把函数实现放进头文件的三种办法

模板必须放头文件（实例化需要看到定义），非模板函数则不应该。若确实要放，有三种规避重定义的手段：

**（1）`inline`**

```cpp
inline int add(int x, int y) { return x + y; }
```

`inline` 的现代语义是"允许在多个编译单元中出现相同定义"（ODR 豁免），"就地展开"只是编译器可选的优化提示，不保证。缺点：可能增大代码体积；C 语言里 `inline` 的链接语义与 C++ 不同（C99 需要配合 `extern` 声明或 `static inline`），跨语言头文件要留意。

**（2）`static`**

```cpp
static int add(int x, int y) { return x + y; }
```

每个包含它的编译单元各得一份**内部链接**副本，互不冲突。代价是代码膨胀，而且每个单元的函数地址不同——不能用它做跨单元的函数指针比较。

**（3）类的静态成员函数**

```cpp
class MathAdd {
public:
    static int add(int x, int y) { return x + y; }
};
```

类内定义的成员函数隐式 `inline`，因此同样满足 ODR。这是最"干净"的一种，也便于加命名空间。

无论哪种方案，工程上仍应优先**声明放头文件、定义放源文件**。

## 三、静态库与动态库

| | 静态库 | 动态库 |
|---|---|---|
| Windows | `.lib` | `.dll` + 导入库 `.lib` |
| Linux | `.a` | `.so` |
| 链接时机 | 编译期把目标代码复制进可执行文件 | 链接期只记录依赖，运行/加载时解析 |
| 体积 | 可执行文件大 | 可执行文件小，库单独分发 |
| 更新 | 必须重新链接 | 替换库文件即可（ABI 兼容前提下） |
| 符号可见性 | 不涉及导出表 | 需显式导出，否则外部不可见 |

### 3.1 只有被导出的符号才会生成导入库

一个实际踩过的坑：把静态库工程改成 DLL 后，只产出了 `.dll`，没有 `.lib`。原因是**没有任何符号被导出**——MSVC 只有在检测到导出符号时才生成导入库。

排查顺序：

1. 导出宏是否真的展开成了 `__declspec(dllexport)`；
2. 导出宏依赖的预定义宏（如 `MYLIB_EXPORTS`）是否在**本工程**的编译选项里定义；
3. 导出的是类还是函数，类导出是否覆盖了需要调用的成员。

### 3.2 `dllexport` / `dllimport` 的标准写法

```cpp
// export.h
#ifndef MYLIB_EXPORT_H_
#define MYLIB_EXPORT_H_

#ifdef MYLIB_EXPORTS
#  define MYLIB_API __declspec(dllexport)
#else
#  define MYLIB_API __declspec(dllimport)
#endif

#endif
```

`__declspec(dllexport)` 表示"本模块导出"，`__declspec(dllimport)` 表示"从别的模块导入"。使用方若不加 `dllimport`，通常也能链接成功（链接器会走 thunk），但会损失一点调用效率，且无法导入数据符号。

### 3.3 库嵌套时 export.h 的宏名冲突

每个库工程习惯各写一个 `export.h`，若 guard 都叫 `FMEXPORT_H`，那么当一个工程同时包含两个库的头文件时，第二个 `export.h` 会被 guard 直接跳过，导致它的导出宏根本没有定义，随后出现一堆莫名其妙的编译/链接错误。

规则：**guard 宏必须带库名前缀**。

```cpp
#ifndef FM_CJSON_EXPORT_H
#define FM_CJSON_EXPORT_H
// ...
#endif
```

### 3.4 导出函数的重命名问题

MSVC 下 C++ 函数会按调用约定修饰名字（如 `?fn@@YAXXZ`），C 编译器则不做 C++ 修饰：32 位 x86 上通常只加前导下划线，x64/ARM64 则不加（可用 `dumpbin /symbols` 实测确认）。跨语言调用时必须统一：

- 方案一：接口声明外包 `extern "C"`；
- 方案二：用模块定义文件（`.def`）显式指定导出名。

`extern "C"` 可移植性好；`.def` 可以精确控制导出名且不影响函数本身的 C++ 链接属性。`__declspec(dllexport)` 会为每个重载导出各自修饰后的名字，C++ 调用方仍能按修饰名链接到；只有需要按未修饰的同名符号导出（例如供 C 调用）时，才必须用 `.def` 指定导出名。

## 四、链接错误：LNK2019 / LNK2001

`LNK2019: 无法解析的外部符号` 和 `LNK2001: unresolved external symbol` 本质相同——链接器找不到某个符号的定义。按下面顺序排查，基本能覆盖全部情况。

### 4.1 排查清单

**（1）源文件根本没参与编译**

最常见。文件在磁盘上，但没加入工程 / 没写进 CMakeLists / Makefile。此时符号确实不存在。先确认 `.obj` 是否生成。

**（2）声明与定义的符号不一致（C/C++ 混编）**

`.cpp` 调用 `.c` 里的函数，而头文件没有 `extern "C"`，于是 C++ 侧找的是修饰后的名字 `?foo@@...`，C 侧只提供了 `_foo`。这是 LNK2001 在混合工程里的头号原因，处理方式见第五节。

**（3）库没链接，或链接顺序不对**

GCC/binutils 的静态库按命令行顺序**从左到右**单遍扫描：库必须放在引用它的目标文件之后。循环依赖需要 `--start-group/--end-group` 或重复列出。

**（4）平台/架构/运行库不匹配**

x86 工程链接了 x64 的库；`/MD` 与 `/MT` 混用导致 CRT 符号对不上；Debug 链接了 Release 库。这类错误往往伴随大量 CRT 符号（如 `__imp__printf`）缺失。

**（5）符号被 `static` 或匿名命名空间限制**

定义处加了 `static`（内部链接），别的编译单元永远看不到。头文件里 `static` 函数尤其容易造成"每个单元一份、地址还不同"的隐性 bug。

**（6）类的静态成员变量只声明未定义**

```cpp
class Foo {
    static int count;   // 声明
};
int Foo::count = 0;     // 必须有这一行（C++17 起可用 inline static 免去）
```

**（7）只声明了纯虚函数/模板，没有实例化**

模板定义不在头文件中，或显式实例化缺失。

### 4.2 与"重定义"区分

- **未解析的外部符号**：缺定义；
- **重定义（LNK2005 / multiple definition）**：定义多了，通常是头文件里放了非 inline 的函数或全局变量。

两者是同一枚硬币的两面，都指向"符号在哪里、有几份"。

## 五、C 与 C++ 混合编程

### 5.1 名字修饰（name mangling）

C 没有重载和命名空间，符号基本就是 `_函数名`（32 位 x86 的前导下划线，x64/ARM64 上没有）；C++ 为了支持重载，把函数名、参数类型、命名空间等信息编码进符号，例如 `void foo(int, int)` 可能变成 `_foo_int_int`（不同编译器规则不同，GCC 是 `_Z3fooii`）。

链接器只认符号字面量，所以两边规则不一致就一定找不到符号。`extern "C"` 的本质就是：**告诉 C++ 编译器，这段声明按 C 的规则生成/查找符号**。

### 5.2 `extern "C"` 的两重含义

1. 被修饰的目标具有 `extern` 链接属性（外部可见、可跨模块引用）；
2. 被修饰的目标按 C 语言方式编译和链接（不做 C++ 名字修饰）。

补充：`extern` 只是声明，不分配存储；与它相对的是 `static`（内部链接）。因此只在本模块使用的函数没有理由加 `extern "C"`。

### 5.3 标准写法：让头文件同时服务 C 和 C++

```cpp
// cfun.h
#ifndef MYPROJECT_CFUN_H_
#define MYPROJECT_CFUN_H_

#ifdef __cplusplus
extern "C" {
#endif

void cfun(void);

#ifdef __cplusplus
}
#endif

#endif
```

`__cplusplus` 只在 C++ 编译器中定义，所以 C 编译器看到的是普通声明，C++ 编译器看到的是 C 链接声明。**头文件和实现文件都要遵守同一套规则**：如果 `.c` 文件被误当作 C++ 编译，或者 `.c` 里没有包含该头文件，仍会不一致——所以 `.c` 文件第一件事就是 `#include` 自己的头文件。

### 5.4 C++ 调用 C

C 侧按上面的方式提供头文件即可，C++ 侧直接 `#include` 并调用。

### 5.5 C 调用 C++ 函数

C++ 侧把要暴露的函数声明为 `extern "C"`，C 侧用普通 `extern` 声明：

```cpp
// cppfun.h（供 C 包含，不能出现任何 C++ 语法）
#ifndef MYPROJECT_CPPFUN_H_
#define MYPROJECT_CPPFUN_H_

#ifdef __cplusplus
extern "C" {
#endif

void cppfun(void);

#ifdef __cplusplus
}
#endif

#endif
```

```cpp
// cppfun.cpp
#include "cppfun.h"
#include <iostream>

void cppfun() { std::cout << "hello world." << std::endl; }
```

```c
/* main.c */
extern void cppfun(void);
int main(void) { cppfun(); return 0; }
```

注意：C 侧的头文件里不能出现类、模板、引用、默认参数、函数重载——C 编译器解析不了。

### 5.6 C 调用 C++ 类：句柄 + 包装层

C 没有类，标准做法是**不透明句柄（opaque handle）**：C 侧只看到 `void*`，真正的类型转换全部留在 C++ 侧。

```cpp
// person.h（C++）
#include <string>

class Person {
public:
    Person(std::string name, int age);
    const char* GetName() const { return name_.c_str(); }
    int GetAge() const { return age_; }
private:
    std::string name_;
    int age_;
};
```

```cpp
// wrapper.h（供 C 包含）
#ifndef MYPROJECT_WRAPPER_H_
#define MYPROJECT_WRAPPER_H_

#ifdef __cplusplus
extern "C" {
#endif

void*       call_Person_Create(void);
void        call_Person_Destroy(void* p);
int         call_Person_GetAge(void* p);
const char* call_Person_GetName(void* p);

#ifdef __cplusplus
}
#endif

#endif  // MYPROJECT_WRAPPER_H_
```

```cpp
// wrapper.cpp
#include "wrapper.h"
#include "person.h"

void* call_Person_Create(void) {
    return new Person("Aland", 18);
}

void call_Person_Destroy(void* p) {
    delete static_cast<Person*>(p);
}

int call_Person_GetAge(void* p) {
    return static_cast<Person*>(p)->GetAge();
}

const char* call_Person_GetName(void* p) {
    return static_cast<Person*>(p)->GetName();
}
```

```c
/* main.c */
#include <stdio.h>
#include "wrapper.h"

int main(void) {
    void* p = call_Person_Create();
    int age = call_Person_GetAge(p);
    const char* name = call_Person_GetName(p);
    printf("name=%s, age=%d\n", name, age);
    call_Person_Destroy(p);
    return 0;
}
```

几条硬性约束：

- **谁分配谁释放**：`new` 出来的对象必须由 C++ 侧的 `Destroy` 释放。C 侧调用 `free` 是未定义行为（不同 CRT/堆）。
- **异常不能穿过 C 边界**：包装函数里要 `try/catch` 兜住所有异常，转成错误码返回。C 没有异常机制，栈展开会直接崩。
- **返回的指针生命周期**：`GetName()` 返回的是 `Person` 内部 `std::string` 的缓冲区，对象销毁后立即失效；需要跨调用保留就拷贝出去。
- **`const char*` 的所有权**要说清楚，否则 C 侧很容易 `free` 它。

### 5.7 `extern "C"` 的使用要点

```cpp
extern "C" double sqrt(double);          // 单条声明

extern "C" {                             // 复合语句，内部声明全部按 C 链接
    double sqrt(double);
    int min(int, int);
}

extern "C" {                             // 也可以包住整个头文件
    #include <cmath>
}
```

限制与细节：

- 不能写在函数体内部；
- 写在类的成员函数上是合法的（`extern "C" void T::g() {}` 可以通过编译），只是 C 链接语义被忽略、不生效，因此实际只能指望它作用于**自由函数**；
- 同一函数多次声明时，可以只对第一次声明加 `extern "C"`，后续声明沿用第一个链接指示符；
- 除 `"C"` 外标准还允许 `"C++"`，编译器可扩展支持 `"FORTRAN"` 等。

## 六、标准库头文件：`stdlib.h` 与 `stdio.h`

| | `stdlib.h` | `stdio.h` |
|---|---|---|
| 全称 | standard library | standard **buffered** input/output |
| 关注点 | 通用工具、内存管理、进程控制、数值转换 | 带缓冲的流式输入输出 |
| 典型内容 | `malloc/free/calloc/realloc`、`atoi/atol/strtol`、`rand/srand`、`exit/abort`、`system`、`qsort/bsearch` | `FILE`、`fopen/fclose`、`fread/fwrite`、`printf/scanf`、`fgets/fputs`、`fseek/ftell` |
| 类型/宏 | `size_t`、`div_t`、`EXIT_SUCCESS`、`RAND_MAX` | `FILE`、`EOF`、`BUFSIZ`、`stdin/stdout/stderr` |

一句话区分：`stdlib.h` 是"和系统打交道"的杂项工具箱（申请内存、退出进程、字符串转数字）；`stdio.h` 是"和流打交道"的 I/O 接口，带用户态缓冲。

## 七、`fread` 的返回值

```c
size_t fread(void* ptr, size_t size, size_t nmemb, FILE* stream);
```

返回值是**成功读入的完整元素个数**（`nmemb` 维度），**不是字节数**。

```c
size_t n = fread(buf, sizeof(Item), 100, fp);   // n <= 100
size_t bytes = n * sizeof(Item);                // 字节数要自己乘
```

要点：

- 返回 `n < nmemb` 不一定表示出错：正常读到文件末尾也会返回短计数。必须用 `feof(fp)` 和 `ferror(fp)` 区分；
- 最后一个元素可能只读到了一部分（文件长度不是 `size` 的整数倍），这部分数据**不会被计入返回值**；标准只规定该元素的值未指定，实现通常会把已读到的字节写进缓冲区，但不应依赖；
- 用 `fread` 的返回值直接当字节数去 `memcpy`/解析，是典型的越界或截断来源。

## 八、类型转换：`static_cast` 与 `const_cast`

### 8.1 `static_cast`

语义可以理解为"以 `x` 为参数构造一个 `T` 类型的值"，转换合法性在**编译期**确定，不做运行期检查。

```cpp
const int x = 10;
int y = static_cast<int>(x);            // OK：拷贝，丢掉 const
const int& r1 = static_cast<const int&>(x);  // OK
// int& r2 = static_cast<int&>(x);      // 错误：不能从 const 对象得到非 const 引用
std::string s = static_cast<std::string>("abc");  // OK，走 string 的构造函数
```

主要用途：

- 算术类型互转（`int` ↔ `double`、枚举 ↔ 整数）；
- `void*` ↔ 具体指针（`malloc` 返回值必须这样转，C++ 不允许 `void*` 隐式转 `T*`）；
- **向上转换**（派生类指针/引用 → 基类）是安全的；
- **向下转换**（基类 → 派生类）**不做检查**，类型不对就是未定义行为。需要运行时校验时用 `dynamic_cast`（要求基类是多态类型）。

### 8.2 `const_cast`

只做一件事：加上或去掉 `const` / `volatile` 限定。

```cpp
const char* p = "123";
char* c = const_cast<char*>(p);
// c[0] = 'x';   // 未定义行为
```

关键点：**如果原对象本身被定义为 `const`（或位于只读段，如字符串字面量），去掉 const 后写入是未定义行为**，不是"系统不允许"这么温和。`const_cast` 的合法用途只有一个：调用一个签名不严谨、但承诺不修改参数的旧接口。

### 8.3 四种转换的分工

| 转换 | 用途 | 运行期检查 |
|---|---|---|
| `static_cast` | 相关类型间的编译期转换、上行转换、`void*` 转换 | 无 |
| `const_cast` | 增删 cv 限定 | 无 |
| `dynamic_cast` | 多态类型的向下/交叉转换 | 有（失败返回 `nullptr` 或抛 `bad_cast`） |
| `reinterpret_cast` | 按位重新解释（指针 ↔ 整数、无关指针类型） | 无，最危险 |

C 风格转换 `(T)x` 会依次尝试上述组合，行为不明确，C++ 代码中应避免。

## 九、工程代码注意事项

- **一行声明多个指针时，每个都要写 `*`**：

  ```cpp
  int *a, *b;    // 两个都是指针
  int* a, b;     // b 是 int，不是指针
  ```

- **头文件必须自包含**：任何头文件单独包含都能编译通过，不要依赖"调用方先包含别的头"。
- **头文件只放声明**，模板和 `inline` 除外；全局变量用 `extern` 声明放头文件、定义放源文件（C++17 可用 `inline` 变量）。
- **导出宏、include guard 一律带库名前缀**，避免多库集成时撞名。
- **接口边界统一调用约定与内存归属**，尤其是跨 DLL、跨语言、跨 CRT 的接口。
- **不要忽略返回值**：`fread`、`fwrite`、`malloc`、系统调用都要检查；`fread` 的坑见第七节。
- **编译选项保持一致**：同一工程内 Debug/Release、`/MD` 与 `/MT`、x86/x64 不要混。
