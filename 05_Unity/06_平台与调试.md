# 平台与调试

> 本文整合 iOS 真机调试流程、通过 SSH 端口转发连接车机 Profiler 的办法、各平台图形 API 的关键差异，以及日志/帧调试中的实用技巧。

## 1. iOS 真机调试

### 1.1 前置确认

1. 先确认 Xcode 与 Unity 版本匹配，**用一个空的 Unity 工程做一次完整验证**，排除项目本身干扰。版本策略上直接对齐最新稳定版即可。
2. 确保工程能正常打出 iOS 包，或至少能正常做一次真机调试。

### 1.2 连接真机 Profiler 的步骤

1. Unity 切换到 iOS 平台。
2. `Build Settings` 中勾选 `Development Build` 与 `Autoconnect Profiler`（原文写作 auto profile）。
3. 点击 `Build and Run`。这一步实际是**导出 Xcode 工程**并自动打开。
4. 在 Xcode 中点击 Run，编译并安装到手机，正常情况下程序会直接启动。
5. 切回 Unity，Profiler 显示的即为真机数据。有时需要手动在 Profiler 的 `Active Profiler` 下拉框中选择设备。

关键点：Profiler 连接依赖 `Development Build`，Release 包不带 Profiler 连接能力；Wi-Fi 连接不稳定时优先用 USB。

### 1.3 常见报错

**Q: `"Unity-iPhone" requires a provisioning profile.`**

A: 在 Xcode 的 `Signing & Capabilities` 中配置 Team 与 Provisioning Profile，或勾选 `Automatically manage signing`。

### 1.4 添加 Link Flag

若链接阶段报错，可在 Xcode 的 `UnityFramework` target → `Build Settings` → `Linking - General` → `Other Linker Flags` 中追加 `-ld64`，强制使用 Xcode 的 ld64 链接器。

Unity 导出工程的默认值（不含 `-ld64`）：

```text
-weak_framework CoreMotion -weak-lSystem
```

出问题时是在这一行末尾**追加** `-ld64`：

```text
-weak_framework CoreMotion -weak-lSystem -ld64
```

（`-weak-lSystem` 中的是小写字母 `l`，表示弱链接 libSystem；截图中该字形与数字 `1`、大写 `I` 形近，勿写成 `-weak-ISystem`。）

## 2. MAC 通过 Wi-Fi 连接车机/台架无法连 Profiler

### 2.1 现象

Mac 与台架处于同一 Wi-Fi，但 Unity Profiler 直接填台架 IP 连不上。常见原因是台架的**防火墙/入站规则**拦住了 Profiler 端口（另一种情形才是进程把端口只绑在 `127.0.0.1` 上，没有对外暴露）。

### 2.2 解决：SSH 本地端口转发

**步骤 1：在台架上找到进程 PID**

```bash
ps -ef | grep navi
```

```text
root@adelegg:~# ps -ef| grep navi
 2672 navcn     0:49 {nav_main_thread} /opt/navroot/cn_amap/nv_main -platform-hmi-enable-signal-handlers 0 ...
```

**步骤 2：根据 PID 查端口占用**

```bash
netstat -tunple | grep 2672
```

```text
tcp  0  0 127.0.0.1:60001   0.0.0.0:*  LISTEN  6301  42188  2672/nv_main
tcp  0  0 0.0.0.0:55000     0.0.0.0:*  LISTEN  6301  41501  2672/nv_main
```

**步骤 3：确定端口**

上例中 `127.0.0.1:60001` 是只对本机可见的内部端口，Profiler 用的是另一个端口 `55000`——它绑在 `0.0.0.0:55000`，对所有网卡可见。因此连不上的原因通常不是"只绑了回环"，而是台架的**防火墙/入站规则**把这个端口拦住了。

**步骤 4：在 Mac 上建立端口转发**

新开一个终端，把本地的 55000 转发到车机的 55000：

```bash
ssh -L 55000:127.0.0.1:55000 root@192.168.230.1
```

**步骤 5：配置 Profiler**

在 Unity Profiler 的 `Active Profiler` 中选择 `Enter IP`，填入：

```text
127.0.0.1:55000
```

**步骤 6：开始连接**

如果仍连不上，在台架上刷新防火墙规则：

```bash
nft flush ruleset
```

### 2.3 原理

`ssh -L 本地端口:目标地址:目标端口` 会在本地监听一个端口，把连接通过 SSH 隧道转发到远端主机的目标地址。对 Unity 而言，它连的是"本机的 55000"，实际数据最终落到台架的 `127.0.0.1:55000`，从而绕开防火墙/入站规则对该端口的拦截。这条路径不依赖 Wi-Fi 是否允许入站，只要能 SSH 登录即可。

## 3. 平台图形 API 差异

### 3.1 深度约定与 reversed-Z

Unity 各平台的深度约定并不一致：

| 平台/API | NDC 深度 | 深度缓冲 | 说明 |
|---|---|---|---|
| OpenGL / OpenGL ES | `[-1, 1]` | `[0, 1]`（经 `glDepthRange`） | 近裁剪面 -1，远裁剪面 +1 |
| Direct3D 11/12 | `[0, 1]` | `[1, 0]`（reversed-Z） | 近 1 远 0 |
| Metal / Vulkan / Switch | `[0, 1]` | `[1, 0]`（reversed-Z） | 同上 |

宏定义（`UNITY_REVERSED_Z`、`UNITY_NEAR_CLIP_VALUE`）与 `_ZBufferParams` 的推导见《03_渲染设置与相机》§6.6，此处不再重复。

### 3.2 投影矩阵约定

| | OpenGL | D3D |
|---|---|---|
| 相机空间 Z | 视锥体在 -z 半轴，`Zv` 为**负** | 视锥体在 +z 半轴，`Zv` 为**正** |
| 近平面映射 | NDC `z = -1` | NDC `z = 0` |
| 远平面映射 | NDC `z = +1` | NDC `z = +1` |
| 矩阵存储 | 列主序 | 行主序 |
| 乘法形式 | `M * v`（矩阵在左） | `v * M`（向量在左） |

Unity 使用**列主序**，C# 中写作 `P * V * M * vector4`。透视投影矩阵是 D3D 矩阵的转置；但由于 DX 平台启用 `UNITY_REVERSED_Z`，实际投影矩阵并非简单转置，近/远平面的映射被交换。

### 3.3 纹理坐标方向

- OpenGL：U 向右、V 向上（原点左下）；
- DirectX：U 向右、V 向下（原点左上）；
- Unity 遵循 OpenGL 约定，纹理坐标原点在**左下角**。

这也是法线贴图切线空间手性需要按平台写入 `tangent.w` 的原因（详见 `02_Shader与材质.md` 第 9.3 节）。

### 3.4 原子操作支持

- **Metal 不支持对 Texture（`Texture2D` 等）的原子操作**，只支持对 `RWBuffer` 的原子操作。
- 需要在 Compute Shader 中对屏幕像素做原子累加时，要把二维坐标压成一维索引：

```hlsl
uint ScreenID2BufferIdx(uint2 id)
{
    return id.y * _RTSize.x + id.x;
}
```

### 3.5 纹理压缩格式与平台

同一张纹理在不同平台需要不同的压缩格式（ETC2 / ASTC / DXT / BC），这直接导致**不同平台的 AssetBundle 不能通用**。打包时执行的是目标平台的格式转换，进入包体的是已转换好的格式。详见 `04_序列化与资源管理.md` 第 7 节。

## 4. 日志与调试技巧

### 4.1 Debug.Log 与 print

- `Debug` 是 `UnityEngine` 下的静态类，`print` 是 `MonoBehaviour` 的成员方法。
- 因此 `print` 必须写在继承自 `MonoBehaviour` 的类里，`Debug.Log` 任意位置可用。
- 两者输出等价，`print` 内部就是 `Debug.Log`。

### 4.2 FrameDebugger 的两个坑

**（1）某个 Pass 没显示，但它的 Clear 生效了**

SRP 中每个 Pass 可自主配置执行前是否 Clear 相关 RT。FrameDebugger 中没有出现某个 Pass，一般是因为该 Pass 的对象都被过滤了（没有要画的东西），但**它配置的 Clear 依然会被执行**——clear depth / clear color 仍然发生。

例如下图中的 `Clear (Depth)` 并不是 `CarOnlyPass` 配置的，而是它前面那个 Pass（截图中为 `TaaPass`）配置的；只是因为该 Pass 没有要画的对象，所以没有显示出来。（原文此处写作 `AfterTimeDomainFilterPass`，截图中 `Clear (Depth)` 的前一项是 `TaaPass`，已按图更正。）

**（2）FrameDebugger 闪烁**

在 `sandbox_artprj` 中遇到 FrameDebugger 闪烁，解决办法：在 Hierarchy 中搜索 `Directional Light`，去掉 `Shadow Generator` 组件。

### 4.3 RenderDoc 集成

在 Scene 或 Game 窗口的标题栏**右键**，会出现 `Load RenderDoc` 选项，加载后即可抓帧。

### 4.4 花屏问题排查

**可能原因：相机的 `clearFlag` 没有设置。**

Unity 每个渲染帧开始时**不会自动清空**颜色缓冲区和深度缓冲区，清空与否完全由相机的 `clearFlag` 决定。

因此必须满足：

- 至少有一个相机的 `clearFlag` 设为 `SolidColor` 或 `Skybox`；
- 该相机的 `depth` 必须是所有相机中**最小**的（depth 最小的相机最先渲染）。

否则当前帧会在上一帧的结果上继续绘制，表现为花屏/拖影。

各 `ClearFlag` 的实际行为：

| ClearFlag | 颜色缓冲区 | 深度缓冲区 |
|---|---|---|
| `SkyBox` | 清除，随后绘制 skyBox | 清除 |
| `SolidColor` | 清除，设置为 BackGround 颜色 | 清除 |
| `DepthOnly` | 不清除（保留原内容） | 清除 |
| `Nothing` | 不清除 | 不清除 |

注意 `SkyBox` / `SolidColor` 不只是清颜色，**也会清深度**；只有 `DepthOnly` 只清深度，`Nothing` 两者都不清。误以为 `SolidColor` 不动深度，就会得出"SolidColor 相机不清深度也没关系"的错误结论——而深度未清正是花屏/拖影的典型成因。

### 4.5 多边形被裁剪的排查

- 当 cube 的侧边到相机的距离小于近裁剪面距离时，会出现多边形裁剪效果。
- 当 cube 的某个侧面完全位于近裁剪面之后，整个面会被裁掉。此时"什么都没画出来"还有一个额外原因：Shader 的 `Cull` 默认为 `Cull Back`，对相机来说最远的面是背面朝向相机的，无论怎么前后移动都不会被画出来。

### 4.6 用深度图模拟 ZTest

可以用"采样深度图 + 与当前像素深度比较 + `clip`"的方式模拟 ZTest，用于自定义深度测试逻辑：

<img src="../../技术笔记/assets/WEBRESOURCEb4f84dc6c7c6e1e1671cecdfceb444dd.png" width="783" height="382">

图中的 `ClipPixel` 是一个 Custom Function 节点（Type 选 `String`），其 Body 为：

```hlsl
oColor = iColor;
clip(SceneDepth - PixelDepth);
```

节点接口与连线：

| 项 | 内容 |
|---|---|
| Inputs | `PixelDepth`（Float）、`SceneDepth`（Float）、`iColor`（Vector4） |
| Outputs | `oColor`（Vector4） |
| `PixelDepth` 来源 | `Screen Position`（Mode = `Raw`）→ `Swizzle`（Mask = `w`）取屏幕深度 |
| `SceneDepth` 来源 | `Scene Depth` 节点（Sampling = `Eye`），UV 用 `Default` 的 `UV(4)` |
| `iColor` 来源 | `Vector4`（X=1, Y=1, Z=0, W=1） |

### 4.7 换材质后 Pass 不生效

现象：使用新材质重画一遍 GameObject 时，不移动一次对象，Pass 就不生效。

排查方向：材质/渲染状态的变更没有触发重建，或该对象被前一步的剔除/缓存逻辑跳过。实际处理方式是先移动一次对象强制刷新（**这是一个 workaround，不是根因结论，待核实**）。

### 4.8 像素级着色时的坐标精度

想在像素着色器里按屏幕坐标给单个像素着色时，直接用 `i.positionCS.x == 700` 判断会全部为 `false`。

```hlsl
if (i.positionCS.x == 700.5f && i.positionCS.y == 700.5f)
{
    color = float4(0, 0, 0, 1);
}
```

结论：`positionCS.xy` 的范围是 `[0.5, width - 1 + 0.5]`，即整型像素中心偏移 0.5。这与 `LOAD_TEXTURE2D` 期望的 `[0, width-1]` 正好差一个 `floor`：

```hlsl
LOAD_TEXTURE2D(_MainTex, positionCS.xy);          // 隐式转换
LOAD_TEXTURE2D(_MainTex, (int2)positionCS.xy);    // 等价于 floor
```

### 4.9 Compute Shader 屏幕坐标验证

```hlsl
[numthreads(8, 8, 1)]
void CSMain(uint3 id : SV_DispatchThreadID)
{
    uint width, height;
    _Result.GetDimensions(width, height);
    float2 uv = (id.xy + 0.5f) / float2(width, height);
    _Result[id.xy] = float4(uv.x, uv.y, 0, 1);
}
```

输出可见：原点在左下角，`id.x` 向右增长，`id.y` 向上增长。

## 5. 调试流程小结

1. **先隔离**：空工程验证版本/工具链，避免项目配置干扰。
2. **再连通道**：iOS 用 USB + Development Build；远端设备用 SSH 端口转发。
3. **再分平台**：深度、UV、原子操作、压缩格式的差异优先怀疑平台约定，而不是算法。
4. **最后看帧**：FrameDebugger 确认 Pass 是否执行、Clear 是否发生；RenderDoc 抓具体 draw call。
