# Unity 序列化与资源管理

> 本文整合 Unity 序列化规则、ScriptableObject、可空类型与序列化的关系，以及资源加载/释放、RenderTexture 生命周期与纹理压缩打包策略。

## 1. 序列化与持久化不是一回事

| 概念 | 定义 | 侧重点 |
|---|---|---|
| 序列化 | 将对象转换成某种格式（二进制、JSON、XML、CSV 等），供下一步处理 | 解决对象的**传输**问题 |
| 持久化 | 将内存数据以某种方式（数据库、文件）保存到外存，供以后使用 | 解决对象的**存储**问题 |

在 Unity 语境里说"序列化"，通常指把 Inspector 中可见的字段写进 `.asset` / `.prefab` / `.unity` / `.mat` 等文件，并在加载时还原。它同时承担了持久化的职责，因此两个概念容易混。

**静态（`static`）、常量（`const`）、只读（`readonly`）的变量，以及抽象类，都不能被序列化。**（抽象类的限制针对经典字段序列化——它无法实例化抽象类型；需要多态引用时要配合第 2.5 节的 `[SerializeReference]`。）

## 2. Unity 序列化规则

Unity 的基本判断是：**在没有自定义 Inspector 的情况下，所有显示在 Inspector 中的字段都同时具备序列化能力**。反过来也成立——你在 Inspector 里改了什么，保存时就会写进文件。

### 2.1 可被序列化的声明方式

**（1）public 字段**

不加任何 Attribute 时，`public` 字段默认被序列化：

```csharp
public int MaxExp;
```

**（2）[SerializeField]**

强制 Unity 序列化一个私有/受保护字段，并且它同样会显示在 Inspector 中：

```csharp
[SerializeField]
protected int foobar = 0;

[SerializeField]
private Button btn1;   // UGUI 中常见写法
```

**（3）[System.Serializable] 修饰自定义 class / struct**

不从 `MonoBehaviour` 派生的普通类，默认不会被识别为可序列化类型，加 `[System.Serializable]` 后才会注册：

```csharp
[System.Serializable]
public class FooBar
{
    public int foo = 5;
    public int bar = 10;
}
```

注意：`[Serializable]` 只对 `class`、`struct`、`enum`、`delegate` 生效，**不能用于属性（property）**。字段才参与序列化。

**（4）ScriptableObject**

见第 4 节。

### 2.2 不被序列化的情况

| 情况 | 说明 |
|---|---|
| `protected` / `private` / `internal` 字段 | 默认不序列化，除非加 `[SerializeField]` |
| `[System.NonSerialized]` | 显式排除，即使字段是 public |
| `readonly` / `const` / `static` | 无论其它设置如何，都不序列化 |
| `Dictionary<TKey, TValue>` | Unity 不支持，需要绕行 |
| 属性（property） | 不序列化，哪怕有 `[SerializeField]` |
| 可空值类型 `int?` | Unity 的序列化器不支持 `Nullable<T>` |

```csharp
[System.NonSerialized] public float foobar = 1.0f;
```

### 2.3 Dictionary 的序列化绕行

Unity 能序列化 `List<T>`，但不能序列化 `Dictionary<K,V>`。通用做法是序列化一个键值对列表，在 `Awake` 中构建字典：

```csharp
[System.Serializable]
public class NameToID
{
    public string name = "";
    public int ID = -1;
}

public List<NameToID> nameToIDList = new List<NameToID>();
private Dictionary<string, int> nameToID = new Dictionary<string, int>();

void Awake()
{
    foreach (NameToID info in nameToIDList)
        nameToID[info.name] = info.ID;

    nameToIDList = null; // 交给 GC，运行时不再需要
}
```

注意这里把 `nameToIDList` 置空后，如果之后又触发一次序列化（例如在编辑器中保存场景），列表内容会丢失。更稳妥的做法是保留 `nameToIDList` 作为可序列化字段，而让 `nameToID` 这个 `Dictionary` 保持 `private`——`private` 字段本就不参与序列化，它天然就是运行时缓存，不需要再加 `[NonSerialized]`；或者用 `ISerializationCallbackReceiver` 的 `OnBeforeSerialize` / `OnAfterDeserialize` 做双向同步。

### 2.4 Inspector 中的字段命名显示

Unity 会按大写字母拆分字段名，并把首字母强制大写显示：

```csharp
public int myFooBar = 0;
```

在 Inspector 中显示为 `My Foo Bar`。这也是为什么字段习惯用 camelCase。

### 2.5 序列化与 null

这是最容易踩的坑：**Unity 的序列化系统不保存引用类型字段的 `null`**。

- 对于一个 `class` 字段，序列化时若为 `null`，反序列化后 Unity 会用一个**默认构造的空对象**填充，而不是 `null`。因此"用 null 表示未配置"的写法在 Unity 里不可靠。
- 对于 `UnityEngine.Object` 派生类型的引用（`GameObject`、`Material`、`Texture` 等），`null` 会被存成 `{fileID: 0}`，反序列化读回来的就是**真正的 `null`**。所谓"假 null"是另一种情形：对象已被销毁、或引用的资源丢失（缺资源、被卸载），此时引用本身非空，`obj == null` 为 `true`，但 `(object)obj == null` 为 `false`，访问成员会抛 `MissingReferenceException`。
- 从 Unity 2019.3 起可用 `[SerializeReference]` 序列化**多态引用**，并且它**可以保存 null**；但它与 `UnityEngine.Object` 引用体系不兼容（待核实具体版本限制），普通资源引用仍应使用直接字段。

实践建议：

- 需要表达"没有"时，用 `bool hasX` 之类的显式标记，或使用可序列化的空对象 + 有效标志。
- 判断 `UnityEngine.Object` 是否为空统一用 `== null` / `if (obj)`，不要用 `ReferenceEquals`。
- 可空值类型 `int?` 无法序列化，需要改成 `int` + `bool hasValue`，或使用哨兵值。

### 2.6 序列化的边界

- Unity 的序列化器**不支持循环引用**（普通字段级别），会静默截断。
- 序列化深度有限（默认约 7 层，待核实具体版本），过深嵌套会被截断。
- 自定义 `class` 字段在 Inspector 中按值内联展开；同一个对象被两个字段引用时会被**复制成两份**，而不是共享引用（这正是需要 `ScriptableObject` 的原因之一）。

## 3. 可空类型与序列化的交叉点

C# 的 `int?` / `DateTime?`（`System.Nullable<T>`）语义、`?:`、`??`、`?.` 等运算符属于语言基础，统一放在 `05_CSharp与工程实践.md` 第 3 节，这里只讨论它与序列化的冲突。

**Unity 不能序列化 `Nullable<T>`**：`int?` 字段既不会显示在 Inspector，也不会被保存。需要"可选值"语义时改成显式标记：

```csharp
[SerializeField] private bool hasRadius;
[SerializeField] private float radius;
```

`T?` 只对值类型有意义；引用类型上的 `?`（C# 8 可空引用类型）是编译期注解，不改变运行时行为，也不影响 Unity 的序列化判定。

## 4. ScriptableObject

### 4.1 它要解决什么问题

`MonoBehaviour` 的痛点：

- 运行时修改的数据，退出后全部丢失；
- 每 `new` 一个对象就在内存里多一份实例，浪费空间；
- 很难在场景与项目之间共享数据。

`Prefab` 的痛点：

- 确实能跨场景共享，但容易被改乱——实例化一个 prefab 就能随意改数据；
- 只想存数据，却被迫带上一堆 Component。

### 4.2 ScriptableObject 的优点

- 内部继承自 `UnityEngine.Object`（`ScriptableObject` 本身就是 `UnityEngine.Object` 的子类），但**不必挂在 GameObject 上**作为 Component。
- 可以被序列化，并且自动获得类似 `MonoBehaviour` 的 Inspector 面板。
- 可以存成 `.asset` 文件，即**自定义资源类型**。Unity 内置的材质、贴图、音频本质上都是这种资源，ScriptableObject 让我们能定义自己的资源类型来存数据。
- 可以解决某些多态问题（基类字段持有不同子类实例；配合 `[SerializeReference]` 更灵活）。

### 4.3 它如何解决问题

- 数据存在 asset 里，退出运行不会被重置，改数值就是真的改了资源——和改材质、贴图的行为一致。
- 实例化时是**引用**而非复制。
- 可被任何场景引用，实现跨场景共享，也可跨项目共享。
- 没有多余的东西，例如多余的 Component。

### 4.4 缺点

- 回调很少，只有 `OnEnable`、`OnDisable`、`OnDestroy`（以及编辑器下的 `OnValidate`）。
- **一旦修改数据，就真的被修改了**：在编辑器里运行时改 ScriptableObject，退出 Play Mode 后修改依然保留（这点与场景对象不同）。需要临时数据时应 `Instantiate` 一份副本。

### 4.5 总结

ScriptableObject 的优缺点同源：它表现得就像一个材质/纹理类型的资源，位于 `Assets` 下。**同一个 asset 文件在内存中只有唯一一份实例、被所有引用者共享**；但"唯一"只到 asset 这一层——同一类型可以有多个 asset 文件，`Instantiate` 还能复制出额外副本。

```csharp
[CreateAssetMenu(fileName = "EnemyConfig", menuName = "Game/Enemy Config")]
public class EnemyConfig : ScriptableObject
{
    public float hp = 100f;
    public float speed = 3f;
    [SerializeField] private AnimationCurve difficulty;
}
```

## 5. 资源的加载

### 5.1 编辑器专用：AssetDatabase

```csharp
// 按路径精确加载
private static Material mat = (Material)AssetDatabase.LoadAssetAtPath(
    "Assets/res/test/materials/m_normal_visualization.mat", typeof(Material));

// 按条件搜索，返回 GUID 数组
string[] guids = AssetDatabase.FindAssets("t:Material Normal");
```

`AssetDatabase` 只在编辑器下可用，打包后不存在，不能出现在运行时逻辑里。

### 5.2 Resources.Load

```csharp
var prefab = Resources.Load<GameObject>("Prefabs/Enemy");
```

- 路径相对于任意 `Resources` 文件夹，不带扩展名。
- 找不到时返回 `null`。
- `Resources` 目录下的所有资源都会被打进包体，且**无法按目录/bundle 批量释放、也没有依赖自动卸载**，只能随 `UnloadUnusedAssets` 释放引用计数归零的对象；单个非 GameObject 资源可以用 `Resources.UnloadAsset(obj)` 显式卸载（见 5.3）。大型项目通常避免使用 `Resources`，改用 AssetBundle / Addressables。

### 5.3 加载后的所有权

- `Resources.Load` / `AssetBundle.LoadAsset` 返回的是**共享资源实例**。修改它会影响所有引用者，且修改会持久化到资源本身（编辑器下）。
- 需要独立副本时用 `Object.Instantiate`（GameObject/Component）或 `Object.Instantiate(scriptableObject)`。
- 场景切换（`LoadScene`）结束时会自动触发一次 `UnloadUnusedAssets`，未被引用的 `Resources` 资源随之释放；但仍有引用的不会释放。需要立即释放某个资源时可显式 `Resources.UnloadAsset(obj)`，或主动调用 `Resources.UnloadUnusedAssets()`。

## 6. 资源的释放

### 6.1 UnityEngine.Object 的生命周期

- C# 侧的对象是托管包装，真正的大块内存（纹理、Mesh、RT）在原生侧。
- `Destroy(obj)` 销毁原生对象并把托管包装标记为"假 null"；`DestroyImmediate` 立即销毁，仅建议在编辑器代码中使用。
- 托管包装本身要等 GC。频繁创建/销毁大资源会造成托管堆与原生堆的不同步，表现为内存曲线锯齿。

### 6.2 RenderTexture 的创建与销毁

**教训案例**：在 `ScriptableRenderPass` 的 `OnCameraSetup` 中申请 RT，却在 `OnCameraCleanup` 里把字段置 `null`：

```csharp
public override void OnCameraCleanup(CommandBuffer cmd)
{
    m_Handle = null;   // 错误：没有 Release，原内存无人引用也无人释放
}
```

结果：每帧 `OnCameraSetup` 都重新申请一块 RT，而旧 RT 的原生内存没有释放，内存一路涨到 177GB 后死机。**置 null 不等于释放。**

正确做法：

```csharp
public override void OnCameraCleanup(CommandBuffer cmd)
{
    cmd.ReleaseTemporaryRT(m_Handle.id);   // RenderTargetHandle 时代
}
```

```csharp
// RTHandle 时代
void Dispose()
{
    m_Handle?.Release();
}
```

`RenderTargetHandle` / `RTHandle` 的完整写法与 `GetTemporaryRT` 的池化细节见 `01_SRP与URP.md` 第七、八节。

### 6.3 频繁创建 RT：用池，不要 new

1. 需要频繁分配/销毁 RT 时，不要直接 `new RenderTexture(...)`，而要用 `cmd.GetTemporaryRT` / `RenderTexture.GetTemporary` + `ReleaseTemporary`。Unity 内部维护了一个池，可复用大小格式一致的 RT。
2. `GetTemporary` 内部会调用 `DiscardContents()`，这在 TBR/TBDR 架构的移动 GPU 上很重要：
   - 基于 Tile 的 GPU 上，RT 与 Tile 存储之间存在同步；
   - 往"有内容"的 RT 上绘制会触发这种同步；
   - `DiscardContents()` 告诉 GPU"已有内容不用管"，直接覆盖，避免同步开销。

TBR 的基本策略：

1. 对 CPU 提交的 DrawCall 只做顶点处理并暂存结果，直到必须刷新 FrameBuffer 才做光栅化；
2. 把 FrameBuffer 分成能被片上 SRAM 容纳的小块（Tile），逐块渲染后回拷到主存，降低主存带宽；
3. 频繁读写 FrameBuffer 的操作（逐像素读、写、查询）代价最高。

### 6.4 回读 RenderTexture

1. RT 的数据在 GPU 显存（服务端），回读到 CPU 用 `Texture2D.ReadPixels`。
2. **RT 与目标 `Texture2D` 的格式必须匹配**，否则回读失败或数据错误。
3. 回读是同步操作，会强制 CPU 等待 GPU，务必避免每帧执行。

```csharp
var tex = new Texture2D(rt.width, rt.height, TextureFormat.RGBA32, false);
RenderTexture.active = rt;
tex.ReadPixels(new Rect(0, 0, rt.width, rt.height), 0, 0);
tex.Apply();
RenderTexture.active = null;
```

## 7. 纹理压缩与打包

### 7.1 三个层次的概念

| 层次 | 例子 | 说明 |
|---|---|---|
| 文件格式 | JPG、PNG | 存储在硬盘上的格式，GPU 不能直接使用 |
| 纹理格式 | R8G8B8、A8R8G8B8、R5G6B5 | 能直接被 GPU 使用的未压缩格式 |
| 压缩纹理格式 | ETC1/ETC2、ASTC、DXT/BC | 硬件可直接采样的压缩格式 |

![](../../技术笔记/assets/WEBRESOURCEfa2f28610ccf0bca19929503b25e4b7f.png)

### 7.2 压缩纹理解决的问题

- 不需要在 CPU 解压，也不需要 GPU 对**整张图**解压；
- 解决带宽问题：CPU → GPU 的传输数据量显著降低；
- 降低包体：打进包里的已经是压缩格式；
- 降低内存与显存占用。

### 7.3 什么时候解码

以 ETC 为例，解码发生在**渲染阶段**，由 GPU 硬件实时完成：

1. 加载阶段：纹理以压缩格式从磁盘进入显存，**保持压缩状态**，不解压。
2. 渲染阶段：Shader 采样时，GPU 从显存读取压缩数据，**按需解码局部纹理块**（如 4×4 像素块），而不是一次性解压整张图。
3. 主流移动 GPU（Adreno、Mali、PowerVR）都有 ETC 解码单元，解码与渲染并行，延迟极低。

对比：PNG/JPG 这类非硬件压缩格式必须由 CPU 在加载时解压成 RGBA 再上传 GPU，内存占用高、加载慢。举例：1024×1024 的 ETC2 纹理约 0.5MB，解压成 RGBA8888 后约 4MB。（以上按不含 alpha 的 ETC2 RGB 计；带 alpha 的 ETC2 RGBA 为 1MB。）

ETC1 与 ETC2 的差异：

- ETC1：仅支持不透明纹理，OpenGL ES 2.0+ 广泛支持；
- ETC2：支持 Alpha 与更高质量，需要 OpenGL ES 3.0+ 或 Vulkan，解码机制相同。

ASTC 是另一种硬件压缩格式，机制类似，但块尺寸更灵活、压缩率更高。

### 7.4 打包流程

1. 资源导入时：解码 JPG/PNG 等文件格式；
2. 打 AssetBundle / 构建包体时：执行**目标平台对应的纹理格式转换**；
3. 最终进入包或 bundle 的是已转换好的格式。

这也解释了**为什么不同平台的 bundle 不能通用**：纹理格式、端序、Shader 变体都不同。跨平台复用 bundle 需要在打包时选择"不转换"或使用通用格式，代价是运行时转换开销。

## 8. 其他资源管理结论

- Unity 中**无法单独获取和采样 Stencil Buffer**，它通常随 depth-stencil attachment 一起使用；`RenderTextureDescriptor.depthStencilFormat` 同时指定 depth 与 stencil 的格式。可以设 `S8_UInt` 做 stencil-only（不带 depth）的 attachment，但平台支持有限，不宜依赖。
- `RenderBufferLoadAction` 决定渲染前如何处理 RT：`Clear` 清除、`DontCare` 跳过加载/清除（最快，但内容是脏的）、`Load` 保留原内容继续画。
- `RenderBufferStoreAction` 决定渲染后如何处理：`Store` 保存、`DontCare` 丢弃（省带宽）、`Resolve` 做 MSAA 解析、`StoreAndResolve` 两者都做。
- `RenderTargetIdentifier` 允许把颜色与深度合并到同一个句柄；URP 中 `RTHandle` 的默认做法是分别持有 color 与 depth 两个句柄，且 `desc.depthBufferBits` 设为 0。这是 URP 的约定而非 API 限制——`RTHandleSystem.Alloc` 本身带 `depthBufferBits` 参数，可以分配带 depth 的 `RTHandle`。
