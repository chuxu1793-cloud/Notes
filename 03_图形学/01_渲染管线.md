# 渲染管线：从三维场景到屏幕像素

> 本文梳理三维图形渲染显示的全过程：应用程序阶段、几何阶段、光栅化与逐片元操作，并对照 OpenGL 固定功能管线、URP 的渲染流程，最后落到一个软渲染器（SoftRender）的实现要点与顶点/片元着色器的职责划分。深度测试、Early-Z、Z 精度等可见性问题见《02_光栅化与深度可见性》；阴影见《05_阴影》。

## 管线总览

渲染管线（rendering pipeline）把三维场景转化为一幅二维图像：[应用程序阶段 Application] → [几何阶段 Geometry] → [光栅化 Rasterizer] → [帧缓冲 FrameBuffer] → [显示器]。

![](../../技术笔记/assets/BC0F5176053142629C25D4507CC6E03A.jpg)

![](../../技术笔记/assets/A3B269195FFB43FB84740904E53E933A.png)

图像中物体所处的位置与外形由几何数据和摄像机位置共同决定；物体的外表则由材质属性、光源、纹理与着色模型决定。

管线的本质是一串坐标空间变换，任何一段都可以用"空间 + 变换矩阵"来定位：

| 空间 | 说明 | 典型变换 |
|:--|:--|:--|
| Object / Model | 模型顶点原始坐标 | `M`（模型矩阵） |
| World | 场景统一坐标系 | `V`（视图矩阵） |
| View / Eye | 摄像机位于原点，视线沿 -Z（右手系） | `P`（投影矩阵） |
| Clip（齐次） | 4D 齐次坐标，尚未做透视除法 | 裁剪在此空间进行 |
| NDC | 透视除法后归一化 | 视口变换 |
| Window / Screen | 像素坐标 + 深度值 | 光栅化 |

## 应用程序阶段（Application）

运行在 CPU 上，能被开发者完全控制：

1. **准备场景数据**：加载 Mesh、Material、Shader、Texture（硬盘 → 内存 → 显存）；确定摄像机（位置、朝向、视锥体）；确定光源（位置、类型、参数）。
2. **裁剪与剔除**：视锥裁剪（frustum culling）、遮挡剔除（occlusion culling）；背面剔除在光栅化阶段按 winding 完成。
3. **计算模型视图矩阵**，以及投影矩阵、法线矩阵等。
4. **设置渲染状态（Render State）**。
5. **发起 DrawCall**。

### 渲染状态

渲染状态定义了"这批 mesh 将被怎样渲染"：

- 使用哪个顶点着色器 / 片元着色器；
- 使用哪张纹理、哪个材质；
- 开启哪些片段测试（scissor / alpha / stencil / depth）；
- 是否开启混合（blending）、混合方程、深度写入掩码、剔除模式等。

OpenGL 是状态机：如果没有改变状态，那么随后所有 mesh 都沿用同一套渲染状态。状态切换带来驱动校验与命令记录开销（D3D9 还会触发批处理刷新）；现代 API 应复用/预建 PSO、描述符集，因此**按状态排序**仍是减少驱动开销的常规手段。

### 渲染顺序

- **不透明物体**：从前向后（front-to-back）绘制，配合 Early-Z 可以大幅减少 overdraw；同一批次内按材质/Shader/纹理排序以减少状态切换。
- **透明物体**：从后向前（back-to-front）绘制，关闭深度写入（`ZWrite Off`）、保留深度测试，才能正确混合。
- 深度预通道（Pre-Z / depth prepass）可以先把不透明物体的深度写入，再正常着色，从而让后续 pass 的深度测试尽量早地剔除片元。

### 剔除与可见性

视锥剔除在 CPU 侧用包围体（AABB / OBB / 包围球）与视锥平面做快速测试；背面剔除在光栅化前由图元顶点的环绕方向（winding）决定；遮挡剔除可以用硬件遮挡查询（Occlusion Query）或软件 HZB。Occlusion Query 与 OBB 的细节见《02_光栅化与深度可见性》。

## 几何阶段（Geometry）

几何阶段负责与每个渲染图元打交道，进行逐顶点、逐多边形的操作。它的核心任务是把顶点坐标变换到"带深度的屏幕空间"，再交给光栅器。可细分为：模型视图变换 → 顶点着色 →（曲面细分）→（几何着色）→ 投影 → 裁剪 → 屏幕映射。

![](../../技术笔记/assets/91DFF93E6E0242FB980711F0A610E1BD.png)

### 模型变换与视图变换

- **模型变换**：模型空间 → 世界空间。
- **视图变换**：世界空间 → 眼空间（摄像机在原点）。OpenGL 约定摄像机看向 -Z，因此视图空间中的 z 通常为负值，深度 $d=-z_v>0$。

两者常合并为 modelview 矩阵，统称模型视图变换。

![](../../技术笔记/assets/B9039ED435BA403581398B1334C5883F.png)

### 顶点着色器（VS）

主要职责是修改/生成顶点属性：

- 位置：用 MVP（或 model-view + projection）把顶点变换到**裁剪空间**；
- 颜色：逐顶点光照（可选）；
- UV：纹理坐标变换。

处理单元是顶点：每输入一个顶点就执行一次 VS。VS 不能创建或销毁顶点，也拿不到顶点与顶点之间的关系。输入通常是变换矩阵 + 顶点属性；输出是裁剪空间坐标及其携带的其它属性（颜色、UV、法线等）。

**关键约束：VS 输出的是齐次裁剪坐标，绝不能在这里做透视除法**（原因见下文"为什么不能在 VS 中做透视除法"）。

### 曲面细分着色器（Tessellation）

用于细分图元，分三个阶段：

1. **Control Shader**：控制后续阶段的初始化，例如细分程度（可编程）；
2. **Tessellator**：处理 Control 阶段的输出，细化 patch 数据（不可编程）；
3. **Evaluation Shader**：输入 patch 数据，输出 VS 应输出的数据，但是批量的（可编程）。

### 几何着色器（GS）

输入是 1 个图元，输出是 $N$ 个图元（$N\ge 0$），因此可以增删顶点/图元：可在 GPU 上"长草"、生成毛发、生成火花等粒子特效。

> 工程注意：GS 在很多驱动上实现代价较高（历史上部分实现落在 CPU/驱动侧），对流水线吞吐影响大，实际效能常常很低。能用 VS + 实例化/计算着色器代替时优先替代。

### 投影

分为透视投影与正交投影，作用是在眼空间把三维点投影到二维平面：D3D 的像平面取 $z=1.0$，OpenGL 取 $z=-1.0$。这是"单位距离像平面"的图示约定，不要与近裁剪面混为一谈——近裁剪面在 $z=\pm n$，只有 $n=1$ 时才与 $\pm1$ 重合。

![](../../技术笔记/assets/E097C309B8DD4C82AFC4AC7DC1447717.png)

上图为眼空间；D3D 使用左手系，OpenGL 使用右手系。

![](../../技术笔记/assets/9464CF24273A430DBE56A2188CFEB2C7.jpg)

投影之后再做透视除法，才得到归一化设备坐标（NDC）：

- x、y 归一化到 $[-1,1]$；
- z 归一化：D3D 为 $[0,1]$，OpenGL 为 $[-1,1]$；近裁剪面对应最小深度，远裁剪面对应最大深度。

> 注意区分：[投影变换] 输出的是齐次裁剪坐标；[透视除法 $/w$] 之后才得到 NDC；[视口变换] 再把 NDC 的 z 映射到 $[0,1]$ 的窗口深度。

### 裁剪（Clipping）

将不在摄像机视野内的顶点/图元裁掉，多边形裁剪会产生新顶点，新顶点的颜色、UV 等属性需要按参数 $t$ 插值。

裁剪在**齐次裁剪空间**中完成，判据是对每个裁剪平面（$x=\pm w,\ y=\pm w,\ z=\pm w$ 加用户自定义平面）做测试，而不是先除 $w$ 再判断——因为 $w$ 可能为负或为 0，先除法会破坏线性性并引入除零。

![](../../技术笔记/assets/5D7C27BACF2A463EADA8852EFBEC46C0.png)

### 图元装配（Primitive Assembly）

顶点着色器处理完顶点后进入图元装配：按连接关系（点、线、三角形）把顶点组装成图元，随后执行**裁剪、透视除法、视口变换**。

> 表述统一：图元装配 → 裁剪 → 透视除法 → 视口变换，四者都属于"从裁剪空间到窗口空间"的固定功能部分。原文有一处把顺序写成"裁剪、透视分割、Viewport 变换"，与上述一致；但不要把透视除法放到 NDC 之后。

### 屏幕映射与视口

屏幕映射把 NDC 的 x、y 从 $[-1,1]$ 变换到屏幕/视口坐标，z 映射到深度范围：

$$
\begin{aligned}
x_w &= (x_{ndc}+1)\cdot\frac{W}{2} + x_0 \\
y_w &= (y_{ndc}+1)\cdot\frac{H}{2} + y_0 \\
z_w &= \frac{z_{ndc}+1}{2}\,(f-n) + n
\end{aligned}
$$

其中 $(x_0,y_0,W,H)$ 是视口矩形，$[n,f]$ 是深度范围（默认 $[0,1]$，可由 `glDepthRange` 修改）。

- D3D：屏幕左上角为原点，x 向右，y 向下；
- OpenGL：屏幕左下角为原点，x 向右，y 向上。

![](../../技术笔记/assets/EF1308017BAA41DEA49559FF6675352B.png)

**视口（Viewport）**就是最终渲染结果的输出目的地，是一个以像素为单位的矩形区域；视口坐标系原点位于窗口客户区左下角，x 向右为正，y 向上为正（与 Windows 的窗口坐标系不同）。OpenGL 用 `glViewport(x, y, width, height)` 设置；初始化窗口时默认铺满整个客户区。

视口本身也是 OpenGL 维护的状态变量之一，一次渲染默认只能用当前视口输出（GL 4.1+ / D3D11+ 支持 viewport array，可用 `glViewportIndexedf` 等为同一次渲染指定多个视口）；但一帧内可以做任意多次渲染，多个视口的结果拼成完整画面（分屏）。

## 光栅化（Rasterization）

光栅化要决定"每个图元覆盖了哪些像素"，并对顶点属性做插值（深度、法线、UV、颜色……）产生片元。

![](../../技术笔记/assets/7D6AB8612F0D4F8BBF028DED2D7C8B0B.png)

### 三角形设置与三角形遍历

- **三角形设置（triangle setup）**：由三个顶点计算出三角形边所在直线、包围盒等，为扫描做准备；
- **三角形遍历（triangle traversal / scan conversion）**：扫描三角形覆盖的像素，用重心坐标判断像素中心是否在三角形内，并插值出片元属性。

### 三角形的分类

按形状可分为平底（bottom-flat）、平顶（top-flat）与任意三角形；经典的软光栅器先把任意三角形按 y 排序，在中间顶点处水平切一刀，拆成一个平顶 + 一个平底三角形分别扫描。

![](../../技术笔记/assets/B53E11A96E3C403E8D5C6D30FC21E156.png)

![](../../技术笔记/assets/87EEF1F7C83A43E8AF2E896242141DBB.png)

### 像素中心与填充规则

光栅化不是看像素"方块"是否与三角形相交，而是看**像素中心**（整数坐标 + 0.5）是否落在三角形内；落在边上的像素用 top-left rule 保证共享边只被填充一次（不会重复着色，也不会漏缝）。

软渲染中常见的取整写法：

```c
// 采用 y 轴向上的屏幕坐标系（yMax > yMin）
xMin_int = ceil(xMin - 0.5);     // 左边界
xMax_int = ceil(xMax - 1.5);     // 右边界，等价于 ceil(xMax - 0.5) - 1
yMin_int = ceil(yMin - 0.5);     // 下边界
yMax_int = ceil(yMax - 1.5);     // 上边界，等价于 ceil(yMax - 0.5) - 1
```

即 x/y 的**最小边界**（左、下）取"第一个中心在内部"的像素，**最大边界**（右、上）减 1，是因为区间上端是开区间——写成 $-1.5$ 只是把"减一"合进了同一个 `ceil` 里。边界变量用 min/max 命名、并先声明 y 轴方向，就不会因为屏幕 y 轴朝上还是朝下而把 $-0.5$ 与 $-1.5$ 这两档用反。

### 属性插值：为什么必须透视校正

屏幕空间中的属性插值不是线性的：透视投影后，需要先把每个顶点属性除以 $w_i$——$a/w$ 与 $1/w$ 在屏幕空间才是线性的。注意属性**本身**对屏幕坐标的变化率并不与 $1/w$ 成正比，它取决于表面朝向（正对相机的平面约为 $\propto w$，掠射的地面约为 $\propto w^2/h$），所以不能直接线性插值 $a$。硬件用下面的方式做**透视校正插值**（$\lambda_i$ 为重心坐标，$a_i$ 为顶点属性）：

$$
a = \frac{\sum_i \lambda_i\, a_i / w_i}{\sum_i \lambda_i / w_i}
$$

实现上等价于：对 $a_i/w_i$ 与 $1/w_i$ 分别做屏幕空间线性插值，再相除。深度 $z_{ndc}$ 则由三个顶点的 $z_{ndc}$ 直接用重心坐标线性插值（它在屏幕空间本就是线性的）。

## 逐片元操作（Per-Fragment Operations / 像素测试）

片元是"准像素"：屏幕上一个整数坐标可以有多个前后堆叠的片元。逐片元操作通过一系列测试淘汰不合格片元，并决定如何写入帧缓冲。

![](../../技术笔记/assets/62A3F3E8B322476690D4CC40E466AA87.png)

![](../../技术笔记/assets/WEBRESOURCEab44e22afef14da70ccea5bbb11a3c00.png)

典型顺序（不同 API 略有差异，但顺序固定）：

1. **Scissor Test**：片元是否在用户指定的裁剪矩形内；
2. **Alpha Test**（可选，现代管线中多用 `clip()`/discard 实现）：比较片元 alpha 与参考值；
3. **Stencil Test**：用模板缓冲做条件判断，并按 stencil op 更新模板值；
4. **Depth Test**：比较片元深度与深度缓冲；
5. **Blending**：与颜色缓冲中已有颜色做 Alpha 混合；
6. **写掩码**：按 RGBA/深度写掩码决定是否真正写入。

只有通过所有测试的片元，才会与颜色缓冲区中已存在的像素颜色混合并写入。

- **Alpha 测试**：大量片元会在此被丢弃，因此对含大量透明物体的场景能显著提升性能；但它是固定管线遗留功能，GL 3.1 core+ / D3D10+ 已移除该状态（改用 `discard`），且 `discard` 会让该 draw 失去 Early-Z，所以并非无条件更快。
- **模板测试**：8 位模板缓冲的取值范围是 $[0,255]$ 的整数，初值是清屏时设置的值。注意：**若关闭深度测试，则深度测试恒通过**；模板缓冲只参与测试，片元本身没有"模板值"。
- **深度测试**：NDC z 区间 D3D 为 $[0,1]$、OpenGL 为 $[-1,1]$（视口变换后统一为窗口深度 $[0,1]$，两者的深度缓冲都是 $[0,1]$）；位数越多精度越高，初值为清屏时设置的值。关闭深度测试意味着所有片元恒通过。
- **使能与掩码是两件事**：使能控制"是否做测试"（不做则直接通过），掩码控制"通过后是否写入"。

### 绘制物体轮廓（模板缓冲的典型用法）

用 stencil buffer 描边的固定套路：

1. 第一遍绘制物体，**写入**模板：清模板为 0 → 开启模板写入 → 绘制物体，物体覆盖处模板变为 1；
2. 第二遍绘制放大的物体，**关闭**模板写入、关闭深度测试，只让模板值不等于 1 的像素着色（即物体外的一圈），得到轮廓。

同一思路也可用于"只让被遮挡部分显示 X 光效果"等。

## 帧缓冲与显示

![](../../技术笔记/assets/3440CFD0E49D4CD2BA8C06968F3498A9.png)

- **单缓冲**：直接画到屏幕，能看到中间绘制过程，会闪烁，一般只用于静态图像。
- **双缓冲**：在后台缓冲（backbuffer）离屏绘制，完成后通过交换指令（D3D 的 `Present`、OpenGL 的 `SwapBuffers`）与前台缓冲交换，一帧完整画面才上屏。交换只是指针互换，非常快。
- **三重缓冲**：一个前台 + 两个后台，可缓解 VSync 下的卡顿，但会带来约一帧的延迟。

```c
// OpenGL 单缓冲
glutInitDisplayMode(GLUT_SINGLE | GLUT_RGB);
glFlush();
// OpenGL 双缓冲
glutInitDisplayMode(GLUT_DOUBLE | GLUT_RGB);
glutSwapBuffers();
```

### VSync 与撕裂

CRT/液晶逐行扫描一帧后回到起点，硬件用 HSync（换行）与 VSync（换帧）信号同步。显示器以固定频率刷新，VSync 就是这个信号产生的频率。

若 GPU 写入速度快于显示器刷新（例如 FPS=100、刷新 75Hz），一个刷新周期内会写入 $4/3$ 帧，下一帧的 1/3 覆盖在前一帧之上，出现**撕裂（tearing）**。

![](../../技术笔记/assets/6932C941CFF54E7890E4977D0EAF6E18.jpg)

![](../../技术笔记/assets/609417DB9820468A98FDBF19DAF2D0E8.png)

开启 VSync 后，FPS 被钳制到刷新率，减少无用功、降低功耗，但会引入输入延迟；若 FPS 低于刷新率，帧率会跌到刷新率的整数分之一，卡顿（stutter）加剧。三重缓冲可以缓解。

## OpenGL 流水线与固定功能管线

![](../../技术笔记/assets/536A0B4C6CED402A9382289707463355.png)

> 图上附注（逐字转写）：其实上 Fragments 英文字段就是"片段"的意思，在图形学或者 GPU 渲染管线里被认定为三角面光栅化得到的片段。图形学或者 GPU 渲染管线里光栅化后得到的称为片段而非像素，是因为片段是还没经过 Z 缓存测试（Z 缓存画家算法）的，而像素是片段经过 Z 缓存测试最终要输出到后置缓存的。但是请注意的，D3D 管线里 Fragment 和 Pixel 貌似统一用 Pixel 表示，这就是为什么 D3D11 是 PixelShader 而 OpenGL 为 FragmentShader，也就是说 OpenGL 和 GPU 渲染管线的 FragmentShader（片段着色器）等同于 D3D11 的像素着色器（PixelShader）。

![](../../技术笔记/assets/B00A9B310856460B8697E5566F1739D7.png)

### OpenGL Context

调用任何 OpenGL 函数之前必须已创建 OpenGL Context，它保存了状态变量以及与渲染相关的信息。创建 Context 通常与创建窗口一起完成，窗口带有默认帧缓冲（Default Frame Buffer），OpenGL 通过它把内容显示到屏幕（GLUT 创建窗口时已顺带创建）。

### 固定功能管线的各阶段

**顶点处理**：顶点齐次坐标变换 + 逐顶点光照（固定管线只有逐顶点光照）。

- 若光照关闭，顶点颜色直接取当前颜色（`glColor()`）；
- 若开启，按当前材质（`glMaterial()`，可分正/背面）与法向量（`glNormal()`）计算环境光、漫反射、高光并叠加；
- 光照分正背面进行，处理完每个顶点有两个颜色（对应 `gl_FrontColor` / `gl_BackColor`）：正面用正面材质与法线 $n$，背面用背面材质与 $-n$；
- 若关闭双面光照，只算正面并把背面颜色设为与正面相同（**单面光照不等于只照亮正面**）；
- 光栅化时按顶点环绕方向判定正背面，据此选择用哪一组颜色做插值；
- 逐顶点光照类似 Gouraud 模型，区别于逐片元光照（Phong：先插值法线再算光照，需片元着色器）；
- 光照计算涉及的距离、内积都在相机坐标系中进行；`glGetLightfv(GL_LIGHT0, GL_POSITION, ...)` 返回的光源位置也是观察坐标——因为按顶点变换的实际意义，相机空间仍是直角坐标系，而裁剪空间不一定。

**图元装配与裁剪**：顶点处理后得到裁剪坐标系的顶点，先按连接关系装配成图元，再裁剪；多边形裁剪可能产生新顶点，其颜色、UV 需插值；除默认的 6 个裁剪面外可指定额外裁剪面；裁剪之后是透视除法，再之后是视口变换（同时把 z 缩放到 `[0,1]` 成为深度值，默认越小越近，可用 `glDepthRange` 修改）；之后的图元进入光栅化。上述流程之间还可以插入几何着色器。

**光栅化**：

1. 经过视口变换，光栅化在二维（附带深度）的屏幕坐标系中进行；
2. 两个任务：(a) 确定图元覆盖哪些整数坐标的"小方块"（此时还只能叫片元候选）；(b) 确定这些小方块的深度与颜色（由顶点插值得到）；
3. 填充前要先判定多边形是 front-facing 还是 back-facing（点、线只有正面），该结果决定插值用哪组颜色；若 `glIsEnabled(GL_CULL_FACE)` 为真，则与 `glCullFace(GL_FRONT/BACK)` 指定方向相同的图元直接被剔除；
4. 除填充外，也可只画边或只画点（`glPolygonMode`）；
5. 最复杂的纹理处理在光栅化阶段进行：每个片元要算出纹理坐标去索引纹素，看似简单，出错时效果非常意外；
6. 之后可由片元着色器代替纹理、雾等固定操作，并做逐片元光照等更多计算。

**逐片元处理**：见上一节。补充：缓冲区"使能"与"屏蔽"相互独立——使能决定是否测试（不测试则直接通过），屏蔽决定通过后是否更新缓冲区。

## URP Pipeline

![](../../技术笔记/assets/5A2F5E57BC6F42D9AB50BCB2280E24E3.png)

图中的层级结构与 Pass 顺序（逐字转写）：

```text
Universal Render Pipeline
└─ beginFrameRendering
   ├─ RenderCameraStack
   │  ├─ beginCameraRendering
   │  │  └─ RenderSingleCamera(Base Camera)
   │  │     ├─ Clear color + depth + stencil
   │  │     ├─ MainLight & AdditionalLights ShadowCasterPass
   │  │     ├─ DepthOnlyPass (if require depth texture)
   │  │     ├─ DrawObjectsPass (Opaque)
   │  │     ├─ CopyDepthPass (if require depth texture)
   │  │     ├─ CopyColorPass (if require opaque texture)
   │  │     ├─ DrawSkyboxPass
   │  │     ├─ DrawObjectsPass (Transparent)
   │  │     ├─ PostProcessPass (if any post process)
   │  │     └─ Renderer.Execute
   │  ├─ endCameraRendering
   │  ├─ ……
   │  ├─ beginCameraRendering
   │  │  └─ RenderSingleCamera(Overlay Camera)
   │  │     ├─ Clear depth + stencil
   │  │     ├─ ……
   │  │     └─ FinalPostProcessPass (if FXAA or others) or FinalBlitPass (if needed)
   │  └─ endCameraRendering
   └─ endFrameRendering
```

> **更正注（原图有误，转写保留原样）**：上面的 Pass 顺序忠实转写自原图，但原图把 CopyDepth / CopyColor 画在了 Skybox 之前，与 URP 实际顺序不符——URP 中 `m_DrawSkyboxPass` 的事件点是 `BeforeRenderingSkybox`、`m_CopyColorPass` 是 `AfterRenderingSkybox`。正确顺序应为 **Opaque → Skybox → CopyDepth / CopyColor → Transparent**。

URP 把一次相机渲染拆成可配置的 `ScriptableRenderer` 阶段：设置（`Setup`，剔除、排序、决定 RenderPass 列表）→ 若干 Pass（ShadowCaster、DepthPrepass、Opaque、Skybox、Transparent、PostProcess 等）→ 提交（`FinishRendering`）。

从本文视角只需要记住三点（Unity 侧的细节归 Unity 主题的笔记）：

1. URP 的**不透明物体默认从前向后排序**，与 Early-Z 配合；
2. **主光阴影是单独一个 ShadowCaster Pass**，把场景渲染进 shadowmap（见《05_阴影》）；
3. 每次 DrawCall 之前绑定的是"渲染状态集合"（Shader/Pass、混合、深度、模板、剔除），切换集合才是真正的开销来源。

## 渲染器结构

软渲染器/引擎的典型对象组织（两份原始结构图）：

![](../../技术笔记/assets/8AED034CC12E466691E4C476C3037F1E.png)

`renderer` → 多个 `render`（渲染过程/pass）→ 引用 `scene` → `model` → `node`（场景树）→ `drawable`（可绘制对象）→ 共享 `program`（着色器程序）。

![](../../技术笔记/assets/DDB3AAA007B74983A6FC2447F05B8E5E.jpg)

`Window` / `Win32` / `Framebuffer`；`Scene` / `Camera` / `Manipulator`；`Render` 内含 `VS`、`FS`、`Clipper`、`Rasterize`，并持有 `Varying`、`Uniform`、`Attribute`；具体渲染策略派生为 `PhongRenderer`、`SkyboxRenderer`；`Model` 由 `Mesh`、`Material`、`Transform` 组成，`Material` 持有 `Texture`。

这套划分对应图形管线的四个可变点：**几何数据的来源（Mesh/Transform）、着色程序的输入（Attribute/Uniform/Varying）、逐图元与逐片元的固定功能（Clipper/Rasterize）、输出目标（Framebuffer）**。把固定功能部分独立出来，替换 `Renderer` 子类就能实现不同的着色模型（Phong / Skybox）。

## SoftRender 实现要点

原始笔记只留下了几条"踩坑"记录，它们恰好是软渲染最容易出错的四个点：

```
！ 注意原始顶点数据不可修改；
！ += 运算符重载出错；
！ 光栅化规则，浮点数转整数规则；
```

逐条展开：

1. **不要原地修改顶点数据**。顶点数组是"输入"，MVP 变换应当输出到独立的 `varying`/`clipPos` 数组中。就地覆盖会破坏同一 mesh 的多次绘制（阴影 pass、多光源 pass），也让"模型空间坐标"这一信息永久丢失（法线变换、贴花投影都需要它）。
2. **`+=` 重载的坑**。向量/颜色类型重载 `+=` 时如果返回引用或者混用了不同精度/不同分量数（`float3 += float4`），会静默截断或重复累加。着色器里的累加（光照求和、属性插值）必须明确"左值类型 = 右值类型"。
3. **光栅化取整规则**。浮点边界转整数时要用统一的规则（见上文"像素中心与填充规则"），并且**四个边界必须用同一套约定**，否则会出现裂缝（漏一个像素）或重复着色（一个像素被画两次）。
4. **透视除法与裁剪的顺序**。软渲染里必须严格按"裁剪空间裁剪 → 透视除法 → 视口变换 → 光栅化"执行。

### 软渲染中的裁剪

在齐次裁剪空间对三角形做 Sutherland–Hodgman 裁剪，逐个平面测试 $w>0$ 且 $-w\le x,y,z\le w$：

- 三角形与平面相交时，按参数
$$
t=\frac{d_0}{d_0-d_1}
$$
在新顶点处线性插值所有顶点属性（位置、法线、UV、颜色），**包括 $w$**；
- 裁剪后三角形可能变成 3~4 个顶点（这是单个裁剪面的情形）；对 6 个裁剪面依次裁剪理论上最多 9 个顶点，都需要重新三角化；
- 因为插值发生在齐次空间（线性空间），所以插值结果正确；若先除 $w$ 再裁剪，插值就发生在非线性空间，UV 与深度都会错。

### 为什么不能在 VS 中做透视除法

一句话：**为了保证插值的正确性**。

管线中的线性空间只有四个——物体空间、世界空间、相机空间、齐次（裁剪）空间。透视除法之后进入 NDC，NDC 对屏幕坐标是非线性的（只有 $a/w$ 与 $1/w$ 保持线性，属性本身不是），此时直接插值会得到错误结果。

因此想拿到片段的屏幕 UV、深度，顶点着色器必须输出**齐次空间下的线性坐标**，由光栅化器用 $1/w$ 做透视校正插值：

- **屏幕 UV**：`ComputeScreenPos(clipPos)` 把齐次坐标的 xy 从 $[-w,w]$ 映射到 $[0,w]$，zw 保持不变；片元着色器里再除以 $w$ 得到 $[0,1]$。
- **深度**：不要把 `o.depth = o.vertex.z / o.vertex.w` 传给 FS——这是投影后的非线性深度，插值后不是片段的真实深度。应直接把裁剪空间深度（或 `o.vertex.z` 与 `o.vertex.w`）传下去。

> 更本质的解释：透视变换改变原点，是非线性变换，但它把直线映射为直线；正因为如此，$1/w$ 在屏幕空间上是线性的，才可以用 $1/w$ 做"线性插值 + 反变换"来实现透视校正。

## Shader 各阶段职责（小结）

| 阶段 | 输入 | 输出 | 允许做什么 | 不能做什么 |
|:--|:--|:--|:--|:--|
| VS | 顶点属性 + uniform | 齐次裁剪坐标 + varying | 顶点变换、逐顶点光照、UV 变换、构造 `ComputeScreenPos` | 透视除法；访问其它顶点 |
| （曲面细分） | patch | 批量顶点 | 细分密度、位移 | — |
| （GS） | 1 个图元 | $N$ 个图元 | 增删图元、生成粒子/草 | 高效吞吐（注意性能） |
| 光栅化（固定） | 图元 | 片元 | 重心坐标、透视校正插值、深度插值 | 用户不可编程 |
| FS | 插值后的 varying、屏幕坐标 | 颜色（可写深度） | 纹理采样、逐像素光照、`clip()` 丢弃、写 `SV_Depth` | 改变像素位置；跨片元通信 |
| 逐片元操作（固定） | 片元 | 帧缓冲 | scissor/alpha/stencil/depth/blend | 用户不可编程 |

FS 中能拿到的屏幕信息：`SV_POSITION`（像素坐标，含 z）或 GLSL 的 `gl_FragCoord`；以及 `ComputeScreenPos` 手动传递并除以 $w$ 的 UV。这两者与 `dFdx/dFdy`、2×2 quad 的关系见《02_光栅化与深度可见性》。
