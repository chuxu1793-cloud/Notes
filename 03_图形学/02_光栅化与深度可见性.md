# 光栅化与深度可见性

> 本文讨论"哪个片元该被看见"这套机制：深度缓冲的存储与比较、深度值从投影到窗口的映射及其精度分布、Reversed-Z 与 w-buffer、Early-Z/Pre-Z、z-fighting 与 stitching、片元着色器如何拿到屏幕坐标与导数，以及由深度图重建世界坐标。阴影相关的深度比较见《05_阴影》。

## 深度缓冲基础

深度缓冲（depth buffer / z-buffer）与颜色缓冲同宽同高，逐片元存储一个深度值，通常为 16 / 24 / 32 位（多数系统为 24 位）。

开启深度测试后：片元深度与缓冲中的值比较，**通过则写入新深度（受写掩码控制），失败则丢弃片元**。

```c
glEnable(GL_DEPTH_TEST);
glClear(GL_COLOR_BUFFER_BIT | GL_DEPTH_BUFFER_BIT);  // 每帧必须清，否则沿用上一帧的深度
glDepthMask(GL_FALSE);   // 只读深度：仍做测试，但不写深度（透明物体、粒子常用）
```

深度测试默认是**关闭**的（`glEnable(GL_DEPTH_TEST)` 打开）。测试发生在片元着色器之后、模板测试之后，在**屏幕空间**执行；屏幕坐标由 `glViewport` 决定，可在着色器中通过 `gl_FragCoord` 访问：`gl_FragCoord.xy` 是窗口坐标（左下角为原点），`gl_FragCoord.z` 就是要与深度缓冲比较的值。

### 深度测试函数

```c
glDepthFunc(GL_LESS);   // 默认
```

| 运算符 | 含义 |
|:--|:--|
| `GL_ALWAYS` | 永远通过 |
| `GL_NEVER` | 永不通过 |
| `GL_LESS` | 片元深度 < 缓冲深度时通过 |
| `GL_EQUAL` | 相等时通过 |
| `GL_LEQUAL` | ≤ 时通过 |
| `GL_GREATER` | > 时通过 |
| `GL_NOTEQUAL` | ≠ 时通过 |
| `GL_GEQUAL` | ≥ 时通过 |

把函数设为 `GL_ALWAYS` 在**比较结果**上等价于关闭深度测试：后画的覆盖先画的（若最后画地面，地面会盖住所有物体）。但两者的深度**写入**行为不同——关闭测试时既不比较也不写深度，而 `GL_ALWAYS` 仍按 `glDepthMask` 写深度，后续 pass 读到的深度缓冲内容会不一样。恢复 `GL_LESS` 才得到正确遮挡。

> Reversed-Z 时比较方向要反过来用 `GL_GREATER` / `GL_GEQUAL`（见后文）。

## 深度值是怎么来的

### 从投影矩阵推导

以标准透视投影为例（眼空间深度 $d=-z_v>0$，$n$、$f$ 为近/远平面距离）：

$$
z_{clip} = -\frac{f+n}{f-n}\,z_v - \frac{2fn}{f-n},\qquad w_{clip}=-z_v=d
$$

（等价写法：矩阵元素为 $m_{22}=-(f+n)/(f-n)$、$m_{23}=-2fn/(f-n)$。首项的负号不能丢，代入 $z_v=-n$ 才得到 $z_{clip}=-n$、$z_{ndc}=-1$。）

代入 $z_v=-d$ 得 $z_{clip}=\dfrac{f+n}{f-n}d-\dfrac{2fn}{f-n}$，于是 **OpenGL**（NDC 为 $[-1,1]$）：

$$
z_{ndc}=\frac{z_{clip}}{w_{clip}}=\frac{f+n}{f-n}-\frac{2fn}{(f-n)d}
$$

代入 $d=n$ 得 $-1$，$d=f$ 得 $+1$，符合约定。再经视口变换 $z_w=\frac{z_{ndc}+1}{2}$：

$$
\boxed{\;z_w=\frac{f}{f-n}-\frac{fn}{(f-n)}\,\frac{1}{d}\;}
$$

**D3D**（NDC 为 $[0,1]$）不需要再映射，结果与上式相同：

$$
z_{ndc}^{D3D}=\frac{f}{f-n}-\frac{fn}{(f-n)d}=\frac{f(d-n)}{d(f-n)}
$$

两个结论：

1. 窗口深度 $z_w$ 是 $1/d$ 的**仿射函数**，因此深度在屏幕空间是**非线性**的（对 $d$ 而言）；
2. 精度集中在近平面附近，远处极差——这就是 z-fighting 的根源。

### 反解：NDC/窗口深度 → 视空间深度

由上式反解得视空间（线性）深度：

$$
\text{OpenGL:}\quad d=\frac{2fn}{f+n-z_{ndc}(f-n)}
$$

$$
\text{D3D/窗口深度:}\quad d=\frac{fn}{f-z_w(f-n)}
$$

在 OpenGL 中常见的线性化代码（先把 $[0,1]$ 还原为 $[-1,1]$，再套用上式）：

```glsl
float linearizeDepth(float depth) {
    float z = depth * 2.0 - 1.0;                      // [0,1] -> [-1,1]
    return (2.0 * near * far) / (far + near - z * (far - near));
}
```

若把结果再除以 `far`，就得到便于可视化的 $[0,1]$ 线性深度。

> **易错点**：上面的 `depth*2-1` 只适用于 NDC 为 $[-1,1]$ 的 OpenGL。D3D/Vulkan/Metal 的 NDC z 是 $[0,1]$，Unity 里应使用 `LinearEyeDepth(raw, _ZBufferParams)`，而不是照搬这段代码。

### Unity 的 `_ZBufferParams` 与 `LinearEyeDepth`

因为 $1/d$ 是窗口深度的仿射函数，可以统一写成

$$
\frac{1}{d}=A\,z_w+B
$$

- 非 reversed：$A=\frac{1}{f}-\frac{1}{n}$，$B=\frac{1}{n}$（$z_w=0$ 对应近平面）；
- reversed：$A=\frac{1}{n}-\frac{1}{f}$，$B=\frac{1}{f}$（$z_w=0$ 对应远平面）。

Unity 把 $A,B$ 打包进 `_ZBufferParams.z/.w`，于是：

```hlsl
float LinearEyeDepth(float rawDepth, float4 zBufferParams)
{
    return 1.0 / (zBufferParams.z * rawDepth + zBufferParams.w);
}
float Linear01Depth(float rawDepth, float4 zBufferParams)
{
    return 1.0 / (zBufferParams.x * rawDepth + zBufferParams.y);
}
```

（`_ZBufferParams` 的具体打包方式随是否 reversed、是否 orthogonal 而不同，跨平台时以宏为准，手写时请核对符号。）

## 精度分布

以 $2^N$ 个量化级为例，窗口深度的一个量化步长是 $\Delta z_w = 1/2^N$。由 $z_w(d)$ 求导：

$$
\frac{dz_w}{dd}=\frac{fn}{(f-n)d^2}
\quad\Longrightarrow\quad
\Delta d=\frac{d^2(f-n)}{fn\,2^{N}}\approx\frac{d^2}{n\,2^{N}}
$$

即**可分辨的最小深度间隔随距离平方增长**，相对误差 $\Delta d/d \approx d/(n\,2^N)$ 与距离成正比。

另一种更直观的写法（`Learning to Love your Z-buffer` 给出的近似式）：

$$
\delta \approx \frac{z^2}{z_{near}\,2^{N}-z}
$$

当 $z\ll z_{near}\,2^{N}$ 时（分母的 $-z$ 可忽略）与上式一致。原文给出的经验数据（16 位深度，$z_{near}=1\,\text{m}$；各近似式在此处的解相差约 10%，如 5% 一条：δ 式解 3121、微分式解 3277，故下表取量级约值）：

| 相对误差 | 可分辨距离 / $z_{near}$ |
|:--|:--|
| 10% | ~6000 |
| 5% | 3500 |
| 1% | 666 |
| 0.1% | 66 |
| 0.01% | 6 |

即 $z_{near}=1\text{m}$ 时，3500m 处误差约 5%；若把 $z_{near}$ 改成 0.1m，350m 处就有 5% 误差，3.5km 处误差约 53%（$\approx 3500/(0.1\times2^{16})$）——一架飞机可能突然出现在山前面。24 位深度把这些比值放大约 256 倍（$Z_{1\%}\approx1.7\times10^5$），32 位再大约 256 倍。

结论与工程建议：

1. **$z_{near}$ 越大越好**（在近处物体不被裁掉的前提下），这是消除 z-fighting 最有效的一招；
2. 深度位数越高越好（24 位是底线，32 位/浮点深度更稳）；
3. 不要让两个面共面或贴得太近，必要时给一点肉眼不可见的偏移；
4. 大世界场景考虑 Reversed-Z、对数深度、或多 pass 分层深度。

回到映射本身：它之所以非线性，是因为裁剪空间 $z$ 对视空间 $z_v$ 只是**仿射**的，一般可写成

$$
z_c = a\,z_v + b
$$

再除以 $-z_v$（透视投影下它等于 $w_{clip}$）得到 NDC 深度，最后线性映射到窗口深度：

$$
z_n=\frac{z_c}{-z_v}=-a-\frac{b}{z_v}\qquad[-1,1]
$$

$$
z_{viewport}=\frac{z_n+1}{2}\qquad[0,1]
$$

可见"映射到 $[0,1]$"只是对 $z_n$ 做一次平移缩放，非线性的来源完全在 $-a-b/z_v$ 这一步。

### w-buffer（OOZ-buffer）

要让整个深度范围的分辨率一致，就不要存裁剪空间 z，而存**观察空间的线性深度**——它恰好出现在齐次坐标的 $w$ 分量里，故称 w-buffer。

透视投影矩阵（行向量约定）：

$$
\begin{bmatrix}
W&0&0&0\\
0&H&0&0\\
0&0&Q&1\\
0&0&-QZ_n&0
\end{bmatrix},\quad
\begin{aligned}
W&=\frac{2Z_n}{\text{viewportW}}\\
H&=\frac{2Z_n}{\text{viewportH}}\\
Q&=\frac{Z_f}{Z_f-Z_n}
\end{aligned}
$$

点 $(x,y,z,1)$ 乘该矩阵后 $w$ 不再为 1，且 $w\propto z$，于是透视除法产生近大远小。

| | z-buffer | w-buffer |
|:--|:--|:--|
| 存什么 | 投影后的 z | 投影后的 w（∝ 视空间 z） |
| 分布 | 非线性，近处精度高、远处差 | 线性，全域均匀 |
| 优点 | 近处精度高；硬件普遍支持 | 远处精度好、行为可预测 |
| 缺点 | 远处易 z-fighting | 近处精度不足；硬件支持少（D3D9 有 `D3DZB_USEW`，D3D10 起移除；OpenGL 无原生支持） |

两者的转换：

$$
z_{depth}=Q\,\frac{w_{depth}-Z_n}{w_{depth}}=\frac{Z_f}{Z_f-Z_n}\cdot\frac{w_{depth}-Z_n}{w_{depth}}
$$

用途举例：3DS MAX 使用 w-buffer，若把它的深度信息导出给使用 z-buffer 的 D3D 作预渲染背景，必须先做上述转换，否则结果错误。

## Reversed-Z 与 `UNITY_REVERSED_Z`

**核心思想**：把深度方向反过来——近平面映射到 1，远平面映射到 0：

$$
z_w^{rev}=1-z_w=\frac{n}{f-n}\left(\frac{f}{d}-1\right)
$$

- $d=n\Rightarrow z_w^{rev}=1$；$d=f\Rightarrow z_w^{rev}=0$；
- 反解：$d=\dfrac{fn}{n+z_w^{rev}(f-n)}$。

为什么这样就准？两个分布的"误差"刚好互相抵消：

1. $z_w$ 对 $1/d$ 是仿射的，精度本身集中在 $d$ 小的一端；
2. 浮点数的绝对精度随数值减小而指数级变细——**越接近 0，可表示的间隔越小**。

把远平面放到 0、近平面放到 1，等于让"最需要补精度"的远处落在浮点最密的一侧，于是 $d$ 上的精度分布接近**对数均匀**：近处不损失，远处获得数量级的提升。这也是为什么 Reversed-Z 只在**浮点深度缓冲 + NDC 为 $[0,1]$** 的平台上收益明显（D3D11/12、Vulkan、Metal；OpenGL 的 NDC 是 $[-1,1]$，需要 `glClipControl` 才能受益）。

> **常见误解**：Reversed-Z 并不会让"取值区间变成 $[-1,1]$"或"近处精度变低"。它的取值仍是 $[0,1]$，只是端点对调；精度收益来自浮点表示，而不是来自把非线性变线性。

工程上必须同步改的三件事：

1. 清深度缓冲的值改为 0（`glClearDepth(0)` / `ClearDepth 0`），因为"最远"是 0；
2. 深度比较函数改为 `GREATER` / `GEQUAL`（Unity 中由管线按平台处理）；
3. 投影矩阵的第三行（z 行）取反。

Unity 中用 `SystemInfo.usesReversedZBuffer` 判断，并在矩阵层面手动翻转（URP 的 `GetShadowTransform` 就是这么做的）：

```csharp
if (SystemInfo.usesReversedZBuffer)
{
    proj.m20 = -proj.m20;
    proj.m21 = -proj.m21;
    proj.m22 = -proj.m22;
    proj.m23 = -proj.m23;
}
```

着色器里则用 `UNITY_REVERSED_Z` 分支，把读到的深度翻回去：

```hlsl
#if defined(UNITY_REVERSED_Z)
    depth = 1 - depth;   // (1,0) -> (0,1)
#endif
```

> 注意"反转"不是万能的：它只改善**深度缓冲的比较精度**，不改变阴影贴图、自定义 RTHandle 格式、深度图采样等处的约定；混用 `1 - depth` 与 `LinearEyeDepth` 时要确认每一步的约定是否一致——这是跨平台深度 bug 的第一大来源。

### 两种 API 风格的投影矩阵与 NDC→depth 映射

统一用**列向量约定、右手系、相机朝 $-z$**（即 $d=-z_v>0$），只写出与 z 有关的第三行和 $w$ 行。

**DX 风格（NDC z 为 $[0,1]$）**——D3D11/12、Metal、Vulkan、Switch（NVN）都属于这一类。反转后：

$$
P_{\text{rev}}=\begin{bmatrix}
\cdot&\cdot&\cdot&\cdot\\
\cdot&\cdot&\cdot&\cdot\\
0&0&\dfrac{n}{f-n}&\dfrac{fn}{f-n}\\
0&0&-1&0
\end{bmatrix}
$$

代入两端验证：$z_v=-n$ 时 $z_{clip}=n$、$w=n$，故 $z_{ndc}=1$；$z_v=-f$ 时 $z_{clip}=0$，故 $z_{ndc}=0$。非反转版本把这两个系数换成 $-\dfrac{f}{f-n}$、$-\dfrac{fn}{f-n}$，端点即变为 $0\to1$。

**GL 风格（NDC z 为 $[-1,1]$）**：非反转是 $m_{22}=-\dfrac{f+n}{f-n}$、$m_{23}=-\dfrac{2fn}{f-n}$；反转为

$$
m_{22}=\frac{f+n}{f-n},\qquad m_{23}=\frac{2fn}{f-n}
$$

端点：$z_v=-n\Rightarrow z_{ndc}=+1$，$z_v=-f\Rightarrow z_{ndc}=-1$。

> **别照搬"取反"这一步。** GL 风格的两个系数关于原点对称，所以"$m_{22},m_{23}$ 同取负"恰好就是反转——前文 `proj.m20 = -proj.m20` 那段之所以成立，是因为 Unity 内部保存的就是 GL 的 $[-1,1]$ 投影，取反后由 `GL.GetGPUProjectionMatrix` 再映射到 $[0,1]$。DX 风格的系数并不对称（$-\frac{f}{f-n}$ 与 $-\frac{fn}{f-n}$），**直接取负得不到 $[1,0]$**，必须换成上式的 $n/(f-n)$ 与 $fn/(f-n)$。

NDC 还要再过一次视口映射，$z_w$ 才是写进深度缓冲、被 `SAMPLE_DEPTH_TEXTURE` 读到的值：

| 平台 | NDC z 范围 | $z_{ndc}\to z_w$ | 反转后的 $z_w$ 范围 |
|:--|:--|:--|:--|
| D3D11/12 | $[0,1]$ | 恒等（viewport Min/MaxDepth 默认 0/1） | $[1,0]$ |
| Metal | $[0,1]$ | 恒等；也可把 viewport 的 `znear/zfar` 设为 1/0 直接反转 | $[1,0]$ |
| Vulkan | $[0,1]$ | 恒等（viewport `minDepth/maxDepth`） | $[1,0]$ |
| Switch（NVN） | $[0,1]$ | 恒等 | $[1,0]$ |
| GL（传统） | $[-1,1]$ | $z_w=\frac{z_{ndc}+1}{2}$ | $[1,0]$ |
| GL + `glClipControl(GL_ZERO_TO_ONE)` | $[0,1]$ | 恒等 | $[1,0]$ |

反转后所有平台的窗口深度都是 $[1,0]$，差别只在**矩阵给出的是 $[0,1]$ 还是 $[-1,1]$ 的 NDC**。GL 不切 `glClipControl` 时，矩阵先给出 $[1,-1]$，再经 $0.5z+0.5$ 折到 $[1,0]$：这只多了一次仿射折半，折完仍是"近处 1、远处 0"，浮点间隔不会因此变粗（实测 n=0.1、f=1000 时与 D3D reversed 一致到 1~数 ulp、ulp 间隔相同，例如 d=1 时 0.09991005 vs 0.09990999；差别只在多这一次仿射折半的舍入，d 越大相对差越明显）。所以 GL 需要 `glClipControl` 的理由是**统一到 $[0,1]$ 约定、省掉这次折半映射并与其它平台对齐**，而不是精度收益打折。

> 源笔记用"对 $z_v$ 取绝对值（以 $z_v=0$ 为轴翻转）"来图示从 GL 曲线过渡到 DX 曲线，这只是示意图。（原稿有误，已更正：取绝对值只把定义域翻到 $d>0$，取值范围仍是 $[-1,1]$；要落到 DX 的 $[0,1]$，还需叠加 $z_w=0.5\,z_{ndc}+0.5$ 这一仿射映射。）

## Z-fighting 与 stitching

- **z-fighting**：两个面共面（或极接近）时深度值相同，深度缓冲无法区分，位于后面的图元上的一些像素被渲染到前面的图元上，表现为条纹/闪烁，逐帧变化。
- **stitching**：先用 `GL_FILL` 画多边形、再用 `GL_LINE` 画同一边界时，**直线与多边形的光栅化规则不同**，同一位置的深度值并不严格相等，于是线框时隐时现、断断续续。

```c
glPolygonMode(GL_FRONT_AND_BACK, GL_FILL);
pObj->renderOBJ();

glPolygonMode(GL_FRONT_AND_BACK, GL_LINE);
glEnable(GL_POLYGON_OFFSET_LINE);
glPolygonOffset(-1.0, -1.0);   // 让线更靠近相机
pObj->renderOBJ();
```

`glPolygonOffset(factor, units)` 的偏移量是

$$
\Delta z = factor\cdot\left|\frac{\partial z}{\partial \text{window}}\right| + units\cdot r
$$

其中 $r$ 是实现相关的最小可分辨深度值。`factor` 处理斜率大的面，`units` 处理常数偏移；两者都取负值即"朝观察者方向拉"。

消除 z-fighting 的常规手段：拉开物体间距、推远近平面、提高深度位数、Reversed-Z；线框叠加则用 polygon offset 或深度偏移（`SV_Depth` / `DepthOffset`）。

把视空间深度线性归一化到 $[0,1]$：

$$
F_{depth}=\frac{z-near}{far-near}
$$

（下图为 $near=1$、$far=50$ 时的曲线，是一条直线，深度值与距离成正比。）

![](../../技术笔记/assets/3E412D4404954BDDA5C6DA1F3CA078F8.png)

而深度缓冲实际使用的是对 $1/z$ 的归一化（等价于前面推出的"$z_w$ 是 $1/d$ 的仿射函数"），于是变成非线性映射：

$$
F_{depth}=\frac{1/z-1/near}{1/far-1/near}
$$

（下图为同样的 $near=1$、$far=50$ 下的曲线：近处陡、远处平，绝大部分取值区间被近处占去——这就是前文"精度集中在近平面附近"的图像化表现。）

![](../../技术笔记/assets/FE3E56CB8FCA434C820C5D35A12938F9.png)

把窗口深度直接当颜色输出时，画面几乎全白——因为非线性深度在很近处就迅速逼近 1；只有贴近物体时才看得到渐暗。这直观地说明了"深度值的非线性性质"。

![](../../技术笔记/assets/09AE3C4D883344E2B2D5910F33A2A124.png)

![](../../技术笔记/assets/1EE58FF9076E450792E89BFFC472928A.png)

教材里通常这样推一遍（$Far$、$Near$ 为远/近裁剪面距离，$z_{view}$ 为视空间深度，取负值）：

用透视投影裁剪矩阵 $P_{clip}$ 对视角空间下的顶点变换后，裁剪空间下的 $z$、$w$ 分量为

$$
z_{clip}=-z_{view}\frac{Far+Near}{Far-Near}-\frac{2\cdot Near\cdot Far}{Far-Near}
$$

$$
w_{clip}=-z_{view}
$$

经齐次除法得到 NDC 下的 $z$ 分量：

$$
z_{ndc}=\frac{z_{clip}}{w_{clip}}=\frac{Far+Near}{Far-Near}+\frac{2\cdot Near\cdot Far}{(Far-Near)\cdot z_{view}}
$$

深度纹理中的深度值由 NDC 计算而得：

$$
d=0.5\cdot z_{ndc}+0.5
$$

联立以上几式，可以反解出用 $d$ 表示的 $z_{view}$：

$$
z_{view}=\frac{1}{\dfrac{Far-Near}{Near\cdot Far}\,d-\dfrac{1}{Near}}
$$

（与本文前面的 $d=\dfrac{fn}{f-z_w(f-n)}$ 是同一关系的两种写法：把 $d$ 换成 $z_w$、$Near/Far$ 换成 $n/f$ 即得。）

## Early-Z 与 Pre-Z

两者目的相同：**减少 overdraw，别在会被遮挡的片元上浪费着色**。

### Early-Z

1. 传统管线中深度测试发生在片元着色器**之后**；
2. Early-Z 是硬件把深度测试**提前到光栅化阶段**，先剔除必然不可见的片元，再进 PS；
3. 它是底层写好的功能，满足条件才生效。会失效的典型情况：
   - 片元着色器**写深度**（`SV_Depth` / `gl_FragDepth`）——硬件无法预知最终深度；
   - 使用 **discard / alpha test**——片元可能被丢弃，深度写入不确定；
   - 开启混合且依赖前序结果时，某些硬件也会退化；
   - 具体的"保守深度（conservative depth）"支持情况因 GPU 而异。

### Pre-Z（depth prepass）

1. 一个单独只写深度的 pass（可以简单到只有 VS + 空 FS）；
2. 之所以需要它：开启 alpha test 会让 Early-Z 失效。做法是**先做一次 pre-Z pass，在 pass 内处理 z 与 alpha test**；之后正常绘制该物体时不再开 alpha test，于是 Early-Z 又能生效；
3. 代价是多一遍几何提交与一次额外的深度带宽；在 overdraw 严重的场景收益明显，在几何量巨大而 overdraw 小的场景可能亏。

> Early-Z 的剔除粒度不是单像素，而是 **pixel quad（2×2）**（见后文"fs 最小处理单位"）。

## 片元着色器与屏幕坐标

### `SV_POSITION` / `gl_FragCoord`

设裁剪空间坐标为 `clipPos`：

- `clipPos.xy / clipPos.w` 把 $[-w,w]$ 映射到 $[-1,1]$（NDC）；
- 再 $\times 0.5 + 0.5$ 映射到 $[0,1]$；
- 再按屏幕宽高映射到 $[0,W]$、$[0,H]$ 像素。

在 FS 中，`SV_POSITION`（或 `gl_FragCoord`）的 xy 就是**像素坐标**，可直接用于屏幕空间效果。`clipPos.z` 的范围是 $[0,w]$（D3D/Vulkan）或 $[-w,w]$（GL），注意不是 $[0,1]$；`clipPos.w = -z_{view}$，是**正的**视空间深度，后续透视除法与校正都用它。

### `ComputeScreenPos`

```hlsl
float4 ComputeScreenPos(float4 clipPos)
{
    float4 o = clipPos * 0.5;                              // 此时 o.w 仍是 0.5w
    o.xy = float2(o.x, o.y * _ProjectionParams.x) + o.w;   // x 只平移；y 按投影是否翻转取符号
    o.zw = clipPos.zw;                                     // 关键：把 w 恢复为 clipPos.w，供 FS 做 .xy/.w
    return o;
}
```

`_ProjectionParams.x` 为 `1` 或 `-1`（渲染到 RT 等投影 y 翻转的场合为 `-1`）。**不要用 `#if UNITY_UV_STARTS_AT_TOP` 单独判断 y 翻转**：它描述的是平台纹理原点，而不是当前投影矩阵是否翻转，二者在渲染到 RT 时会不一致；写成编译期分支还必须额外处理投影翻转，容易漏。

等价的展开写法（便于看清每一项的来源）：

```hlsl
float4 o = clipPos * 0.5;
o.x  = o.x + o.w;                              // [-w,w] -> [0,w]
o.y  = o.w + o.y * _ProjectionParams.x;
o.zw = clipPos.zw;
```

**易错点**：`o = clipPos * 0.5` 之后 `o.w` 是 `0.5w`。若既不恢复 `zw`、又在末尾统一写 `o.xy += o.w`，那么 x 只加了 `0.5w`（基准少一半，`uv.x` 落在 `[0,2]`），y 又多加一次平移（`uv.y` 落在 `[1,3]`）——**x、y 两个分量都会错**，屏幕中心点会得到 `(1,2)` 而不是 `(0.5,0.5)`。根因是漏掉 `o.zw = clipPos.zw`。正确写法是：x 与 `o.y * _ProjectionParams.x` 各加一次 `o.w`（落在 `[0,w]`），最后必须把 `zw` 恢复成 `clipPos.zw`。

VS 中调用，FS 中 `o.xy / o.w` 得到 `[0,1]` 的屏幕 UV（用于采样深度图、GrabPass 等）；若要真实像素坐标再乘 `_ScreenParams.xy`。

**为什么不在 VS 里除 $w$？** 因为除完之后顶点已经落在非线性空间，而插值是靠 $1/w$ 在线性空间完成的：**先插值 `x/w` 与 `1/w` 再相除**，与先插值 `x`、`w` 再相除，结果不同，**前者**才正确（后者等价于在屏幕空间线性插值 $x/w$，得到的是错误的仿射结果）。透视变换改变了原点（非线性），但它把直线映射为直线，所以 $1/w$ 在屏幕空间是线性的——这正是透视校正插值的全部依据。

### fs 的最小处理单位：2×2 pixel quad

像素着色器不是一像素一像素执行的，而是以 **2×2 的像素块（quad）** 为最小工作单元并行执行；32 个像素线程组成一组（相当于 8 个 quad），由 SM 的 warp 调度器管理。

![](../../技术笔记/assets/WEBRESOURCEaf6cf13122f8134800c4ad7cb07a9d6e.png)

推论：即使三角形只覆盖 3 个像素，只要它们落在 3 个不同的 quad 里，就要占用 12 个线程槽位（3 个 quad），未被覆盖的像素被"遮掩"但依然消耗执行资源。

![](../../技术笔记/assets/WEBRESOURCE63781e3f0857f1359e7155640ebf04f4.png)

### dFdx / dFdy

偏导函数：HLSL 为 `ddx`/`ddy`，GLSL 为 `dFdx`/`dFdy`，含义是**屏幕空间中变量在 x/y 方向上的变化率**。因为硬件以 2×2 quad 同步执行，四个像素的局部变量在"同一指令点"都是可得的，于是

$$
\frac{\partial f}{\partial x}=f(x+1,y)-f(x,y),\qquad
\frac{\partial f}{\partial y}=f(x,y+1)-f(x,y)
$$

即沿 x 正向取差分、沿 y 正向取差分（屏幕坐标 y 的方向由 API 决定：D3D 的 y 向下，`ddy` 是下减上；OpenGL 的 y 向上，`ddy` 是上减下）。

典型用途：

1. **Mipmap 级别**：对 UV 求偏导，偏导过大说明贴图离得远，选择更低 level 的 mip；
2. **Flat shading / 重建面法线**：把顶点位置传到 FS，用两条差分向量叉乘得到法线——
$$
\mathbf{n}=\text{normalize}\big(\partial_x \mathbf{p}\times \partial_y \mathbf{p}\big)
$$
   HLSL/Unity 中要写成 `normalize(cross(ddy(pos), ddx(pos)))`（左右手坐标系导致顺序相反，否则法线反向）。

![](../../技术笔记/assets/BAA809AAED25492084CE185F97F39FE7.png)

![](../../技术笔记/assets/758816997E104651B87C6E77B6C0EB8E.png)

![](../../技术笔记/assets/8605E8E4DCB74B98B7DA4ECA09F94554.png)

![](../../技术笔记/assets/C4763B9CC167452B8E55CC708DD3B28F.png)

3. **贴图锐化/勾边**：`c += ddx(c)*2 + ddy(c)*2` 可以强化边缘。

![](../../技术笔记/assets/0F7049B407D24885AA97A46768B3C693.png)

![](../../技术笔记/assets/F2170A93F34C4C219CB9CB3231B94EDC.png)

4. **前沿渲染下的 edge artifact**：`ddx/ddy` 的 2×2 区域可能跨越两个三角形。Forward 渲染时，quad 中未被覆盖的像素会作为 **helper invocation** 参与执行，其取值由**同一图元**的平面方程外推得到——被保证的是"同一图元"，而不是"只包含覆盖像素"；而 **Deferred 的后处理 pass 画的是全屏 quad**，这个"免费合法性检查"失效，参与差分的四个像素可能来自不同表面，于是边缘出现 artifacts。

![](../../技术笔记/assets/668E623E65E84EF182CC40C735B99D00.png)

![](../../技术笔记/assets/0F56BD5C5AB84C999C7318D86D02F357.png)

结论：`ddx/ddy` 与 forward 渲染兼容性更好；用位置差分重建法线时，务必确认 2×2 区域落在同一三角面内，否则改用几何法线（G-buffer 里存的那一份）。

**实现视角**：`ddx` 要求 4 个像素"在同一指令点汇合"。CPU 上要么用 Fiber/线程切换栈上下文，要么完全 SIMD 化——前者极慢，后者才接近硬件做法。

## 由深度图重建世界坐标

### 逆 VP 矩阵法

```hlsl
float4 GetWorldSpacePosition(float rawDepth, float2 uv)
{
    // uv ∈ [0,1] -> NDC xy ∈ [-1,1]
    // rawDepth ∈ [0,1] 是窗口深度，但 NDC z 的区间随平台而变，不能直接当 NDC z：
    //   D3D/Metal/Vulkan：NDC z ∈ [0,1]，窗口深度与之一致，直接用
    //   GL/GLES：NDC z ∈ [-1,1]，窗口深度要 *2-1 映射过去（reversed 时 1-2*rawDepth）
    float ndcZ;
#if defined(SHADER_API_GLCORE) || defined(SHADER_API_GLES) || \
    defined(SHADER_API_GLES3) || defined(SHADER_API_WEBGL)
    #if defined(UNITY_REVERSED_Z)
        ndcZ = 1.0 - 2.0 * rawDepth;      // 窗口 1→-1、0→+1（NDC 近=-1、远=+1）
    #else
        ndcZ = 2.0 * rawDepth - 1.0;      // [0,1] -> [-1,1]
    #endif
#else
    ndcZ = rawDepth;                      // NDC z ∈ [0,1]
#endif
    float4 ndc = float4(2.0 * uv - 1.0, ndcZ, 1.0);
    #if UNITY_UV_STARTS_AT_TOP
        ndc.y *= -1;                      // NDC 的 y 自下而上
    #endif
    float4 positionWS = mul(UNITY_MATRIX_I_VP, ndc);
    positionWS /= positionWS.w;           // 齐次 -> 三维
    return positionWS;
}
```

> **上面这段的 z 分支不能省。** 把窗口深度直接当 NDC z，只在 NDC z ∈ $[0,1]$ 的平台（D3D/Metal/Vulkan）成立；GL/GLES 的 NDC z 是 $[-1,1]$，照搬会把近平面当成 $z=0$，重建出的世界坐标整体偏移。若不想分平台，另一条路是先 `LinearEyeDepth(rawDepth, _ZBufferParams)` 拿到线性眼空间深度 $d$，再把像素视线方向缩放过去（相似三角形）：$\text{world}=\text{camPos}+\hat{r}\cdot\dfrac{d}{\hat{r}\cdot\hat{f}}$，其中 $\hat{r}$ 是该像素的世界空间单位视线方向、$\hat{f}$ 是相机前向。

**为什么可以直接用 NDC 乘逆 VP？** 正常流程应是"先乘 $w$ 还原 clip，再乘 $\text{VP}^{-1}$"，但投影变换损失了维度，我们并不知道该乘哪个 $w$。利用"世界点的 $w$ 必为 1"这一条件可以推出：

$$
\text{ndc}=\frac{\text{clip}}{\text{clip}_w},\qquad
\text{world}=\text{VP}^{-1}\cdot\text{ndc}\cdot \text{clip}_w
$$

$$
1=\text{world}_w=(\text{VP}^{-1}\text{ndc})_w\cdot\text{clip}_w
\;\Longrightarrow\;
\text{clip}_w=\frac{1}{(\text{VP}^{-1}\text{ndc})_w}
$$

$$
\boxed{\;\text{world}=\frac{\text{VP}^{-1}\cdot\text{ndc}}{(\text{VP}^{-1}\cdot\text{ndc})_w}\;}
$$

也就是说，"NDC 乘逆 VP 再除 $w$"是数学上严格等价的写法，不是近似。

### 全屏三角形与 uv 的平台差异

```hlsl
float2 GetFullScreenTriangleUV(uint vertexID)
{
#if UNITY_UV_STARTS_AT_TOP
    return float2((vertexID << 1) & 2, 1.0 - (vertexID & 2));
#else
    return float2((vertexID << 1) & 2, vertexID & 2);
#endif
}
```

要点：

1. 用顶点 ID 生成 uv（3 个顶点画满全屏），没有顶点缓冲；
2. uv 直接采样深度图；但在**参与逆 VP 计算前**可能要做一次 y 翻转。

`UNITY_UV_STARTS_AT_TOP` 生效的平台（如 Metal）要求纹理起点在左上角，因此采样深度图时可直接用 uv；而 NDC 的 y 是自下而上（D3D11、OpenGL、Metal 在 Unity 的抽象里皆如此；Vulkan 裸 API 的 NDC +y 向下，由 Unity 翻转投影对齐），所以构造 NDC 时必须翻转。

需要区分两种写法：

```hlsl
// A：uv 先垂直翻转，NDC 不再翻
float2 uv = float2(i.uv.x, 1 - i.uv.y);

// B：uv 保持，NDC.y 取反
posCS.y = -posCS.y;
```

**A 与 B 等价**：A 把 uv 翻成 $1-uv.y$ 后再映射到 NDC，得到 $2(1-uv.y)-1=1-2uv.y$，正是 B 中 `posCS.y = -posCS.y` 的结果。要注意的只是别把翻转叠加两次：A 已经翻过一次，此时就不必再执行 B；反过来，若生成 uv 时已经做过一次 `1 - ...`，也不要再叠一个 `1 - uv.y`。

### 射线插值法

VS 里算出从相机指向远平面的射线，逐像素插值后用线性深度缩放：

```hlsl
// VS
int index = v.uv.x + (2 * v.uv.y);   // 0:左下 1:右下 2:左上 3:右上（uv 原点在左下，与 corners 的行序一致）
o.viewRayWorld = _FrustumCorners[index];

// FS
float depth = SAMPLE_DEPTH_TEXTURE(_CameraDepthTexture, i.uv);
depth = Linear01Depth(depth);        // 0=相机, 1=远平面
float3 worldPos = _WorldSpaceCameraPos + depth * i.viewRayWorld;
```

四个角射线的构造（C#）：

```csharp
var halfHeight = far * Mathf.Tan(fov / 2 * Mathf.Deg2Rad);
var toRight   = cam.transform.right   * halfHeight * aspect;
var toTop     = cam.transform.up      * halfHeight;
var toForward = cam.transform.forward * far;
corners.SetRow(0, toForward - toTop - toRight);   // 左下
corners.SetRow(1, toForward - toTop + toRight);   // 右下
corners.SetRow(2, toForward + toTop - toRight);   // 左上
corners.SetRow(3, toForward + toTop + toRight);   // 右上
```

也可在 VS 里用逆投影矩阵生成射线（原理相同）：

```hlsl
float4 ndcPos = float4(v.uv * 2 - 1.0, 1.0, 1.0);
float4 clipRay = mul(_InverseProjectionMatrix, ndcPos);
o.viewRay = clipRay.xyz / clipRay.w;
```

两种方法的代价对比：逆 VP 法每个像素一次 4×4 矩阵乘法；射线法把矩阵乘法搬到 VS（每顶点一次），FS 只做一次乘加，通常更快，但需要正确插值射线（射线在屏幕空间是线性可插值的）。

### 由 screenUV 与线性深度的相似三角形法

射线法的一个变体，工程上常见于屏幕空间贴花（shadow decal）：深度图来自一次 pre-z，贴花本体是全屏 quad，不可能带着世界坐标进来，只能重建。

```hlsl
// VS
float4 clip = mul(UNITY_MATRIX_VP, float4(v.positionWS, 1.0));
o.screenUV = clip.xy * 0.5 + 0.5 * clip.w;        // 缩放到 [0, w]

// FS
float2 uv   = i.screenUV.xy / i.screenUV.w;          // 透视除法 -> [0,1]
float  zn   = SAMPLE_DEPTH_TEXTURE(_CameraDepthTexture, uv);
float  zv   = LinearEyeDepth(zn, _ZBufferParams);    // 沿光轴的眼空间深度（正值）
float  t    = tan(0.5 * fovY);
float3 posV = float3((2 * uv.x - 1) * t * aspect * zv,
                     (2 * uv.y - 1) * t * zv,
                     -zv);
float3 posWS = _WorldSpaceCameraPos + mul((float3x3)UNITY_MATRIX_I_V, posV);
```

推导就是相似三角形：视锥在深度 $z_v$ 处的半高为 $z_v\tan(\mathrm{fov}_y/2)$，半宽再乘 aspect，屏幕 uv 的 $[0,1]$ 线性映射到 $[-1,1]$：

$$
x_v=(2u-1)\,a\,t\,z_v,\qquad y_v=(2v-1)\,t\,z_v,\qquad t=\tan\frac{\mathrm{fov}_y}{2}
$$

两个容易踩的点：

1. `screenUV` 在 VS 里是 $[0,w]$，**必须在 FS 里除以插值后的 $w$** 才能当采样坐标；在 VS 里提前除会破坏透视校正（与 `ComputeScreenPos` 的理由相同，FS 中取 `.xy/.w`）。
2. 这里乘的是 $z_v$（沿光轴的距离）。若手头只有 `Linear01Depth`（$=z_v/far$），必须先乘回 `far` 再套上式，否则重建坐标整体被缩到近平面上；反过来，乘"到远平面的射线"时就必须用 $z_v/far$，两者不能混。

u/v 的方向沿用前面的约定：`UNITY_UV_STARTS_AT_TOP` 下 v 向下增长，$y_v$ 的符号随之取反——从 uv 到 $x_v,y_v$ 这一条链路必须共用同一套约定。

Shadow decal 的收尾是把世界坐标转回物体空间做盒体裁剪，超出盒子的片元丢弃：

```hlsl
float3 objCoord = mul(unity_WorldToObject, float4(posWS, 1.0)).xyz;
clip(0.5 - abs(objCoord));
```

### 后处理中使用重建坐标的注意事项

- **几何只有 4 个顶点**：全屏 quad/三角形不带任何物体属性，世界坐标、法线、视空间位置都得靠深度（或 G-buffer）重建，这是它与普通 `shader-material` 最根本的区别。
- **深度图要与颜色同源同分辨率**：重建用的深度应来自同一次光栅化的 pre-z / G-buffer 深度；分辨率被后处理改变后，采样点与颜色像素对不上，遮挡边界会错位（见附录的 FSR 讨论）。
- **约定要端到端一致**：uv 原点（左下/左上）、NDC 的 y 方向、是否 reversed、手里是 $z_w$ 还是 $z_{ndc}$——四件事在矩阵、采样、重建三步中任何一处不一致，都会得到"镜像 + 反向"的世界坐标。排查方法：把重建坐标直接当颜色输出，放一个已知坐标的物体比对。
- **精度被放大**：$\partial\,\text{world}/\partial z$ 在掠射角处极大，SSAO、雾、贴花在极远处或几乎平行视线的面上容易出现条纹；必要时按距离淡出，或先线性化深度再插值。

### 深度重建的其他用途

- **屏幕空间阴影**：用重建的世界坐标转到光源空间采样 shadowmap（见《05_阴影》）。
- **贴花（decal）**：用世界坐标转物体空间，`clip(0.5 - abs(objCoord))` 把贴花限制在盒子内。
- **深度相关后处理**：SSAO/HBAO、雾、景深。

### HBAO 中对深度的用法（仅摘深度相关结论）

1. **per-pixel normal**：不依赖顶点法线，直接用相机空间位置的偏导得到 $\Delta P=\Delta u\cdot \mathrm{d}P/\mathrm{d}u+\Delta v\cdot \mathrm{d}P/\mathrm{d}v$，再叉乘出法线（同上文 dFdx/dFdy，注意跨三角面 artifact）；
2. **采样步长由深度决定**：相机空间半径 $R$ 投影到屏幕 uv 为
$$
R_{uv}=\frac{\cot(\mathrm{fovY}/2)\cdot R}{2\,P_z},\qquad
(\Delta u,\Delta v)=\frac{R_{uv}}{N_s+1}
$$
   其中 $P_z$ 是像素的线性眼空间深度（正值）。上式只对竖直（v）方向成立，水平方向还要再除以宽高比，$R_{uv,u}=R_{uv}/\text{aspect}$，否则 u、v 共用同一个 $R_{uv}$ 会把屏幕空间的采样脚印拉成椭圆。深度越大，同样的世界半径在屏幕上越小；
3. **半分辨率**：AO 是低频效果，可在半分辨率深度缓冲上计算，再配合边缘保留的上采样；
4. 采样点需 snap 到像素中心（先 snap 起点 $S_0$，再 snap 步长），避免采样到 texel 之间的插值结果。

## 可见性：Occlusion Query 与 OBB

### Occlusion Query

先用一个 depth-only pass 把深度写入 z-buffer，再用物体的**包围盒**做遮挡测试：若包围盒的所有像素都被遮挡，则物体不可见；否则可见。

两个工程障碍：

1. 查询本身有开销（多一次提交 + 一次 GPU 同步）；
2. **查询结果有延迟**——从 GPU 回读数据到 CPU 很慢，通常把结果留到下一帧使用，于是遮挡剔除**延迟一帧生效**（快速转身时可能"漏出"或"多剔除"一帧）。

现代替代方案是基于 HZB（Hierarchical Z-Buffer）的 GPU 驱动遮挡剔除，或直接依靠 Early-Z 的带宽优势不做 CPU 侧剔除。

### OBB（有向包围盒）

OBB 用于比 AABB 更紧的视锥/遮挡剔除测试，构造方法是 PCA：

1. 求点集样本均值；
2. 求协方差矩阵（先算各分量相对均值的偏差，利用对称性只算上三角）；
3. 求特征值与特征向量（雅可比迭代法）；
4. 特征值从大到小排序，特征向量同步调整；
5. 取前两个特征向量做施密特正交化（第一个为主轴），第三个由叉乘得到，得到新坐标系。

OBB 相对新坐标系就是一个 AABB，需要存：三个轴向、局部空间的最小/最大点、中心点（相对外部坐标系）。

**射线求交**：先把射线变换到 OBB 的局部坐标系，再按 AABB 的 slab 方法求交——这是所有 OBB 相交测试的通用套路（视锥测试同理：把视锥平面变换到 OBB 局部空间，或反之）。

### Reversed-Z 的补充推导

正文《Reversed-Z 与 `UNITY_REVERSED_Z`》已给出"浮点深度 + NDC 为 $[0,1]$ 才明显受益"的结论及两个前提的推导，此处只补三点正文未展开的内容。

**整型深度是均匀量化。** 整型深度把非线性的 $[0,1]$ NDC 深度做 $2^n$ 级**均匀**量化；因为 NDC 深度本身在近平面附近密集，均匀量化无法改变"越远越粗"的分配。这正是"整型深度不能受益于 Reversed-Z"的直接原因（浮点一侧的推导见正文）。

**量化发生的时机。**

1. FS 里读到的片元深度是 NDC 深度，非 OpenGL 平台值域为 $[0,1]$；
2. NDC 深度的**量化发生在 FS 之后、z-test 之前**；
3. z-fighting 发生在 z-test 阶段，本质是深度缓冲的分辨率不足，而不是 FS 算错了深度。

所以在 FS 里把 NDC 深度转成线性深度时（`LinearEyeDepth` / `Linear01Depth`），必须先按平台判断是否 reversed，否则线性化结果会整体反向。下图是 Metal 平台上的 `_CameraDepthTexture`：远端为 0（黑）、近端为 1（白），正是 reversed-z 的结果。

### 自车写深度与半透遮挡的 ZTest / ZWrite 组合

工程里只用**一张**深度 RT，自车与场景共用：

| 用途 | ZTest | ZWrite | 说明 |
|:--|:--|:--|:--|
| 自车写深度 | `LEqual` | `On` | 车参与深度竞争，写进这张深度 RT |
| 遮挡时的半透叠加 | `Always` | `Off` | 不做深度比较也不写深度，仅按 alpha 混合 |

由此产生两个结论：

1. **必须判自遮挡**：深度图里已经包含车自身的深度，半透 pass 采样深度图时会把自己判成"被遮挡"，需要额外的自遮挡判断（例如再开一张只含场景的深度 RT，或用模板筛选）。
2. **半透 pass 必须在写深度之后**：`ZTest Always` 意味着它不依赖深度测试的先后，正确性完全由绘制顺序和混合保证。

### 分类型遮挡：用 Stencil 过滤遮挡源

"被遮挡就变半透"还要求**按遮挡物类型过滤**：自车可以被 LLN 遮挡，但不应该被 building 遮挡。源笔记记录的做法是**给自车指定一个 stencil 值，按层独享 reference**（场景与车模通过 layer 区分）。至于"遮挡源写深度/模板时打标记、半透 pass 按 stencil 判断这次遮挡是否算数"这一后续流程，是按上述思路推得的（待核实：源只记录到"给车指定了一个 stencil 值"，后续步骤原文未展开）。这本质上是把"深度比较"与"遮挡者身份"两件事拆开：深度回答"谁在前面"，stencil 回答"这个前者算不算"。

### 深度图分辨率与后处理（FSR）的耦合

- 自车若放在 FSR **之后**绘制，半透遮挡会出错：此时深度图不是全分辨率，采样点与颜色像素对不上，遮挡边界出现偏移/块状（推断：源只记录到"深度图不是全分辨率、需要把车提前"，边界表现是按此推得的）；
- 因此要把自车绘制**提前**到 FSR 之前；
- 但 UI 绘制在 FSR 之后，又需要全分辨率的 depth buffer 及其附带的 stencil 来做遮挡。

两条约束方向相反（车要早、UI 要晚），说明**屏幕空间遮挡判断要求深度与颜色同分辨率**；一旦后处理改变了颜色分辨率而深度没跟着变，这套判断就会失效（待核实：该工程最终的取舍方案原文未记录）。
