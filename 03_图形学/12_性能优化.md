# 渲染性能优化：CPU/GPU 分工、批处理、TBDR 与 Shader 成本

> 本文从"一帧里 CPU 和 GPU 各做什么"出发，梳理 Draw call / Batch / 状态切换的真实开销，GPU 的 SIMT 执行模型，移动端 TBDR 的片上行为，以及 Early-Z、分支、Shader 指令、带宽与填充率等具体优化点。Unity 专属的 SRP Batcher 面板与工程设置见《05_Unity》相关篇章；本文只保留通用原理。渲染管线本身见《01_渲染管线》；G-buffer 布局见本文《延迟渲染》一节。

## 性能问题的基本框架

渲染优化没有万能解。性能问题取决于游戏内容、目标硬件、操作系统、驱动，甚至同一场景中相机的位置。唯一可靠的方法是：**先定位瓶颈，再针对性优化**。

一帧的渲染工作可以抽象为三步：

1. CPU 做准备工作：决定哪些对象要画、怎么画；
2. CPU 向 GPU 发送指令；
3. GPU 按指令绘制。

优化的本质是**让 CPU 与 GPU 的负载均衡**，最大化利用有限资源。任何时刻总有一端在等另一端：

- CPU bound：提交批次太多、状态切换太频繁、逻辑/物理/C# 脚本太重；
- GPU bound：填充率、overdraw、Shader 指令、带宽、顶点处理；
- 两者之间的同步点（ReadPixels、`WaitForEndOfFrame`、频繁的 buffer 回读）会把并行变成串行，是最坏的情况。

## CPU 与 GPU 的分工

### CPU 侧

1. **可见性判断**：视锥剔除（frustum culling）、遮挡剔除（occlusion culling）、层/距离剔除。只有通过规则的对象才进入渲染列表。
2. **收集绘制数据**：把每个对象的数据整理成指令，即 Draw call。一个 Draw call 包含一个 mesh 与"如何渲染它"的信息（材质、贴图、Shader 变体等）。设置相同的对象可以被合并进同一个 Draw call，这就是**合批（batching）**。
3. **生成 batch**：CPU 为每个 Draw call 创建数据包（batch），其中不只有 draw call，还有渲染状态等信息。
4. **SetPass Call**：告诉 GPU"下一个材质要用哪套渲染状态"。只有当前后材质确实需要变更状态时才会发出。
5. **Draw Call**：指示 GPU 按最后一次 SetPass 的设置渲染具体材质。
6. **多 pass**：如果一个 Shader 有多个 pass，一个 batch 就要发出多次 SetPass + Draw。

### GPU 侧

1. 收到 SetPass → 切换渲染状态；
2. 收到 Draw → 按 Shader 的顶点/片元阶段执行；
3. 重复直到 CPU 本帧的指令全部完成。

关键结论：**CPU 负责"决定画什么、怎么画"，GPU 负责"真正画"**。两者通过 Command Buffer 解耦，才能并行。

## GPU 的基本概念

### 物理层

| 概念 | 说明 |
|:--|:--|
| SP（Streaming Processor） | 最基本的执行单元，现在多直接用 thread 指代；一个 SP 对应一个 thread |
| SM（Streaming Multiprocessor） | 多个 SP + 寄存器、shared memory、L1 cache、scheduler、LD/ST 单元 |
| Warp | SM 调度与执行的基本单位，通常 32 个 thread；同一 warp 执行相同指令，数据不同 |
| SIMT | Single Instruction Multiple Threads，单指令多线程 |

线程每 32 个组成一个 warp（warp 是调度分组，不是 SP 的物理划分），由调度器分派到 SP 执行；一个 SM 内驻留的多个 warp 共享同一份 memory 与指令单元。取指单元取一条指令，同时发射给 warp 内所有 thread/lane；不需要工作的 lane 被掩码（masked out）置为静默。

### 逻辑层（以 CUDA 为参照）

```text
kernel → grid → block → thread
```

二维索引：

```c
unsigned int xIndex = blockDim.x * blockIdx.x + threadIdx.x;
unsigned int yIndex = blockDim.y * blockIdx.y + threadIdx.y;
```

内存层级：

- 每个 thread 有自己的 register 与 local memory；
- 一个 block 内的 thread 共享 shared memory；
- 所有 block 共享 global memory、constant memory、texture memory；
- global / constant / texture memory 是 context 级、**所有 grid 共享**，不存在 per-grid 隔离；register 与 local memory 是 per-thread，shared memory 是 per-block。

### 执行模型的两个要点

1. **线程数尽量取硬件 warp/wavefront 宽度的倍数**。NVIDIA 是 32，AMD GCN/Vega 是 64（RDNA 上 wave32 是多数着色阶段的默认值，可选 wave64）；不足一个 warp 时仍会占满一个 warp，多余 lane 静默，利用率下降。
2. **分支以 warp 为单位发散**。若一个 warp 内一半线程走 `if`、一半走 `else`，GPU 会先执行 `if` 分支（另一半被掩码），再执行 `else` 分支（前一半被掩码），总时间近似为两分支之和。

（原稿有误，已更正：原稿写"一个 block 含 16 个 warp，最多 512 个线程"，这是早期 CUDA 的规格。现代 CUDA 的 block 上限是 **1024 threads / 32 warps**（具体架构仍有差异，**待核实**目标 GPU 的占用率表）。占用率（occupancy）还受寄存器、shared memory 限制，不是线程越多越好。）

SIMT 与 CPU 的 SIMD 的区别：SIMD 要求开发者把数据凑成固定长度的矢量，且无法并行执行有条件跳转；SIMT 允许每个线程有独立的分支状态（通过掩码实现），编程模型更接近标量线程。

## Draw call 的真实开销

每一次渲染 API 调用都会经过：

```text
Application → Runtime → Driver → Video Card (GPU)
```

每一步都有耗时。CPU 性能影响 Application/Runtime/Driver；GPU 性能影响顶点处理、Shader 计算以及帧缓冲相关操作（Blend、MSAA 等）。

关键机制：Runtime 不会每次 API 调用都立刻通知 GPU，而是把调用转换成**设备无关的命令**并缓存在 **Command Buffer** 中：

- Direct3D 的 Runtime 是独立的 DLL 集合；
- OpenGL 的 Runtime 与 Driver 整合在一起，所以"Command Buffer 在 Runtime 还是 Driver"两种说法都对。

Command Buffer 有两个作用：

1. 让 CPU 与 GPU 并行工作；
2. **减少 CPU 用户态/内核态切换**。命令从 Runtime 到 Driver 要发生模式切换，这是非常昂贵的操作；缓冲后批量提交可以把切换次数降到最低。

**关于"状态切换会强制刷新 Command Buffer"**：这个说法成立的范围是 D3D9 那类**批量提交**模型——runtime 需要把此前累积的 draw 与状态打包提交，状态一变就结束当前批次。现代 API（D3D11/12、Metal、Vulkan）不是这样：`Set*` 只是命令流中的一条记录，既不刷新命令缓冲，也不要求先前的 draw 已在 GPU 上执行完；只有资源写后读这类 hazard 才需要屏障，而那是 GPU 端等待，不是 CPU 刷新缓冲。

于是每次状态切换的主要开销是：

1. 把 Draw call 与状态设置翻译成设备无关命令（含驱动校验）；
2. 在早期（内核态驱动）模型中，批次提交还要陷入内核——现代用户态驱动已把这项成本摊销到每帧少量提交上。

Command Buffer 不是无限累积的，常见的刷新时机有四类：

1. Buffer 写满；
2. 新到来的渲染状态与缓存中的不一致（切换 Shader、切换 RenderTarget）；
3. 需要把显存中的 RT 回读到内存（任何读回都要求此前命令已执行完）；
4. 显式调用 `glFlush` / `Flush`。

> 上列四条来自不同 API 的文档，不宜当成同一套规则："buffer 写满"是 D3D 侧 runtime 的批量提交描述，"回读 RT"主要对应 GL 的阻塞式读回语义，第 4 条也分属两个 API（`glFlush` 是 GL，`Flush` 是 D3D）。各条在目标平台上的确切触发条件与等价性**待核实**，这里只取"状态变更会强制刷新"这一共性。

所以合批的收益是**少几次状态记录与驱动校验**（在 D3D9 式模型下则是少几次批次提交/内核切换），而不是单纯的"少调几次 API"。

历史上内核态切换确实是大头；现代用户态驱动下，主要成本转为命令翻译与驱动侧的校验/去重。这也解释了一个经典实验现象：如果在每次 Draw call 之间故意切换状态，就测不出 batch 的真实吞吐——旧模型里 Command Buffer 会被切碎成很小的批次。

## Batch（批次）

### 定义

调用一次绘制接口（D3D 的 `DrawPrimitive` / `DrawIndexedPrimitive`，OpenGL 的 `glDrawArrays` / `glDrawElements`），向 GPU 提交使用**相同渲染状态**的一批三角形，称为一个渲染批次。

从 API 角度看，Batch 与 Draw call 等价；在引擎语境中，Batch 通常指"打包之后的 Draw call"。

### 经典的 batch size 实验

NVIDIA 内部分享的测试（硬件较老，但结论仍成立）：横轴是 `Triangles/Batch`，纵轴是 `Million Triangles/s`。

![](../../技术笔记/assets/69DEB73FE8354B529A3BF298455A18AC.png)

结论：

1. 每个 batch 的三角形越多，每秒渲染的三角形越多；
2. 在约 **130 triangles/batch** 之前，不同 GPU 的曲线基本重合——瓶颈在 CPU，GPU 有富余；
3. 超过该点后，高端 GPU 继续线性增长，低端 GPU 开始饱和——瓶颈转移到 GPU。

换一组 CPU/GPU 组合再测：

![](../../技术笔记/assets/03B985A783144B8FAD889AAA8A980659.png)

- 每秒能处理的 **batch 数量**与 CPU 性能强相关；
- GPU 性能对"每秒 batch 数"影响很小；
- batch 大小对"每秒 batch 数"几乎没有影响。

**结论：CPU 性能决定提交 batch 的效率；在不给 GPU 造成渲染压力的前提下，batch 越大越好。**

类比：缆车速度恒定，每节车厢装 1 人 vs 装 2 人，单位时间运送人数直接翻倍。每次提交 batch 的 CPU 成本是固定的，所以"少提交、每次多装"就是优化。

### 合批方式

| 方式 | 做法 | 代价/限制 |
|:--|:--|:--|
| Static Batching | 运行前把静态对象的网格合并成更大的网格 | 材质必须相同；需要额外存储合并后的网格；内存上升 |
| Dynamic Batching | 运行时合并视野内的动态小网格 | 合并本身有 CPU 开销；只适合顶点数很少的网格 |
| GPU Instancing | 一次 draw call 用同一 mesh 画多个实例 | 需要相同 mesh + 相同材质；每实例数据走 constant buffer |
| SRP Batcher | 不为每个 draw call 重设/上传材质 CBuffer | 不减少 draw call，只减少 draw call 之间的 CPU 工作 |

### GPU Instancing 的通用原理

把"每个实例不同"的数据（变换矩阵、颜色、UV 偏移、lightmap index 等）放进一个 per-instance 的 constant buffer，一次提交给 GPU；顶点着色器用 `SV_InstanceID` 索引自己的那份数据。

要点：

- per-instance 数据走常量缓冲/结构化缓冲；常量缓冲路径大小有限（常见上限 **64 KB**），结构化缓冲没有这一限制，所以实例属性仍不宜无限多；
- 修改材质属性（颜色、cutoff 等）通常不引起渲染状态切换，因此可以走 instancing；但切换 Shader 变体、换贴图、开关 Blend 会破坏 instancing；
- 若某个实例缺少某属性，一般回退到材质默认值（没有默认值则为 0）；
- 深度排序、材质改变会打断 instancing。

### SRP Batcher 的通用原理

传统路径每次 Draw call 都要 `Setup CBuffer → Upload CBuffer`。SRP Batcher 让**每个材质在显存中占有固定的 CBuffer**；只要材质内容不变，CPU 就跳过 setup/upload。

因此：

- 它**不减少 Draw call 数量**，而是降低 Draw call 之间的 CPU 开销；
- 同一 batch 内 draw call 越多越划算；
- 用 `MaterialPropertyBlock` 逐对象改属性会打断合批（每个对象变成独立材质 CB）；
- 合批序列中插入一个其它材质的对象会"切断"前后两段。

> 实现细节（`UnityPerMaterial`、Shader 变体兼容性、优先级 `SRP Batcher | Static Batching > GPU Instancing > Dynamic Batching`）属于 Unity 专属内容，见《05_Unity》。

## TBDR（Tile-Based Deferred Rendering）

### 为什么移动端要走 tile

- GPU 的片上存储（SRAM / L1 / L2）很小，完整 FrameBuffer 只能放在显存（DRAM）。
- 对显存的频繁访问消耗大量**带宽**，而带宽是移动端功耗的最大来源之一。
- 因此移动端 GPU 把画面切成 tile（常见 16×16/32×32，具体因 GPU 而异，**待核实**），让一个 tile 的 FrameBuffer 能完整放进片上 SRAM。
- 这样像素的 test / read / write / blend 都在 SRAM 内完成，最后再整体写回 DRAM，带宽大幅下降。

### TBR 的工作方式

1. 图元装配后的三角形进入 **triangle cache**；
2. 对每个 tile 维护一个 **triangle list**（只存索引），记录需要在该 tile 内绘制的三角形；
3. 等所有几何提交完，再逐 tile 做光栅化与 per-fragment 操作。

"化整为零"是核心：巨大的 FrameBuffer 被分解成许多能被 SRAM 容纳的小块。

### TBR → TBDR：多出来的 D

（原稿有误，已更正：这里的 **DR 指 Deferred Rendering（延迟渲染）**，但它延迟的不是"光照"，而是**逐 tile 的着色**——等一批 draw call 的几何都到齐后，才在 tile 内决定哪些片元存活，只对最终可见的片元着色。它不是 G-buffer 式的软件延迟着色。以 Apple GPU 为例，其 HSR 在 fragment 着色前完成剔除；但**不同厂商 TBDR 的剔除阶段与粒度并不相同**（有的在片元前、有的只做粗粒度 tile 级剔除），不能把某一家实现当作 TBDR 的定义。）

- 软件延迟渲染针对**一个 draw call 内部**：先写 G-buffer，再统一光照。
- 硬件延迟渲染针对**一批 draw call**：在 FrameData 中筛选真正会写入 FrameBuffer 的片元，滤掉大量无效绘制。

TBR 不能"来一个 Command Buffer 就执行一个"，因为后面的命令可能影响整个 FrameBuffer，最坏情况每个 draw call 都要把所有 tile 搬进搬出。所以 TBR 的策略是：CPU 命令先只做顶点处理，暂存结果，等到**不得不刷新**时才光栅化：

- swap back/front buffer；
- `glFlush`；
- unbind framebuffer；
- 其它需要完整 FrameBuffer 的操作。

### 片上行为带来的性能结论

| 操作 | 在 TBDR 上 | 原因 |
|:--|:--|:--|
| Blending | 很快 | 读写都在 tile 的 SRAM 内，不产生 DRAM 往返带宽 |
| MSAA | 很快 | 多采样在片上完成，只在 resolve 时写回 |
| Alpha Test | 很慢 | alpha 只有跑完 PS 才知道，HSR 无法提前剔除，且会打断后续 draw call 的 early-Z/HSR |
| 频繁切换 RenderTarget | 很慢 | 每次切换都强制把被触及的 tile 按 load-op 载入、渲染后回写 |
| 不 clear | 变慢 | 每个 tile 初始化时要先把原内容从 DRAM 拷回来 |
| 大量 draw call / 顶点 | 变慢 | FrameData 随顶点量与 draw call 增长，可能大到放不下而被迫换出 |

优化建议：

1. **不要在一帧里频繁切换 framebuffer**；
2. **不用的 framebuffer 及时 clear**：`glClear` 可以清空积攒的 FrameData，避免最后一批无效绘制；对 TBR 来说，clear 还能省掉 tile 初始化时的 DRAM 回读；
3. **每帧渲染前尽量 clear**：IR（Immediate Rendering）模式下如果确定整屏会被覆盖可以不 clear，但 TBR 不 clear 就要回读；
4. 减少 draw call 与顶点数；
5. 利用 HSR：HSR 在片元着色前剔除被遮挡的片元；stencil test、scissor test 是另一套与之独立的机制，可以让整个 tile 或整个 draw call 的绘制被提前筛掉；
6. **渲染顺序：opaque → alpha-test → blending**。alpha-test 放在不透明体之后，避免它挡住更多不透明体的 Z 预剔除；blending 最后，且由远及近。

TBR 的代价：存在延迟。想在渲染过程中读回 FrameBuffer 结果会有额外等待。

## IMR 与 TBDR 的架构取舍

独立显卡长期以 **IMR（Immediate Mode Rendering，立即渲染）** 为主，移动端以 **TBDR** 为主。两者的差别不是"谁更先进"，而是**把芯片面积花在哪里**。

| 维度 | IMR | TBDR |
|:--|:--|:--|
| 执行方式 | 按提交顺序逐 draw 执行，图元提交即光栅化 | 先缓存几何，再按 tile 批量光栅化与着色 |
| 片上存储用途 | 主要给 cache/寄存器，FrameBuffer 在显存 | 大量 SRAM 用于容纳整个 tile 的 FrameBuffer |
| 带宽压力 | 无 tile 级片上 FB：多 pass/overdraw 的 DRAM 往返与功耗显著更高 | 小：tile 内读写都在片上，末尾整体写回 |
| 设计目标 | **峰值性能**：同面积放尽可能多的运算单元 | **能效比**：同面积放尽可能多的存储单元 |
| 擅长 | 高分辨率、海量几何、复杂后处理、频繁切换 RT | 低带宽、MSAA、blending、功耗敏感场景 |
| 弱点 | 带宽与功耗高；overdraw 直接变成显存往返 | 有延迟；tile 列表与参数缓冲带来额外存储/带宽开销；alpha-test 与频繁换 RT 代价高 |

由此得到几条跨平台结论：

1. **同一套优化在两端收益不同**。桌面"减少 draw call"主要是省 CPU；移动端同样的改动还顺带降低 tile 列表与带宽压力。
2. **桌面换 RT 便宜，移动端极贵**。桌面上多 pass 后处理是常规操作；移动端应尽量用 `framebuffer fetch`/`input attachment` 或合并 pass，避免每个 pass 都把 tile 写回 DRAM 再读回。
3. **移动端 MSAA 常比后处理 AA 划算**（片上 resolve），桌面端相反——高分辨率下 MSAA 的带宽与存储成本很高。
4. **不要假设"桌面一定 IMR"**。
   - **更正**：原文称"桌面平台通常是 IMR"，该说法只对独立显卡成立，不能作为平台级结论。
   - **补充（非源稿）**：Apple Silicon Mac 采用 tile-based 架构，判断应以目标设备而非"桌面/移动"这一标签为准；具体型号的 HSR 行为**待核实**。

## Alpha Test 与 Blending 的取舍

两种处理透明的方式，行为完全不同：

**Alpha Test**

- 片元 alpha 不通过阈值就 `discard`，通过则按不透明方式写入颜色与深度；
- alpha 只有跑完像素着色器才知道，所以**无法用 Early-Z 预剔除**；
- 在 TBDR 上会打断 HSR，是明确的性能瓶颈；
- 好处：可以写深度、可以不排序、没有混合排序问题。

**Blending**

- 用当前片元 alpha 作为混合因子，与已写入的颜色混合；
- 必须**关闭深度写入**（`ZWrite Off`），只保留深度测试；
- 必须**由远及近**渲染，否则混合结果错误；
- 不能关闭深度测试：半透明物体若在不透明体后面，仍应被正确剔除；
- 在 TBDR 上反而很快（片上混合）。

片元测试顺序（固定管线）：

```text
scissor test → alpha test → stencil test → depth test → blend
```

优化含义：能不透明就不透明；必须透明时优先 alpha-test（若不需要半透过渡），并把 alpha-test 对象排在不透明体之后、blend 之前。

## Early-Z 与 Pre-Z（性能视角）

Early-Z 的定义、深度测试流程与 Pre-Z 的实现细节见《02_光栅化与深度可见性》；这里只保留与 overdraw/HSR 相关的性能结论。

- **Early-Z 的收益**：把深度测试提前到片元着色器之前，失败的片元不再执行 PS，从而减少 overdraw 的着色成本；在 TBDR 上它与 HSR 一起决定被遮挡的片元能否被提前剔除。
- **Pre-Z**：单独跑一个只写深度的 pass 提前建立深度缓冲，后续绘制时深度测试可以尽早剔除；代价是多一次几何提交与一次深度写入。在 alpha-test 场景中，可以先跑一个只做 Z + alpha test 的 pass 把深度写好，正式绘制时关闭 alpha test，Early-Z 就能继续生效。

Early-Z 失效的常见原因（失效即 overdraw 成本回升）：

- Shader 中使用了 `discard` / `clip()`（alpha test）；
- Shader 写入了深度（`SV_Depth`；可用 `SV_DepthGreaterEqual` 保留 early-Z）；
- 开启了深度写入且同时使用 `discard`（不写深度时两者可以共存）；
- 关闭了深度测试或深度写入配置不当；
- `alpha-to-coverage`：覆盖率由像素着色器输出的 alpha 决定，必须在着色之后才能解析，因此 early-Z 无法提前剔除；
- 依赖前序结果的混合（对同一像素读改写）只影响能否重排与提前写深度，并不关闭 early-Z 测试。

（原稿有误，已更正：原整理稿把"开启 multi-sampling"列为 Early-Z 失效条件，此条不准确。MSAA 本身并不必然禁用 early-Z；现代 GPU 可以做 per-sample early-Z。真正容易出问题的是 `alpha-to-coverage`、`discard`、写 `SV_Depth` 以及需要 pixel quad 完整执行的着色。具体行为依 GPU 架构而定，**待核实**。）

## LOD 与代理模型

LOD 的本质是**按屏幕贡献分配预算**：一个物体在远处只占几十个像素，却仍按近处的面数、贴图精度和 Shader 复杂度绘制，多出来的顶点、采样与填充全是纯浪费。

取舍要点：

1. **切换依据是距离**（源文的说法）。**（补充）**实践中更稳的依据是屏幕空间占比而非纯世界距离（阈值随项目而定，**待核实**）：同一个距离阈值在窄 FOV、宽 FOV、不同分辨率下对应的像素数差别很大；按包围球投影后的像素直径切换更稳定。
2. **切换要可见但不突兀**。两级面数差太大时会出现 popping；可用抖动淡入（dither + alpha test）或短暂过渡掩盖，代价是过渡期间要同时持有两级资源。
3. **LOD 不只作用于颜色 pass**。阴影、深度预 pass、反射探针各有自己的可见性集合，远处物体的 shadow caster 往往可以更早降级甚至剔除。
4. **低级别不只是"低模"**：还包括更低分辨率的贴图与 mip 偏置、简化的 Shader（少采样、少光照项）、关闭法线贴图/视差，最远处退化为 impostor（billboard）。

### 代理模型（Proxy Mesh）

高面数主角/Boss 的阴影 pass 不需要与颜色 pass 同等精度：单独做一个简化的主角 mesh，只作为 shadow caster 参与 shadowmap 生成，颜色 pass 仍用完整模型。

这把"可见精度"和"投影精度"解耦了：阴影的视觉容差远大于轮廓，降到几十分之一的面数通常看不出差别（**补充，具体倍数待核实**），却能显著减少 shadow pass 的顶点处理与光栅化开销。同一思路还可用于（**补充**）：

- 反射/环境探针渲染时，远处物体改用低模；
- 遮挡剔除的 occluder 代理，用简化几何代替高模参与深度测试。

## 分支（Branch）与条件转移（Conditional Move）

### CPU

- `if` 不一定生成 branch，编译器可能生成 **conditional move**（`cmov`）；
- **分支预测**成功率高时，branch 更快；预测失败要清空流水线，惩罚严重；
- 条件判断值只有运行时才知道时，流水线必须暂停等待结果。

CPU 的设计目标是**优化单线程延迟**，因此有分支预测、猜测执行等复杂机制。

### GPU

GPU 的设计目标是**优化多线程吞吐量**，不关心单线程快慢。它把芯片面积大量用于计算单元，取消了分支预测与猜测执行，因此：

- 一个 warp 内的线程**锁步执行**同一指令；
- 遇到分支时，先执行满足条件的那部分（其余掩码），再执行另一部分（前一部分掩码）；
- 因此分支的实际耗时约等于 `if` 与 `else` 两条路径之和，而不是像 CPU 那样只走一条。

Shader 中一个典型例子：

```hlsl
void func(int count, int breakNum)
{
    for (int i = 0; i < count; ++i)
    {
        if (i == breakNum)
            break;
        else
            // do something
    }
}
```

每个线程的 `count` 与 `breakNum` 不同，最快完成的线程必须等最慢的线程，warp 才能取下一条指令。

### 静态分支 vs 动态分支

- **静态分支**：条件在编译期即可确定（`#if`、shader keyword 等），编译该变体时就把未选中的代码消除，指令流里不再留条件判断，因此**不产生任何运行时开销，也不会在运行时再分裂变体**（变体由 keyword 组合在打包期决定，见本文《变体的数量控制》一节）；
- **动态分支**：条件在运行时才知道。若条件值逐片元变化（varying / 纹理 / 导数），warp 内会发散，两条路径都要执行；若条件值是 uniform（整个 draw call 相同），则不发散，**只产生控制流开销**——影响 wave 统一性与循环提前退出的效果，而**不分裂变体**。

优化的重点是**消除动态分支**。对简单二选一，可以改写成无分支形式：

```hlsl
if (cx > cy) x = a; else x = b;

// 无分支写法（仅 cx ≠ cy 时严格等价：step 在 x ≥ edge 时返回 1，
// cx == cy 时上式取 b、此式取 a；与 `x = (cx > cy) ? a : b;` 完全等价）
x = lerp(b, a, step(cy, cx));
```

`step` 返回 0/1，`lerp` 做选择；GPU 上一条 `sel`（SPIR-V）或 `movc`（D3D SM4+）指令即可完成。

> **注意**：不要机械地把所有 `if` 都改写成 `lerp`。现代编译器对简单条件本来就会生成 `select`；真正昂贵的是**大段**的 `if/else` 与循环内的动态 `break`。Uniform 分支（整个 draw call 取值相同）基本免费，改成无分支反而可能增加 ALU。

## Shader 优化

### 指令与精度

- 优先使用半精度（`half`/`mediump`）做颜色、UV、法线等对精度不敏感的量；移动端 half 的吞吐通常是 float 的 2 倍（**待核实目标 GPU 的 FP16 比率**）。
- 避免复杂数学函数：`pow`、`exp`、`log`、`sin`/`cos`、`atan2` 都是多周期指令；能用多项式近似或查表就用。
- 用内置函数（`normalize`、`dot`、`saturate`、`mad`）让编译器生成最优指令；手写展开往往更差。
- 注意 `normalize` 在低精度下可能出现除零；必要时加 epsilon。

### 纹理采样

- 每次采样都是一次寻址 + 滤波 + 带宽；能合并到一张图集的就合并（通道打包：Roughness/Metallic/AO 放一张）。
- 尽量使用 mipmap 与各向异性过滤，减少 cache miss 与闪烁。
- 避免在循环中做依赖梯度的采样（`tex2D` 隐式 LOD）；循环内用 `SampleLevel`/`SAMPLE_TEXTURE2D_LOD` 显式指定 mip。
- 依赖屏幕导数的采样（`ddx/ddy`）会把 2×2 quad 绑定在一起，增加无效线程。

### 顶点着色器的限制

顶点着色器**无法访问相邻顶点**：

- 顶点按索引由 IA/PA（输入装配/图元装配）拆成 batch，按硬件 warp/wavefront 宽度锁步执行（NVIDIA 32；AMD GCN 64，RDNA 上 wave32 是多数着色阶段的默认值，可选 wave64），线程间不能通信；
- 因此 VS 中无法计算屏幕空间导数，也就无法自动选择 mipmap；必须显式 `SampleLevel`：

```hlsl
TEXTURE2D(_NoiseMap); SAMPLER(sampler_NoiseMap);
_NoiseMap.SampleLevel(sampler_NoiseMap, noiseUV, 0);
```

片元着色器之所以能访问邻居，是因为计算 mipmap 层级需要 `ddx/ddy`：三角形被光栅化成片元后，每 4 个相邻片元组成一组（2×2 quad），8 个小组共 32 个线程组成一个 warp。即使只有一个片元被覆盖，也要"无中生有"补出另外 3 个，代价是 3 个线程。

### 其它

- 避免 `discard`：它会禁用 Early-Z、打断 TBDR 的 HSR、并强制 quad 完整执行。
- 减少 varying 数量：每个 varying 都占插值器与寄存器带宽。
- uniform 尽量组织成数组/常量缓冲一次上传；数据传输的时间远小于逐项设置。
- 共用材质、共用 Shader 变体，减少状态切换与变体爆炸。
- LOD：距离远的物体用低模、低分辨率贴图、简化 Shader（取舍见本文《LOD 与代理模型》一节）。

## Shader 编译、变体与分级

### 编译期：表达式引用分析

编译器不会逐行翻译源码，而是从**输出**（最终写入的颜色、深度等）反向遍历，构建一张表达式依赖图：

- 只有被输出直接或间接引用的变量、函数才进入最终指令流；
- 未被引用的中间变量、分支、函数调用会被**整体坍塌丢弃**（dead code elimination）。

两个工程含义：

1. **中间结果要"可被丢弃"**。只影响调试视图的计算写在 `#if DEBUG_VIEW` 里，发布变体连指令都不会生成；反过来，若为了"以后可能用到"先把值算出来存进参与最终输出的变量，编译器就删不掉。
2. **不要指望编译器删掉有副作用的东西**。纹理采样本身可被删除；真正阻止消除的是 `discard`、UAV/原子写入、TGSM 写入。

这也解释了为什么"多写几个 `lerp`"通常不比 `if` 差：两者的表达式图规模接近，最终由编译器的指令选择决定（见上文《分支》一节）。

### 变体的数量控制

（补充：通用引擎实践，非源稿）

Shader 变体来自 keyword/宏组合：$n$ 个独立 bool keyword 最坏产生 $2^n$ 个变体。变体爆炸的代价不只是包体与编译时间：

- 运行时更容易发生 Shader 变体切换，打断合批；
- 让分级难以落地（**推断**）——每一级都要再乘一遍 keyword 组合。

控制手段（通用原则，具体 API 见《05_Unity》）：

1. 用**枚举式**的单一 keyword 代替多个相互独立的 bool（例如 `QUALITY_LOW/MID/HIGH` 三选一，而不是 `USE_FOG` + `USE_SH` + `USE_IBL` 自由组合）；
2. **编译期能定的放 `#if`，运行时才定的留 uniform 分支**：后者不发散、几乎免费，且不增加变体数；
3. 打包阶段按目标设备裁剪变体集合，不全量携带（**待核实**各管线提供的裁剪工具链细节）。

### Shader 分级（Quality Tier）

同一功能按效果/成本提供多种实现，按档位选择，是"一套内容覆盖低端到高端"的标准做法。典型例子：

| 功能 | 低档 | 中档 | 高档 |
|:--|:--|:--|:--|
| 雾 | 线性雾（一次 `lerp`） | 指数雾 | 高度雾（含高度积分/多层采样） |
| 球谐光照 SH | 逐顶点计算，插值到片元 | 顶点与片元混合 | 逐片元计算 |
| IBL 高光 BRDF | 数值拟合（解析近似） | LUT 纹理采样 | —（源文只给两种实现） |

工程上一般分 5 级左右，效果从低到高、指令数逐级递增。上表只是"低/中/高"三档的示例，**不能代表 1–5 级的具体划分**。

> **待核实**：源文只给了级数（5 级）与"效果由低到高、指令数逐级递增"这条单调性，**未给 1–5 级各自的开关明细**，因此这里不编造每级内容；逐级划分（哪一级开哪些采样、哪些光照项、哪些后处理）需要从项目实现或引擎的质量档配置中补录。

落地要点：

1. **级别在运行时是常量**。选定后走对应的独立变体或静态分支，不要在每个片元里判断"当前是第几级"。
2. **分级要覆盖整条链路**，而不只是光照：后处理、阴影级联数、探针分辨率、粒子预算都要联动，否则省下的 GPU 时间会被别处吃掉。
3. **默认档位按设备能力选择**（GPU 型号/带宽/分辨率），并允许玩家手动覆盖；自动选择需要实测或设备白名单（具体策略**待核实**）。
4. **验证要看最差档位**。低档指令数虽少，但可能牺牲了对 early-Z/HSR 的友好性（例如用 blend 代替 discard），必须单独 profile。

## 如何评测 Shader 的效率

原则：**让该 Shader 成为瓶颈，然后测吞吐量**。但有很多干扰因素：

1. 目标平台（硬件、OS）不固定；
2. 屏幕分辨率可变；
3. 游戏过程中变数多（渲染 1 个近处 NPC 与 10 个远处 NPC 的瓶颈完全不同），**瓶颈经常改变**。

相对容易评测的是屏幕后处理：瓶颈在 pixel shader、纹理采样、带宽，成本与屏幕分辨率成正比。

粗糙但有效的判断方法：

- 看 Shader 编译后的汇编**指令数**；
- 数**纹理采样次数**（需要几张纹理、每像素几次 fetch）；
- 在目标分辨率下做 A/B：只改一个变量（采样数/指令数/RT 格式），观察 GPU 时间。

工程上的正确做法是**以完整游戏帧为单位评测**，而不是孤立评测每个 Shader：

- 变数太多，瓶颈会漂移；
- 可以做自动化：让 player 在场景中按固定路线行走，记录帧率、CPU/GPU 时间、Draw call、Batch 数；超出阈值就通知团队。

常用工具与指标：GPU 厂商的 profiler（RenderDoc、Xcode GPU Capture、Snapdragon Profiler、Arm Mobile Studio）、GPU 时间戳、overdraw 视图、纹理/带宽计数器。注意 profiler 本身会改变时序，测量值要多次采样。

## 渲染性能优化清单

### 减少 CPU 与 GPU 的数据交换

1. 合批；
2. 减少顶点数、面片数；
3. 尽量避免每帧提交数据，能移到 GPU 端的就移过去（GPU driven）；
4. 减少渲染状态设置与查询（查询会回读参数，例如 `glGetUniformLocation`）；
5. 避免从显存回读数据（`ReadPixels`、`GetData`、occlusion query 的同步等待）。

### 减少 overdraw

overdraw 要在三个层级同时治理：先做高层级剔除，单次收益通常更大（**推断**）：

- **物体级**：相机视锥剔除、遮挡剔除、渲染排序（不透明体从前向后）；
- **多边形级**：视锥/齐次裁剪把屏幕外的三角形在装配阶段就裁掉，不进入光栅化；
- **像素级**：Early-Z / Pre-Z 让被遮挡的片元不执行 PS。

1. 避免 alpha test；
2. 避免不必要的 blend；
3. 开启深度测试，不透明体从前向后画；
4. 开启剔除：背面剔除、遮挡剔除、视口/小物体剔除；
5. 用 Pre-Z / depth prepass 提前建立深度。

### 减少状态切换

- 按材质/Shader/贴图排序，把使用同一状态的物体放在一起；
- 合并材质与贴图（图集、通道打包）；
- 减少 Shader 变体（keyword 组合爆炸会破坏合批）；
- 避免频繁切换 RenderTarget，必须切换时一次性把相关 pass 做完。

### 其它

- 对 uniform 传值尽量组织成数组，减少 API 调用；
- 尽量使用内置函数；
- LOD 与 impostor；
- 控制透明层数与粒子数量；
- 移动端优先考虑带宽与填充率，而不是 ALU。

## 延迟渲染（Deferred Shading）

### 基本思想

把光照/着色计算推迟到第二步，避免对同一像素重复着色。

1. **几何 pass**：只把几何信息写入 G-buffer（位置、法线、纹理坐标、反射系数、材质参数等），不做光照；
2. **光照 pass**：从 G-buffer 读取信息，对每个屏幕像素计算一次最终颜色。

为什么能省：两个多边形重叠时，前向渲染会对该像素着色两次，但只有一次结果可见（混合关闭时）。延迟渲染在所有几何处理完之后再着色，每个像素只算一次。

### 前向 vs 延迟的复杂度

前向渲染：每个物体 × 每个光源，复杂度 $O(n\cdot m)$。光源数量对成本影响巨大，适合户外等光源较少的场景。

经典例子：1000 个三角形沿 Z 轴排列，屏幕只能看到最前面的一个。

- 前向：逐个片元深度测试，通过的就做光照；最坏情况 1000 次深度测试全部通过，做 1000 次光照，其中 999 次被覆盖。
- 延迟：第一个 pass 只写 G-buffer（含深度），第二个 pass 只对最终可见的像素做一次光照。

### G-buffer 布局（示例）

| RT | 内容 | 格式建议 |
|:--|:--|:--|
| RT0 | Albedo（RGB）+ Material Mask（A） | RGBA8 / sRGB |
| RT1 | Normal（视图空间，RGB）+ 其它 | RGBA8 或 RGB10A2 |
| RT2 | Metallic / Roughness / AO / 高度等 | RGBA8（通道打包） |
| Depth | 深度 + Stencil | D24S8 / D32 |

早期实现会存世界坐标（`RGB32F`），非常浪费带宽；现代实现只存深度，在光照 pass 里用逆投影重建位置。

### 优点

1. 光照开销与场景复杂度无关，只与屏幕像素数和光源数有关；
2. Shader 可以访问深度及其它像素信息（SSAO、SSR、Decal、Bloom 都受益）；
3. 材质与光照的 Shader 解耦，光照模型可以集中维护；
4. 每个光源只增加一次覆盖其屏幕包围区域的光照计算（按 light volume/模板只处理覆盖像素），总开销 ≈ min(覆盖面积, 屏幕) × 光源数（对大量点光源非常划算）。

### 缺点

1. **不能硬件 MSAA**：G-buffer 光栅化时几何信息已经丢失，MSAA 需要知道三角形覆盖了哪些 coverage sample；只能靠后处理 AA（FXAA/TAA/SMAA）。
2. **无法直接渲染透明体**：G-buffer 每个位置只记录一个可见像素，透明体需要每像素记录多层；通常先渲染不透明体，再单独用前向渲染透明体。
3. **占用大量显存带宽**：多张屏幕大小的 Render Target，写入 + 读取都是带宽；移动端尤其不友好。
4. **只能用一套 lighting pass**：几何信息写入 G-buffer 后，像素归属哪个 mesh、用什么材质已经无从得知，无法为不同材质走不同的光照 Shader。

### 移动端与 TBDR

- 移动端几乎不用软件延迟渲染：G-buffer 带宽代价过高；
- TBDR 在硬件层已经做了"延迟"（HSR + 逐 tile 着色），软件延迟渲染的必要性下降；
- 移动端实时点光源很少，前向渲染的 $O(n\cdot m)$ 通常可以接受。

## 带宽与填充率

后处理与移动端优化最终都会落到这两个词上。

### 填充率（Fill Rate）

单位时间能处理的片元/像素数量，通常由 ROP（Render Output Unit）与 Shader 吞吐共同决定：

$$
\text{fill rate} = \frac{\text{fragments}}{\text{second}}
$$

影响因素：

- **overdraw**：同一像素被着色多次。透明、粒子、全屏特效是重灾区；
- **Shader 复杂度**：每像素指令数、采样数；
- **分辨率**：成本与像素数成正比；
- **RenderTarget 数量**：MRT 会成倍增加写入。

### 带宽（Bandwidth）

单位时间读写显存的字节数：

$$
\text{BW} \approx \sum_{\text{pass}} \left( \text{pixels} \times \text{bytes per pixel} \times (\text{reads}+\text{writes}) \right)
+ \text{texture reads}
$$

降低带宽的手段：

1. **减少 RenderTarget 数量与格式**：RGBA8 优于 RGBA16F，能打包就打包；法线用 octahedral 编码存两通道。
2. **避免不必要的全屏 pass**：能合并的合并，能在半分辨率做的就半分辨率。
3. **利用片上内存**：TBDR 的 tile memory、Vulkan/Metal 的 `framebuffer fetch`/`input attachment`、`subpass` 可以避免把颜色写回 DRAM 再读出来。
4. **压缩纹理**：ASTC/ETC2/BC，减少采样带宽与显存占用。
5. **避免 resolve 与拷贝**：MSAA resolve、`CopyTexture`、`Blit` 都是全屏带宽操作。
6. **避免回读**：任何 `ReadPixels`/`GetData` 都会强制同步并产生往返带宽。

### 一个实用的判断顺序

遇到 GPU 瓶颈时，按以下顺序排查：

```text
分辨率/RT 格式 → overdraw → 纹理采样与带宽 → Shader 指令 → 顶点/几何
```

因为前两项的收益通常是数量级的，而指令级优化往往是十几个百分点。

本附录只收录工作日志里**前文尚未覆盖**的技术结论、公式与工程做法；与正文重复的部分不重复叙述，只给交叉引用。

### 显存带宽的定量口径

工作日志给出的估算式是：

$$
\text{BW}=\frac{f_{\text{mem}}\times W_{\text{bus}}}{8}\quad(\text{Byte/s})
$$

- $f_{\text{mem}}$：显存等效数据传输率（MT/s），不是物理时钟；
- $W_{\text{bus}}$：显存位宽（bit）；
- 除以 8 是把 bit 换算成 Byte。

（原稿写"带宽 = 时钟频率 × 位宽 / 8"，标注为"时钟频率"不准确：DDR/LPDDR 每个时钟周期传输两次，应取等效数据率，否则结果会少算一半。已更正为 $f_{\text{mem}}$ 记法。）

举例：LPDDR4X-4266、64 bit 位宽的移动 SoC，理论峰值带宽约

$$
4266\times10^{6}\times\frac{64}{8}\approx 34.1\ \text{GB/s}
$$

这是**整颗 SoC 共享**的带宽，CPU、GPU、显示控制器、ISP 都要分。用它做量级校核比记具体数字更有用：

- 1920×1080 的 RGBA8 全屏 RT 约 $1920\times1080\times4\approx 8.3\ \text{MB}$；
- 一次"读 + 写"的全屏 pass 约 16.6 MB；60 fps 下单这一项就是约 1 GB/s；
- 如果一帧有 10 个这样的 pass，仅此一项就约吃掉三成带宽预算；叠加纹理采样与中间 RT 后可能过半。

所以正文的"减少 RT 数量与格式""避免不必要的全屏 pass"不是风格建议，而是直接按上式做减法。

### TBR 的懒刷新：触发条件与真实代价

正文《TBR 的工作方式》一节已说明"CPU 命令先只做顶点处理，等不得不刷新时才光栅化"；触发条件见正文《TBR 的工作方式》一节，此处不再重复列举。日志补全了正文未单列的两项：

- **切换渲染目标**（正文第 4 条为兜底项，日志把其中的"切换渲染目标"单列）；
- 任何需要读回完整 FrameBuffer 的操作（如 `glReadPixels`）。

每一次刷新都意味着**被本批次触及的 tile 按 load-op 载入、渲染后回写**。因此"帧内频繁切换 framebuffer"的成本不是一次状态切换，而是 `tile 数量 × 往返字节数`，与分辨率成正比。

日志对 alpha-test 的归因比正文更具体：**开启 alpha-test 的 draw 使所在 tile 的 HSR 无法提前剔除**；若它写深度，同 tile 内后续 draw 也不能在它写入前完成深度合并。原因不是 alpha-test 本身慢，而是 alpha 值要等像素着色器跑完才知道，硬件无法在着色前判定该片元是否存活。

这也解释了为什么"用 blending 代替 alpha-test"在 TBDR 上经常是净收益：blending 虽然要按深度排序，但读写都在 SRAM 内，且不破坏 HSR。

TBDR 不只 PowerVR：Apple GPU 与部分 Adreno/Mali 也是 tile/binning 架构，隐藏面剔除机制各异（IDVS/FPK、LRZ、HSR），具体型号与机制**逐项待核实**；**"有 HSR"不是所有 TBDR 的共性**，本文涉及 HSR 的结论只对确认具备该机制的型号成立。

### Draw call 成本的不对称性

机制的完整推导见正文《Draw call 的真实开销》一节。对外解释只需一句口径：**1 个三角形和 1000 个三角形对 GPU 是同一条管线，而 1 个 draw call 和 1000 个 draw call 对 CPU 是 1000 次提交**——所以达到 GPU 极限前，每次提交携带的几何越多越好。

### 用 RenderDoc 定位瓶颈

日志记录的是 RenderDoc 的三块常用视图，按"从粗到细"的顺序使用：

| 视图 | 能回答的问题 | 性能用法 |
|:--|:--|:--|
| Timeline（时间线） | 这一帧有哪些区域、哪些 mesh、pass 的先后与重叠 | 看 pass 划分是否合理、有没有整段空转或重复绘制；确认 RenderTarget 切换次数 |
| Event List（事件列表） | 每个 API/动作的 CPU 时间与 GPU 时间；每个 draw call 的顶点数、VS uniform、用到的纹理与采样器、program 包含哪些 shader、shader uniform 的实际取值 | 按 GPU 时间排序找最贵的 draw；对照顶点数判断是几何瓶颈还是填充率瓶颈；对照纹理格式/数量判断带宽 |
| Texture Viewer（纹理查看） | 每个 RT / 纹理的内容、格式、mip | 确认 G-buffer/中间 RT 的格式是否过宽（如 RGBA16F 本可以 RGBA8）、是否有意外的全屏拷贝（通用经验） |

使用要点：

- 先看 **GPU 时间总和**与 **CPU 提交时间**的比例，确定 bound 方向，再进 Event List 排序，不要一上来就逐条看；
- 单个 draw 的 GPU 时间很短时，测量噪声占比高，应看一帧的累计值或多次采样的中位数；
- Timeline 上的"空档"往往比"长条"更有价值：它说明 CPU 没跟上，或 GPU 在等同步点（`ReadPixels`、`WaitForEndOfFrame`）。

### 大规模点云：网格化索引与视锥裁剪

这是一套面向**道路点云**（条带状、极扁平）的工程方案，目标是在有限内存与 IO 带宽下流畅显示大规模点云。它与正文的通用优化互补：不靠合批，而靠"只加载看得见的那一块"。

#### 预处理五步

1. **PCA 生成 OBB**：对原始点云做主成分分析，得到有向包围盒。原因是道路点云呈**条带集中**分布，轴对齐 AABB 会包进大量空白，浪费网格与加载量。
2. **在包围盒上建二维坐标系**：只保留两个主成分方向。原因是道路点云**近似二维**（沿地面铺开、厚度远小于长度），压扁到二维不会丢失可用的空间划分信息。
3. **矩形网格划分**：把 OBB 划成 $M\times N$ 的二维数组，每个格子对应一个数据块。
4. **重排原始数据并建立偏移映射**：按网格布局重排点云，记录"网格坐标 → 文件字节偏移"的一一映射。这样加载某块时可以直接 `seek` 到文件对应位置读取，**不需要把整个文件读进内存再切分**。
5. **块内随机排序**：让每个块内的点均匀混合，而不是按扫描线/空间顺序聚集在一起。

第 5 步是抽稀的前提：如果块内点按空间顺序排列，取前 $k\%$ 会只留下块的某一角，出现空洞；随机排序后取前 $k\%$ 在统计上均匀覆盖整块。

#### 渲染时的二维视锥裁剪

1. 取视锥的**四条侧棱**，与二维网格所在平面求交，得到四个交点，连成一个四边形（仅当相机俯角大于半垂直 FOV、整个视锥都在地平线以下时成立；地平线入画时上方两条侧棱全在地面之上、没有交点，此时改用最大可视距离 $d_{\max}$ 截断：取视锥 ∩ 地面 ∩ 半径 $d_{\max}$ 的圆，得到一个**扇形多边形**（顶点数随弧段细分而定），第 2 步按它的实际顶点数裁剪）；
2. 用这个多边形（四边形，或上述扇区）裁剪矩形网格区域，得到新的多边形（凸多边形被矩形四条边各裁一次，顶点上限 $4+4=8$，三角形～八边形都可能；实现时顶点缓冲按 8 顶点开）；
3. 对新多边形在二维网格上做**光栅化**：先光栅化多边形的边，再填充内部；实现上**每行只记录左右两端的网格坐标**即可，不需要逐个格子标记；
4. 把光栅化得到的网格集合与"当前已显示"的集合做差，得到需要加载与需要卸载的网格；
5. 加载请求送加载线程，卸载请求送卸载线程。

要点与修正：

- "视锥体的四条侧棱"也可等价地读作**俯视图下四个侧面与地平面相交得到的四条射线**（侧棱与该平面的交点，与这些射线两两相交围出的四边形一致）——但这一等价只在俯角大于半 FOV、整个视锥都在地平线以下（地平线不入画）时成立，属于特例；地平线入画时只有下侧两条侧棱与地面相交，应改用上文的 $d_{\max}$ 截断圆（视锥 ∩ 地面 ∩ 半径 $d_{\max}$）。只需在二维平面求这四条线与网格的交点，无需三维逐块测试。本质是把三维视锥投影到 OBB 的二维坐标系里，退化成一个二维凸多边形裁剪问题，复杂度从"逐块做三维测试"降到"一次多边形光栅化"。
- 光栅化输出的是**网格索引区间**（每行一段），后续做集合差是 $O(\text{行数})$ 级别的，比逐网格点测试便宜得多。
- 工程代码里 `CalcArea::rasterize` 在 OSG 工程中以 **x、z 作为宽高**。换到不同 up 轴的引擎时需核对轴映射（**待核实**）。
- 视口适当放大可以一次算出更大的"有效区"，用这个更大的区域去更新缓存，减少边缘处频繁的加载/卸载抖动。

#### 按距离抽稀

预处理已给每块做了随机排序，因此**按比例取前 $k\%$ 的点即可实现均匀抽稀**：读取起点固定在 0，只读前 `count × k%` 个点（`readCount = count × k%`）；也可以用跨步读取（stride 取 $1/k$ 的整数近似，逐块跨步采样）。**不要把偏移设成 `count × k%`**：那等于丢掉头部、只取尾部 $(1-k)\%$ 的点集，$k=0.9$ 时只剩 10%。

渲染时用**网格中心到视点的距离**动态设置这个比例：

$$
k=\operatorname{clamp}\left(\frac{d_{\text{near}}}{d},\;k_{\min},\;1\right)
$$

- 近处 $d$ 小 → $k$ 接近 1，全量显示；
- 远处 $d$ 大 → $k$ 降到下限，单块点数大致按 $1/d$ 下降；
- 由于块内随机排序，任意 $k$ 的子集都是均匀采样，不会出现局部空洞或条纹。

这比"按距离切 LOD 模型"更适合点云：点云没有拓扑，抽稀只需要一个稳定的采样顺序；随机排序把这个顺序一次性烘焙进文件，运行时零成本。

### 八叉树与流式加载的调度

同一项目的另一组调度结论（对象是点云八叉树 + 分块加载）：

**八叉树构建**

- 递归终止条件：**层级 ≥ 10，或节点空间内点数 < 2**。日志确认"不会有点没被包含在树上"——终止时节点直接持有剩余点，不再细分（**推断**）。
- 建树时**不把空 index 包含在内**，避免大量空节点占用内存与遍历时间。
- 层级上限 10 推测是内存折中（**推测**）：再深一层，节点数最多翻 8 倍，而单节点点数已经很少，新增节点的收益递减（具体阈值随点数规模变化，**待核实**）。

**调度与并发**

1. **锁竞争是主要瓶颈之一**：加载线程与卸载线程共用一把数据锁时，IO 的等待会串行化整个调度。可行方向是按块加锁、双缓冲交换，或无锁队列（日志只记录了问题，未记录最终实现）。
2. **视锥剔除放到独立线程**（计划项，落地待核实）：剔除只读场景数据、产出请求列表，与渲染线程解耦，避免每帧在主线程做全量遍历。
3. **卸载用交换代替删除**：把待卸载元素与容器末尾交换后 `pop_back`，均摊 $O(1)$；直接 `erase` 是 $O(n)$，在每帧都有大量上下线时会成为热点。日志中这是**方案**，是否落地**待核实**。
4. **请求生成与缓存管理拆成两个模块**（计划项，落地待核实）：请求模块只负责"这一帧需要哪些块"，缓存模块负责"已有哪些块、淘汰谁"。拆开后请求可以按固定频率（如每秒一次）重算，而不是每次交互都算，降低 CPU 峰值。
5. **先打通"磁盘 → 内存 → 节点"，再改为"磁盘 → 节点"**：分两步落地，第一步保证正确性，第二步去掉中间拷贝。直接做零拷贝会让 IO 格式、节点生命周期、失败回滚同时变复杂。
6. **优先保证首帧可见**：日志记录"缓存的加载影响了场景载入"，处置是去除缓存区，并把"视口先加载"列为替代方案（是否落地**待核实**）。这说明**流式加载的首屏时间比缓存命中率更重要**；若要保留预加载，应放到视口首批数据之后异步进行。
